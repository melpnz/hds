## Типы правил

Каждый существенный вывод в документе имеет статус. Статус важнее формулировки: он говорит, **насколько мы уверены, что свойство действительно является правилом**.

| Статус | Что означает | Как применять |
|---|---|---|
| **OBSERVED** | Факт, замеренный на существующих production-страницах. Описание того, как есть | Не инструкция. Используй как свидетельство, не как требование |
| **INVARIANT** | Свойство, которое с высокой вероятностью является частью идентичности продукта. Нарушение делает интерфейс чужим | Сохраняй при создании нового интерфейса этого продукта |
| **DEFAULT** | Рекомендуемое решение, если нет функциональной или художественной причины поступить иначе | Бери по умолчанию, отклоняйся осознанно |
| **FREEDOM** | Область, которую дизайнер меняет свободно | Не считай существующие значения ограничением |
| **AVOID** | Решение, которое по имеющимся данным обычно даёт результат, плохо соответствующий направлению | Не запрет. Отклоняйся, если понимаешь зачем |
| **NEVER** | Абсолютный запрет | Используется редко и только там, где обоснован |

**Ключевое различие, которое нужно держать в голове:**

* `OBSERVED — в 9 из 11 проектов основной текст набран Inter` — это описание выборки.
* `INVARIANT — Inter обязателен` — это совсем другое утверждение, и оно требует отдельных оснований.

Там, где статус не проставлен явно, значение по умолчанию — **OBSERVED**.

### Design DNA и Implementation conventions

Документ разделяет два уровня:

* **Design DNA** — визуальные и композиционные свойства: типографический характер, плотность, композиция, whitespace, поведение цвета, геометрия, характер карточек, иерархия, art direction. Это то, что может стать инвариантом.
* **Implementation conventions** — особенности конкретной реализации: фреймворк, стратегия rem, набор медиазапросов, именование классов, структура CSS. Это **не бренд**, а следствие технологии. Вынесено в §18.

Технические ограничения production не выдаются за визуальные принципы бренда.

## 1. Design DNA

> **Статус раздела: OBSERVED.** Ниже — характеристика того, как продукт выглядит сейчас. Какие из этих свойств являются осознанной позицией дизайн-команды, а какие — накопившейся реализацией, по production не определить. Классификация по силе — в §2, вопросы к Figma — в §20.

1. **Плиточный layout на сером фоне.** Страница — это серое полотно `#f0f0f0`, на которое положены белые прямоугольные блоки шириной 780px с зазором 12px между ними. Блок — не «карточка с тенью», а именно плитка: белая заливка, нулевой радиус на десктопе, никакой границы.
2. **Очень маленькие радиусы.** Доминирующее значение — **3px** (116 вхождений на ленте против 23 у 4px). 8px встречается почти исключительно на изображениях и обложках. Радиус 12/16/24px в интерфейсе Хабра не используется.
3. **Теней нет.** На всей ленте — одна тень, и та `inset` фокус-кольцо. Иерархия строится фоном (`#fff` / `#f7f7f7` / `#f0f0f0`) и тонкими разделителями.
4. **Два шрифта с чётким разделением ролей.** `Fira Sans` — только заголовки, табы и «титульные» элементы. Системный стек — весь остальной текст, включая тело статьи. Смешение ролей сразу читается как чужеродное.
5. **Высокая информационная плотность.** Тело статьи — 16/24. Метаданные — 13/15. Кнопки — 32px, поля ввода — 40px, табы — 42px. Иконки — 24px. На экране 1440×900 помещается 3–4 полных сниппета статьи.
6. **Приглушённый сине-серый акцент.** `#548eab` — не яркий, низконасыщенный. Используется на ссылках, активных табах, счётчиках. Никогда не заливает крупные площади.
7. **Тёмно-серая шапка, не чёрная и не брендово-цветная.** `#313c45` — сине-серый графит. Подвал — того же семейства, нижняя полоса темнее: `#1e2124`.
8. **Широкая мера текста.** Абзац статьи — 740px при 16px. Это ~90–100 знаков в строке, заметно шире «книжного» идеала. Это осознанная черта Хабра, а не ошибка.
9. **Аватары — квадраты со скруглением 3px.** Не круги. Это одно из самых узнаваемых отличий Хабра.
10. **Декоративной графики почти нет.** Градиенты, паттерны, иллюстрации в UI отсутствуют. Вся визуальная нагрузка — на пользовательском контенте: превью статей, обложки событий, логотипы компаний.

---

### Информационная плотность

* Плотность **высокая**. Сниппет статьи с превью занимает ~230–280px по высоте при ширине 780.
* Whitespace экономный: 12px между плитками, 16px между колонками. Пустых пространств больше 32px внутри контента практически не бывает.
* Элементы мелкие: контрол 32, иконка 24, аватар 24–48.
* Регистр — **editorial**, не marketing и не dashboard. Страница читается как лента публикаций, где текст важнее оформления.
* Пропорция: примерно 80% площади плитки занято контентом, 20% — отступами.

## 2. Core principles

Правила отсортированы по силе. Статус важнее формулировки.

| # | Правило | Статус | Основание |
|---|---|---|---|
| 1 | Страница — **серое полотно с белыми плитками**, а не одно белое поле. Контент лежит в блоках шириной 780px с зазором 12px на фоне `#f0f0f0` | **INVARIANT** | Фундаментальный layout-паттерн, воспроизведён на всех 7 страницах: лента, статья, поток, профиль пользователя, профиль компании, события, событие |
| 2 | Контейнер `max-width: 1096px` + `padding: 0 24px`; main 780, sidebar 300, зазор 16 | **INVARIANT** | Класс `.tm-page-width` даёт идентичные значения на всех 7 страницах. Реальная сущность в коде, а не совпадение |
| 3 | Цвета берутся **только из токен-контракта**, одинакового в светлой и тёмной теме | **INVARIANT** | Единственный продукт экосистемы с полноценной тёмной темой; хардкод hex ломает её (см. §18) |
| 4 | Акцент живёт в тексте, иконке, 1px-обводке и подложке с альфой — но не заливает крупные площади | **INVARIANT** | Поведение цвета — свойство DNA. `#548eab`: 290 текстовых и 98 border-вхождений против 17 фоновых |
| 5 | Радиусы **малые**. Крупных скруглений в интерфейсе нет | **INVARIANT** (характер) / **DEFAULT** (значения) | Гистограмма: 3px ×116, 8px ×52, 4px ×23. Конкретно 3px — DEFAULT; «малый радиус вместо крупного» — DNA |
| 6 | Заголовки — `Fira Sans` weight 500; тело — системный стек weight 400 | **INVARIANT** (разделение ролей) / **DEFAULT** (веса) | Fira Sans подключена с весами 400/500/700, но используется фактически только 500 и только на заголовках и табах. Смешение ролей читается как чужеродное |
| 7 | Радиус контрола 3px; изображения 8px; плитка 0 | **DEFAULT** | Систематично, но это значение реализации, а не проверенное решение дизайн-системы. См. §20 |
| 8 | Высоты: кнопка 32, поле ввода 40, таб 42 | **DEFAULT** | Замерено стабильно, но набор контролов в выборке узкий |
| 9 | Отступы из набора `2 / 4 / 8 / 12 / 16 / 20 / 24 / 32` | **DEFAULT** | Восстановлено по частотности, формальной шкалы в коде нет |
| 10 | Иконки 24×24, заливкой | **DEFAULT** | Единообразно во всей выборке; icon set по production не опознаётся (см. §20) |
| 11 | Sidebar только справа | **DEFAULT** | 7/7 страниц. Левой навигации в Habr нет — но она есть в Q&A, значит это не запрет экосистемы |
| 12 | Тени не используются | **OBSERVED** → **DEFAULT** | На всей выборке 1 тень (focus-ring). Это сильное наблюдение, но **вывод из отсутствия**: возможно, тень просто не понадобилась. Не NEVER |
| 13 | На ≤1023 sidebar убирается; на ≤767 плитки full-bleed, header 80px | **OBSERVED** | Прочитано из реальных `@media` Habr, см. §4. Одновременно Implementation convention — см. §18 |
| 14 | Мера текста статьи 740px при 16/24 | **OBSERVED** → **DEFAULT** | ~90–100 знаков в строке. Заметно шире типографской нормы; преднамеренность не подтверждена (см. §20) |

**Чего в этой таблице нет.** Ни одно правило Habr не выведено на уровень NEVER. Единственный кандидат — хардкод цвета вместо переменной, потому что он ломает существующую тёмную тему.

## 3. Layout

### 3.1. Контейнеры

```
.tm-page-width      max-width: 1096px;  padding: 0 24px;   (внешняя ширина 1144px)
.tm-page__wrapper   display: flex;      (внутри 1096px)
.tm-page__main      width: calc(100% - 316px);  → 780px
.tm-page__sidebar   width: 300px;
зазор между колонками: 16px  (316 = 300 + 16)
```

**Evidence:** `/ru/feed/`, `/ru/companies/selectel/articles/1068446/`, `/ru/flows/backend/articles/`, `/ru/events/`, `/ru/users/techno_mot/` — на всех пяти `.tm-page-width` даёт w=1144, max-width=1096, padding-left/right=24. HIGH.

### 3.2. Внутренняя анатомия плитки

```
блок (белая плитка)     width: 780px;  background: #fff;  margin-bottom: 12px;
контент внутри плитки   width: 740px   (т.е. горизонтальный padding 20px)
шапка блока             margin-left: 20px; width: 740px;
```

Вертикальные паддинги плитки варьируются по типу: `16px 20px` (сниппет), `20px` (виджет), `24px 20px` (крупный блок). HIGH.

### 3.3. Отступы страницы

```
.tm-page  padding-top: 12px (страница статьи) / 200px (лента с рекламным баннером сверху)
          padding-bottom: 60px
```

Верхний отступ 200px на ленте — следствие рекламного слота, не правило. Для нового сервиса бери **`padding: 12px 0 60px`**.

### 3.4. Типы страниц

| Layout | Основная колонка | Sidebar | Особенности |
|---|---|---|---|
| **Listing** (лента, поток) | 780 | 300 | Плитки-сниппеты подряд, 12px между ними; сверху плитка фильтров 780×98 |
| **Article** | 780 (`.tm-article-presenter`, max-width 780) | 300 | Текст 740px; над контентом опциональная обложка компании 1096×249 |
| **Profile** (пользователь/компания) | 780 | 300 | Верхняя плитка-шапка профиля, ниже табы 42px, ниже контент |
| **Events listing** | 780 | 300 | Карточка события — grid `476px 244px`, gap `8px 20px`, изображение справа 244×138 |
| **Full-width** | 1096 | нет | Используется редко: посадочные внутри Хабра |

### 3.5. Правила вложенности

```
body (#f0f0f0)
└ header.tm-header                      (56, sticky, #313c45)
  └ .tm-page-width → .tm-header__container  (1096, padding 12px 0, flex gap 16)
└ main
  └ .tm-page                            (padding 12px 0 60px)
    └ .tm-page-width                    (1096 + 24)
      └ .tm-page__wrapper               (flex)
        ├ .tm-page__main                (780)
        │   └ блок (белый, mb 12)
        │       └ контент (740, т.е. padding 0 20)
        └ .tm-page__sidebar             (300)
            └ блок (белый, mb 12)
└ .tm-footer-menu                       (#313c45)
└ .tm-footer                            (48, #1e2124)
```

Глубже трёх уровней вложенности контейнеров не уходи.

## 4. Responsive rules

Медиазапросы, найденные в стилях Хабра (по частоте): `(max-width: 767px)` ×57, `(min-width: 1024px)` ×19, `(min-width: 768px)` ×9, `(min-width: 768px) and (max-width: 1023px)` ×7.

| Breakpoint | Что меняется | Confidence |
|---|---|---|
| **≥ 1024px** | Полный layout: container 1096 + 24, main 780, sidebar 300, зазор 16 | HIGH |
| **1024–1143px** | Container сжимается: при 1024 ширина 1024, padding 24 → main ≈660, sidebar 300 сохраняется, контент плитки ужимается до 620 | HIGH |
| **768–1023px** | **Sidebar убирается полностью.** Основная колонка на всю ширину. Container `max-width: 768px`, `padding: 0 16px`. Плитки при этом получают `.tm-page-width_no-padding` → выходят на всю ширину, контент внутри остаётся с padding 20 (768 − 40 = 728) | HIGH |
| **≤ 767px** | Page padding обнуляется (плитки **full-bleed** от края до края). Header вырастает **56 → 80px** (две строки: логотип + поиск/бургер). Сниппеты идут одной колонкой | HIGH |
| **≤ 483 / ≤ 414 / ≤ 330px** | Точечные правки мелких блоков (счётчики, даты). Отдельным брейкпоинтом не считать | LOW |

**Что делает mobile:**

* Sidebar → полностью удаляется (не переносится вниз).
* Плитки → full-bleed, белое на белом краю экрана; серый фон виден только в зазорах 12px между плитками.
* Header → 80px, две строки, бургер слева.
* Табы → горизонтальный скролл.
* Grid карточки события `476px 244px` → одна колонка, изображение сверху.
* Таблицы → `overflow-x: auto` на обёртке.

## 5. Typography

### 5.1. Шрифты

```css
--font-title: "Fira Sans", sans-serif;                                  /* заголовки, табы */
--font-ui:    -apple-system, BlinkMacSystemFont, Arial, sans-serif;     /* всё остальное */
--font-mono:  Menlo, Monaco, Consolas, "Courier New", Courier, monospace;
```

Fira Sans подключается через Google Fonts с весами **400, 500, 700**. В интерфейсе фактически используется **только 500**.

Соотношение по ленте: системный стек — 2360 элементов, Fira Sans — 98. Fira — акцентный шрифт, не основной. HIGH.

`letter-spacing` — везде `normal`, кроме табов (`.8px`) и отдельных элементов шапки (`.3px`).

### 5.3. Правила

* H1 в статье — **32/40**, не больше. «Маркетинговых» 48–64px в продуктовом Хабре нет.
* Между H2 и следующим абзацем — 12px; перед H2 — 32px.
* Мера абзаца — 740px. Не сужай до 640–680px «для читаемости»: это не язык Хабра.
* Заголовки никогда не uppercase (кроме табов).
* Числа в счётчиках — weight 700, цвет акцента.

## 6. Colors

Первоисточник — файлы темы продукта `client/css/theme/light-v2.css` и `dark-v2.css` (release 2.346.0). Значения в них заданы в **HSL**; ниже приведены и исходный HSL, и вычисленный HEX.

### 6.4. Правила использования

* **Основа палитры — четыре цвета:** `#333333`, `#8f8f8f`, `#ffffff`, `#f0f0f0`. Ими закрывается 80% интерфейса.
* **Акценты точечные:** `#548eab` (ссылка/активное), `#7ba800` (позитив), `#d04e4e` (негатив). Суммарно занимают единицы процентов площади.
* **Никогда на больших площадях:** `--accent-*`, `--complexity-*`, `--label-*`. Их место — цвет текста, цвет иконки, 1px обводка, подложка с альфой `0.12`.
* **Единственное исключение** — `--comments-*`: они действительно заливают блок комментария целиком, и это строго регламентировано четырьмя случаями.
* **Градиенты в продуктовом UI не используются вообще.**
* **Тёмная тема обязательна — NEVER хардкодить hex в компонентах,** только `var(--token)`. Это единственный абсолютный запрет в документе: он ломает существующую тёмную тему. Тёмная тема не является инверсией светлой: `--icon-primary` в ней темнеет (`#929ca5` → `#666666`), а `--accent-primary` светлеет и насыщается (`#548eab` → `#4cb6eb`).

* Толщина только **1px**.

* `box-shadow: none` — норма.
* Единственные допустимые: `0 0 0 1px inset #548eab` (фокус) и `0 -1px 0 0 inset rgba(146,156,165,.4)` (линия таб-бара).

3. Разделитель `.tm-header__divider` — вертикальная линия 1px.
4. «Все потоки» — 14/18, белый, padding `8px 0`.
5. Промо-ссылка (`.link`, 14/18, `letter-spacing: .3px`) — опциональный слот.

## 11. Images & assets

### Аватары: единое правило экосистемы

Это **нормативное правило, общее для всех продуктов и площадок Хабра**. Оно имеет приоритет над тем, что сейчас реализовано на конкретной странице.

| Тип сущности | Форма | Радиус в этом продукте |
|---|---|---|
| **Пользователь / человек** (автор, комментатор, эксперт, специалист, спикер) | **Круг** | `border-radius: 50%` |
| **Компания, хаб, поток, тег, школа, проект, бренд** | **Квадрат со скруглением** | `border-radius: 3px` |

Правило действует на все размеры аватара и во всех контекстах: список, карточка, шапка профиля, строка автора, комментарий, выпадающее меню.

**Почему так:** круг читается как «человек», скруглённый квадрат — как «организация». Разделение форм позволяет отличить сущности с одного взгляда, без чтения подписи, и работает одинаково во всех продуктах экосистемы.

**Служебные требования:**
* `object-fit: cover` — изображение не должно искажаться;
* заглушка (инициалы или иконка) наследует ту же форму и радиус;
* рамку аватару не добавляй — форма уже отделяет его от фона;
* индикатор статуса (онлайн, верификация) ставится в правый нижний угол бокса аватара.

> **Отклонение от текущей реализации:** на `habr.com` сейчас **все** аватары квадратные с `border-radius: 3px` — и пользовательские, и компанийские (замерено: `a.avatar`, `a.tm-user-info__userpic` на 24 / 40 / 48px). Новое правило меняет форму пользовательского аватара на круг. Аватар компании остаётся квадратом 3px — как сейчас.


* **Превью статьи** — `border-radius: 8px`, `object-fit: cover`, ширина 100% колонки.
* **Обложка события** — 244×138 на десктопе (≈16:9), плейсхолдер `#f0f0f0`.
* **Обложка компании** — 1096×249 (≈4.4:1), над контентом, radius 0.
* **Сторис** — 124×220 (≈9:16), radius 8px.
* **Аватар пользователя** — 24 / 40 / 48 px, **radius 3px**, квадрат.
* **Логотип компании** — квадрат, radius 3px, вписан.
* **Иконки** — SVG **24×24**, `fill`, без обводки. Цвет покоя `#bcced7` или `#929ca5`, активный — `#548eab`. Иконка ставится перед текстом с gap 4–8, выравнивание по центру строки.
* **Декоративной графики нет.** Не добавляй иллюстрации, паттерны, 3D, «абстрактные фигуры» — это чужой язык.

## 13. Interaction & motion

* **hover** — только смена цвета текста/иконки на `--*-hover`. Ни `transform`, ни `box-shadow`, ни изменение размера.
* **focus** — `box-shadow: 0 0 0 1px inset #548eab`.
* **active/selected** — заливка `#548eab` + белый текст (сегменты, табы) или подчёркивание.
* **disabled** — `#bfbfbf`, `cursor: default`.
* **loading** — скелетон: прямоугольники `#f0f0f0` с radius 3px, повторяющие геометрию контента.
* **error / success** — `#d04e4e` / `#7ba800` в тексте и границе.

**Motion:** значимой системы анимации нет. В computed styles преобладает `transition: all` без явных длительностей; единичные значения — `0.3s`, `0.3s ease-in-out`. Опирайся на:

```css
--motion-duration: 150ms;
--motion-easing: ease;
```

и применяй только к `color`, `background-color`, `border-color`, `opacity`. Scroll-анимаций, параллакса, появления по вьюпорту в продуктовом Хабре **нет** — не добавляй.

## 14. Do / Don't

> **Как читать этот раздел.** Пункты «так делать не нужно» — это **AVOID**: по имеющимся данным такие решения обычно дают результат, плохо соответствующий направлению. Это не абсолютные запреты. Пункты, помеченные **NEVER**, — единственные, где запрет обоснован жёстко.
>
> Значительная часть списка выведена из **отсутствия** приёма в выборке. Отсутствие в production ≠ запрет: возможно, приём просто не понадобился, или он есть в макетах, которые мы ещё не видели. Такие пункты помечены `(вывод из отсутствия)` и подлежат проверке в Figma.


### Так делать нужно

* Белые плитки 780px с зазором 12px на сером `#f0f0f0`.
* Радиус 3px на контролах, 8px на изображениях, 0 на плитках.
* Fira Sans 500 на заголовках, системный стек 400 на тексте.
* Метаданные 13px `#8f8f8f`.
* Кнопки 32px, поля ввода и select 40px, табы 42px.
* Иконки 24×24 fill, `#929ca5`.
* Аватар пользователя — круг `50%`; аватар компании/хаба — квадрат `3px`.
* Правый sidebar 300px, зазор 16px.
* Отключать sidebar на ≤1023 и делать плитки full-bleed на ≤767.

### Так делать не нужно

* ❌ **Радиусы 12/16/24px** — сразу читается как Career или Courses, не Хабр.
* ❌ **Круглый аватар у компании или хаба** — круг зарезервирован за человеком.
* ❌ **Pill-кнопки и pill-теги** (`border-radius: 999px`) — не встречаются ни разу `(вывод из отсутствия)`.
* ❌ **Мягкие тени / elevation** (`0 4px 12px rgba(0,0,0,.1)`) — их в продукте нет `(вывод из отсутствия)`.
* ❌ **Крупные кнопки 44–56px** — кнопка в Хабре 32px, поле ввода 40px, таб 42px.
* ❌ **Крупные маркетинговые заголовки 48–72px** — H1 в Хабре 32px.
* ❌ **Градиенты** любого рода в UI `(вывод из отсутствия)`.
* ❌ **Заливка акцентом больших площадей** — `#548eab` только точечно.
* ❌ **Glassmorphism, backdrop-blur, неоновые свечения.**
* ❌ **Просторный layout** с 40–80px воздуха между блоками — Хабр плотный.
* ❌ **Иллюстрации и декоративная графика в интерфейсе** `(вывод из отсутствия — иллюстративный язык Хабра по production не восстанавливается, см. §20)`.
* ❌ **Обводочные (stroke) иконки** — Хабр использует заливку.
* ❌ **Fira Sans в теле текста** и системный шрифт в H1 — роли не менять.
* ❌ **Sidebar слева** — это язык Q&A, не Хабра.
* ❌ **Сужение меры текста до 640px** — в Хабре она 740px.
* ❌ Border на каждом блоке — Хабр разделяет зазором и фоном.

## 17. Сводка правил

> Концентрат разделов 1–16. **Это спецификация, а не готовый prompt для coding-агента.** До валидации в Figma использовать её как основу генерации интерфейсов преждевременно: часть правил здесь — OBSERVED, а не INVARIANT.

> **When building a Habr (habr.com) interface:**
>
> * Use container `max-width: 1096px` with `padding: 0 24px`; main column `780px`, right sidebar `300px`, gap `16px`. Never place a sidebar on the left.
> * Put page background `#f0f0f0` and render content as **white tiles** of width 780px with `margin-bottom: 12px`. Tiles have `border-radius: 0`, no border, no shadow. Inner horizontal padding is `20px`.
> * Use `border-radius: 3px` for every control, tag and badge; `8px` only for images and covers. Never use 12px, 16px, 24px or pill radii.
> * Add **no box-shadow** anywhere except a focus ring `0 0 0 1px inset #548eab`.
> * Headings use `"Fira Sans", sans-serif` at weight **500**: H1 `32/40`, H2 `22/32`, H3 `18/26`. Body text uses `-apple-system, BlinkMacSystemFont, Arial, sans-serif` at `16/24`, weight 400, color `#333333`.
> * Metadata (dates, counters, captions) is `13px`, color `#8f8f8f`. Never larger.
> * Buttons are `height: 32px`; inputs, selects and date fields are `height: 40px` with `border: 1px solid #bcced7`, `border-radius: 3–4px`, `padding: 0 14px`, `font-size: 14px`; tabs are 42px. Never 44 or 48px.
> * Use accent `#548eab` only for links, active tabs, counters and 1px outlines. Never fill a large area with it.
> * Icons are SVG `24×24`, **fill-based**, color `#929ca5` (`#bcced7` when passive), placed before text with a 4–8px gap.
> * Avatars follow the ecosystem rule: a **person is a circle** (`border-radius: 50%`), a **company / hub / flow / tag is a rounded square** (`border-radius: 3px`). Sizes 24 / 40 / 48, `object-fit: cover`, no border.
> * Spacing scale is `2 4 8 12 16 20 24 32`. Nothing else.
> * Header: `height: 56px`, `position: sticky`, background `#313c45`, white text, no border, no shadow. Footer: menu block `#313c45` with `padding: 20px 0`, then a 48px bar `#1e2124`.
> * Article text measure is **740px** at 16/24 — do not narrow it.
> * On `max-width: 1023px` remove the sidebar entirely (do not stack it below).
> * On `max-width: 767px` set container padding to 0 so tiles go **full-bleed**, and grow the header to `80px` with a burger.
> * Prefer plain flat surfaces: separate blocks with the 12px gap and the grey page background, not with borders.
> * Never add gradients, illustrations, decorative graphics, glassmorphism, hover lift, scroll animation or marketing-sized headings.
> * Transitions only on `color`, `background-color`, `border-color`, `opacity` at `150ms ease`.
> * Support dark mode by overriding the same variable names: `--text-main: #dedede`, `--background-primary: #171717`, `--background-gray: #080808`, `--accent-primary: #4cb6eb`, `--header-background: #0d0d0d`.

### 18.2. Existing design tokens

**Token maturity: NATIVE.**

Единственный продукт экосистемы, где токен-слой прочитан **из исходника**, а не восстановлен по замерам.

| Источник | Содержимое |
|---|---|
| `client/css/theme/light-v2.css` | **43 объявления**: 41 цветовой токен + `--formula-filter` + `--cm-name` |
| `client/css/theme/dark-v2.css` | те же 43 имени с другими значениями |
| inline `:root` | `--z-index-loader: 1000`, `--z-index-header: 1001`, `--z-index-overlay: 1002`, `--z-index-footer: 991`, `--z-index-popovers: 992`, `--ipad-locked-header-shift: 0` |

Значения заданы в **HSL**, не в HEX. Полная таблица с обеими нотациями — в §6.

**Расхождение с исходной сводкой:** в постановке указано «~41 variables». Фактически — **43 объявления** в каждом файле темы (41 цветовое + 2 служебных), плюс отдельный слой z-index из 6 переменных, не входящий в тему.

**Что токенизировано:** цвет (полностью, обе темы), z-index (полностью).

**Что не токенизировано:** типографика, отступы, радиусы, размеры контролов, ширины контейнеров, брейкпоинты — всё это литеральные значения в компонентных CSS-чанках.

**Кандидаты на будущую нормализацию** (гипотезы, не предложение системы): container width, tile gap, control heights, radius scale, spacing scale, typography scale. Проектировать их сейчас преждевременно — сначала нужно понять, что об этом говорит Figma.

### 18.3. Media queries — это Implementation convention

Habr — один из немногих случаев, где `@media` **читаются напрямую** (тема лежит на том же домене). Частотность:

`(max-width: 767px)` ×57 · `(min-width: 1024px)` ×19 · `(min-width: 768px)` ×9 · `(min-width: 768px) and (max-width: 1023px)` ×7 · `(max-width: 1023px)` ×3

Плюс единичные `750 / 483 / 414 / 330 / 1025 / 1026 / 1143 / 1156 / 1221 / 960` — точечные правки, не система.

Схема **desktop-first** (`max-width`) — техническое соглашение, а не свойство дизайна. Q&A для сравнения написан mobile-first и выглядит при этом не «более мобильным».

## 19. FUTURE ARTIFACTS

**Рекомендуемый артефакт: UI KIT.**

Обоснование:

* повторяющийся продуктовый интерфейс с устойчивым набором компонентов — плитка, сниппет статьи, карточка события, блок сайдбара, табы, сегменты фильтра, форма;
* **уже существует NATIVE token-слой с двумя темами** — UI kit получает готовый цветовой фундамент, а не строит его с нуля;
* компоненты имеют стабильные имена в коде (`tm-*`), которые можно сопоставить с Figma-компонентами напрямую.

**Условие:** сначала §20. UI kit, построенный по production без сверки с Figma, зафиксирует текущую реализацию вместе с её legacy-слоями.

**Порядок работ после Figma:** сверить token-контракт → определить актуальную версию header и карточек → построить UI kit → дополнить его тем, чего в production нет (спецификации фокуса, состояний загрузки, motion).
