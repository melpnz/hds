# Учёт токенов по этапам

Использовать при каждом новом ревью. Не восстанавливать расход прошлых прогонов по размеру файлов или длине текста.

Начинать журнал сразу после определения папки прогона. Предшествующие сообщения не распределять задним числом. В отчёте отдельно видны незарегистрированные стандартные этапы; наличие одного измеренного интервала не делает учёт всего ревью полным.

До начала каждого этапа:

```text
node "$SKILL_DIR/scripts/stage-usage.mjs" <run> start <stage>
```

После этапа:

```text
node "$SKILL_DIR/scripts/stage-usage.mjs" <run> end <stage>
```

Этапы: `context` (задача и сценарии), `figma` (макет), `capture` (съёмка), `compare` (автоматика), `curation` (визуальная проверка, картинки, исправление описаний), `report` (сборка и проверка), `feedback` (разбор решений). Повторные попытки — отдельные интервалы с тем же названием или понятным суффиксом. Для нескольких страниц вести один журнал в корне общего прогона и включать название страницы в название этапа.

Скрипт использует только текущий идентификатор сессии `CODEX_THREAD_ID` / `CLAUDE_SESSION_ID`. Если окружение его не передаёт, явно передать `--log <полный путь к текущему JSONL>` в команде `start`. Не брать «самый свежий» чужой разговор. Codex: последние накопительные `total_token_usage`; Claude: usage уникальных assistant message id, повторные записи одного id не суммируются повторно. Сохраняются только счётчики, не тексты сообщений и не секреты.

Если приложение отдаёт показатели только через свой интерфейс, их можно внести отдельно:

```text
node "$SKILL_DIR/scripts/stage-usage.mjs" <run> record <stage> --input <число> --output <число> --cached <число> --source <название источника>
```

В `--input` указывать весь вход, включая кэш, в `--output` — весь выход, включая reasoning, если он включён в usage провайдера. Cached и reasoning — разбиение счётчиков, а не дополнительные токены к общей сумме. У Claude полный вход — `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`; у Codex вход уже включает cache. Неполученное разбиение — `null`, не ноль.

Счётчики опубликованных запросов могут запаздывать. Разность между контрольными точками — зарегистрированный интервал, не обещание точной границы мыслительного этапа; текущий незавершённый ответ может попасть в следующий интервал. Без новых счётчиков, при сбросе или смене сессии этап отмечается `unavailable`. Запущенный и незакрытый этап остаётся `running`. Не выдумывать оценки и не называть неполную сумму полным расходом. Нельзя распределять общий расход между этапами пропорционально времени. Параллельную работу других агентов учитывать отдельно и только если известно, что родительский счётчик её уже не включает.

Данные — `<run>/token-usage.json`. В отчёт и feedback попадает очищенная сводка с этапами, временем, входом/выходом/кэшем, источником, доступностью и измеренной суммой. Для завершённого отчёта закрыть `report`, затем пересобрать HTML, чтобы включить последнюю опубликованную контрольную точку. Простой пересборкой старого отчёта расход не измерить. Для нового `feedback`-этапа журналировать отдельно и снова пересобрать отчёт; не создавать бесконечный цикл ради токенов последней пересборки.

Показатели нужны для сравнения качества и расхода между версиями, а не для расчёта стоимости или процента квоты подписки.

Источники формата usage: [OpenAI — counting tokens](https://developers.openai.com/api/docs/guides/token-counting), [Claude — prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).
