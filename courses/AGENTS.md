# Контракт для модели · Хабр Курсы v1.1

Размеры интерфейса берутся из `machine/dimension-tokens.json`, production-палитра — из `machine/tokens.json`, а нейтральные назначения активного provider — из `machine/semantic-tokens.json`; CSS-переменные подключаются через `ui/courses.css`. Масштабируемая база — `0.25rem` при эталонном root `16px`; границы и толщина focus ring остаются в `px`, line-height использует безразмерные токены. Новые размеры не записывай литералами. Остальные значения сверяй с `machine/reports/dimension-exceptions.md` и не округляй без дизайнерского решения.

Канон пакета — адресные файлы `machine/`; viewer лишь отображает их.

## Текущая реализация

Текущий implementation provider — `courses-nuxt-kit/`. В продуктовом проекте
его `layers/courses` копируется локально и считается vendored/read-only кодом:
не изменяй, не форматируй и не переименовывай файлы внутри layer. Разрешено
создавать любые application-компоненты, wrapper-компоненты и композиции страниц
вне layer, используя его публичные props и slots.

Если публичного API не хватает, опиши недостающую возможность и подготовь запрос
владельцу кита вместо локального форка. Изменять канонический
`courses/courses-nuxt-kit/` можно только в явно поставленной владельцем задаче по
поддержке самого кита. Первоначальная установка отсутствующего layer по
зафиксированным URL из `machine/consumer-workflow.json` разрешена и обязательна
для реализации в Nuxt. При работе с уже установленным layer один раз в начале
задачи запусти read-only проверку версии и integrity из его `AGENTS.md`. Только
предложи доступное обновление: не скачивай и не заменяй layer без явного решения
пользователя, особенно если integrity показывает локальные изменения.

## Порядок чтения

1. `machine/index.json` — статус, границы, активный implementation provider и
   доступные проверки.
2. Для Nuxt открой `machine/consumer-workflow.json` и проверь локальный
   `layers/courses/courses-kit.manifest.json`. Если distribution.availability
   равна `prepared-not-published`, будущий архив не скачивать: сообщить, что
   выпуск ещё не опубликован, или использовать предоставленный владельцем локальный слой.
   Для опубликованного выпуска, если layer отсутствует — скачай
   указанные там release-архив и checksum, проверь SHA-256 и скопируй
   `layers/courses` целиком. Если GitHub недоступен, сообщи об этом; не
   воспроизводи компоненты кита вручную. Существующий layer без прямого решения
   пользователя не заменяй.
   Если совместимый layer уже существует, выполни его read-only update check;
   недоступность GitHub не мешает использовать локальную версию.
3. `machine/compatibility.json` — проверенная пара версии гайда и локального
   provider. Если версия локального manifest не перечислена как совместимая,
   не смешивай её с этим гайдом без отдельной сверки.
4. `machine/providers/courses-nuxt-kit.json` — компактное соответствие
   стабильного guide-id текущему export/source/preview. Для выбранного компонента
   открой только его `apiFile`: там находится сгенерированный публичный API
   (`props`, `slots`, `emits`, `models`). Если mapping прямой, используй компонент,
   а не перевёрстывай его по example или скриншоту. Владение полями описано в
   `machine/providers/README.md`.
5. Для нового продукта, страницы или общего визуального языка — `machine/style-profile.json`
   и `docs/decisions/unknowns.md`: карта переиспользования, контракт новой композиции
   и проверка состояний. Для одного подтверждённого компонента этот шаг не нужен.
6. `machine/catalog.json` — найти нужную сущность по id, группе или tags.
7. Только `file` выбранной записи.
8. Затем только названные в записи `rules`, `implementation`, `examples` и
   evidence. Подробную прозу читать по `source.spec`.

Не загружать весь каталог, все SVG или evidence без необходимости. Записи со
scope `design-source-only` не являются фактом о production. Если разметка
равна `null`, соблюдать `missingReason` и `fallback`, а не достраивать DOM.

## Сборка интерфейса

Для страниц из текущего production-среза сначала прочитай
`machine/page-analysis/atlas.json`, найди URL/page-id и открой только названный
`file` в `machine/page-analysis/pages/`. В нём находятся sequence, точная геометрия
на семи ширинах, параметры лент и approvalGaps. Адресные замеры 01.10.2026 имеют
приоритет над обобщениями старого корпуса только для исследованных адресов.
Reference HTML/CSS — инертное evidence, не UI Kit и не разрешение форкать layer.
До согласования gap не утверждай, что текущий public API воспроизводит эту область.
Для новой сборки сначала применяй `ownerDecisions` из atlas/page-контракта:
утверждённые отличия от production имеют приоритет над measurements. В частности,
CardGrid всегда gap12; измеренный gap16 школы остаётся только evidence.

Для нового сервиса сохранять общие шапку и футер Курсов. Размещение новой
навигации и выбор обычного H1 на белом фоне или hero согласовать с пользователем,
если они не заданы задачей или подтверждённым контрактом; не добавлять второй
ряд навигации или цветную внутреннюю шапку автоматически. Решение владельца
05.10.2026 и порядок предложения вариантов — `docs/decisions/unknowns.md`.

Уточнение владельца 06.10.2026: сохранять состав, действия и поведение общей
шапки, а не только её форму и логотип. Новую навигацию вписывать в существующую;
использование SiteHeader само по себе не разрешает заменить штатные пункты
содержимым slot. Удаление, замена или перенос существующих действий требуют
явного согласования, включая mobile; нехватку API решать отдельным запросом Kit.

Типографику выбирать по роли текста и контракту компонента, а не по наличию
маленького токена. Не уменьшать текст ради плотности или отсутствия overflow.
Историческая частота 12/14px не разрешает делать весь новый интерфейс мелким;
неописанное назначение small/micro предложить и согласовать. Проверять читаемость
на desktop/mobile; универсальный новый минимальный кегль пока не утверждён.

Фильтрацию списка не оформлять табами: использовать фильтрующие чипсы из
публичного API. Это правило действует на всех ширинах, а не только на mobile.
Отличать фильтр от навигации, переключения содержимого и выбора в форме.

Аналоги собранных страниц используют существующую композицию. Для нового
сценария предложить блоки, порядок и desktop/mobile-раскладку; существенно
разные варианты показать с рекомендацией и дождаться выбора до реализации.
Не удалять содержательные блоки на mobile без подтверждённого контракта или
отдельного согласования. После выбора собирать из публичных компонентов Kit.

Загрузка, пустой результат, ошибка и успех используют готовые компоненты
и состояния Kit. Если их размещение или поведение в новом сценарии не описано,
предложить вариант и согласовать его до реализации, не создавать новый стиль.

Поведение при перезагрузке и возвращении зависит от сценария. Если оно не задано
задачей или подтверждённым контрактом, предложить человеку варианты сохранения
и сброса, объяснить последствия, дать рекомендацию и дождаться выбора до
реализации. Не назначать автоматически ни сохранение всего, ни сброс всего.
Отдельно описать введённые данные, отправленный результат и незавершённую работу;
после выбора проверить именно согласованный сценарий. Решение 06.10.2026 —
`docs/decisions/unknowns.md`.

Если принято сохранять отправленный ответ, обычно отображать его настоящим
значением поля с readonly, не placeholder в пустом поле. Допустим и отдельный
текст «Ваш ответ: …» с результатом проверки: для такого отличия объяснить смысл,
предложить варианты и согласовать выбор. Это предпочтение отображения, а не
разрешение сохранять данные без принятого контракта. Уточнение 06.10.2026.

При ошибке отправки обычный сценарий: показать понятную ошибку, постараться
сохранить введённое в браузере и предложить устранить проблему и повторить
попытку без повторного заполнения. Интернет или сервер называть причиной только
если это известно; неизвестный исход не выдавать за подтверждённый отказ.
Различать отправку на сервер и локальное сохранение; не обещать сохранность,
если запись не удалась. Альтернативы по ситуации предложить вариантами и
согласовать. Предпочтение владельца 06.10.2026 — `docs/decisions/unknowns.md`.

Для устаревшего черновика обычный вариант — надёжно восстановить совместимые
поля и явно сообщить, что остальные нужно заполнить заново. Не угадывать смысл
изменённых полей. Если восстановление невозможно, предложить варианты с
последствиями и рекомендацией и дождаться выбора: например, начать заново,
сохранив старый черновик для просмотра, или сбросить его после подтверждения.
Не удалять исходный черновик молча. Предпочтение владельца 06.10.2026.

Если новое действие может уничтожить или заменить незавершённую работу,
не выбирать поведение молча. Когда оно не задано подтверждённым контрактом
или задачей, предложить варианты (продолжить, подтвердить замену, сохранить
обе работы), объяснить последствия и дождаться решения человека до реализации.
Это не требование универсальной модалки: способ взаимодействия согласуется
по сценарию. Решение владельца 06.10.2026 — `docs/decisions/unknowns.md`.

До сборки описать возможные статусы и их смысл. Если трактовка или учёт статуса
не заданы задачей либо подтверждённым контрактом, обязательно предложить человеку
варианты решения с последствиями и рекомендацией и дождаться выбора; одного
вопроса «подтверждаете?» недостаточно. Выбранные значения использовать одинаково
в карточках, уведомлениях, прогрессе и итогах, включая условия показа результата.
Не считать пропуск ошибкой или незавершённую работу завершённой без отдельного
согласованного смысла. Решение владельца 06.10.2026 — `docs/decisions/unknowns.md`.

Важные статусы не передавать только цветом. Обычно использовать понятные иконки
и подписи; для компактных или иных особых случаев предложить подходящие
альтернативы с последствиями и рекомендацией и согласовать выбор по сценарию.
Проверять доступность всей application-композиции, включая понятные текстовые
статусы для экранного диктора, а не только отдельных компонентов Kit.
Предпочтение владельца 06.10.2026 — `docs/decisions/unknowns.md`.

Проверка итоговых чисел зависит от задачи: в дизайн-прототипе вручную сверять
демонстрационные цифры и статусы; в рабочем сервисе дополнительно проверять
расчёты автотестами на разных сочетаниях ответов. Ожидаемые значения брать из
согласованной схемы, не придумывать при тестировании. Наличие строк или успешная
сборка не доказывают правильность расчётов. Решение владельца 06.10.2026.

Визуальная проверка одинаково подробная для дизайн-прототипа и рабочего сервиса.
Вести таблицу страниц, применимых состояний и ширин с фактическими результатами;
проверять desktop/mobile, ошибки и раскрытые меню, модалки и блоки. Прикладывать
показательные скриншоты с указанием маршрута, состояния и ширины; пропуски и
неприменимые случаи отмечать с причиной. Сборка и отсутствие overflow не заменяют
визуальную проверку и не разрешают заявлять «всё проверено». Решение 06.10.2026 —
`docs/decisions/unknowns.md`.

Проверку переходов и области действия соотносить с задачей. В дизайн-прототипе
допустимы упрощённые переходы и неполный перенос настроек, если механики страниц
схожи и это не мешает оценить целевой дизайн; обозначить ограничения, не выдавать
их за готовую функциональность. В рабочем сервисе потеря требуемого контекста
и несоответствие действия кнопке недопустимы. Если режим работы или контракт
перехода не определены, уточнить задачу; для неочевидного поведения предложить
варианты с последствиями и рекомендацией и дождаться выбора. Решение владельца
06.10.2026 — `docs/decisions/unknowns.md`.

При проверке навигации открыть меню и убедиться, что текущий раздел виден
и отмечен семантически (aria-current для ссылок, где применимо), включая
вложенные маршруты и mobile. Само наличие переходов не означает выполнения
этого требования. Одинаковые application-блоки переиспользовать, а не собирать
независимо на каждом экране. Если нужны отличия, объяснить их, предложить
варианты и дождаться выбора человека, если решение ещё не задано контрактом.
Недостающий API для active или варианта блока запрашивать у владельца Kit,
не форкать layer. Уточнение проверки принято владельцем 06.10.2026.

Самостоятельная замена общего футера запрещена. Даже если замена прямо
описана в задаче, отдельно показать пользователю предлагаемые изменения,
варианты и последствия и получить подтверждение до реализации. Использовать
публичный API SiteFooter для настройки адресов без изменения состава и вида;
нехватку API решать отдельной задачей канонического Kit. Решение 06.10.2026.

- Для страницы в покрытии выбрать адресный контракт из
  `machine/page-analysis/pages/` через `machine/page-analysis/atlas.json`;
  использовать порядок `sequence`, геометрию `frame` и связанные правила.
  Для нового сценария назвать ближайшую аналогию и отличия, не переносить
  чужую sequence или оболочку автоматически. Описать новую композицию по
  `docs/decisions/unknowns.md` и отделить её от подтверждённых паттернов.
- Если локально доступен текущий implementation provider, использовать его
  публичный компонент. Изолированный example остаётся источником поведения и
  fallback-разметки, но не поводом повторно верстать уже существующий компонент.
- Для guide-only сущности без provider mapping разметку брать из изолированного
  example; классы являются контрактом с `ui/courses.css` и не переименовываются.
- Простые элементы используют intrinsic preview, модули и страницы — viewport
  320 / 480 / 768 / 1024 / Auto.
- Комментарии и допущения хранятся в `previewNotes`, а не внутри iframe.
- Тексты и числа сверять с `machine/content.json`.

## Границы

Пакет включает атлас двенадцати текущих гостевых страниц и их живые компонентные
сборки. Шесть исторических recipes удалены из активного каталога; evidence и
архив v0.1 сохранены. Геометрия Swiper измерена с работающим
production JS; локальный reference-адаптер не подтверждает его анимацию.
Личный кабинет, тёмная тема, серверные ошибки и не снятые состояния не являются
подтверждёнными паттернами этого пакета. По явно поставленной задаче разрешено
проектировать новые сценарии вне layer, обозначив допущения и согласуемые решения
по `docs/decisions/unknowns.md`. Нельзя выдавать их за измеренный production или
добавлять в канон без отдельного решения владельца. Все пробелы, включая
неподдержанные provider-варианты, называть пользователю явно.

Версия v0.1 хранится в `archive/courses/v0.1` только для сверки и не является
обычной точкой входа.
