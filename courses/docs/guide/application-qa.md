# Проверка новых страниц и сценариев

Проверяйте каждую собранную страницу и каждую поверхность одного сценария,
а не только главную. Этот набор шагов дополняет адресные правила production-страниц;
он не назначает продукту способ сохранения, восстановления или подсчёта результатов.
Если ожидаемое поведение не согласовано, предложите варианты с последствиями и
рекомендацией и дождитесь выбора. До выбора отметьте проверку как не выполненную.

## Подготовка

Запишите ревизию приложения, версии гайда и Kit, режим работы (дизайн-прототип
или сервис), все маршруты и поверхности. Для каждой операции отдельно укажите,
что сохраняется: введённый текст, отправленный ответ, результат и незавершённая
работа. Источник ожидаемого результата — согласованный контракт, не код приложения.

Используйте 320, 480, 768, 1024 и 1440; добавьте ширины по обе стороны собственных
адаптивных границ. Проверки хранения выполняйте в отдельном браузерном контексте
с тестовыми данными, без очистки пользовательского браузера и без отправки реальных заявок.

## Адресные сценарии

| Проверка | Что сделать | Что проверить |
|---|---|---|
| repeat-actions | Повторить отправку, открыть и закрыть разбор, перейти к следующему действию | Статусы, результат и число операций соответствуют принятому контракту; закрытие панели не меняет историю случайно |
| reload-and-return | Ввести текст, отдельно отправить ответ, перезагрузить и вернуться; повторить на каждой поверхности | Текст, отправленный ответ и результат сохраняются или сбрасываются именно как согласовано; восстановление одной страницы не доказывает остальные |
| write-failure | До действия принудительно отклонить запись в браузер или тестовый запрос на сервер | Понятная ошибка; нет обещания сохранности; повторная попытка ведёт себя согласно контракту |
| invalid-json | Перед открытием записать в тестовое хранилище повреждённый JSON | Нет падения страницы и молчаливого удаления оригинала; дальнейшее действие предложено и согласовано |
| missing-fields | Отдельно проверить корректный JSON без обязательных полей | Формат проверен до использования; исходная копия не перезаписана без согласованного действия |
| unsupported-version | Отдельно открыть сохранение неизвестной версии | Нет угадывания смысла полей или молчаливого сброса; доступные варианты соответствуют контракту |
| no-false-success | При отказе операции проверить не только ошибку, но и уведомления, карточку, профиль, прогресс | Нигде нет ложного «сохранено/отправлено»; данные в памяти не выданы за долговременное хранение |
| guest-and-populated | Проверить применимые гостевые и заполненные состояния на всех ширинах | Шапка, содержательные блоки и действия не исчезают без согласования; поля и кнопки не перекрываются |
| empty-and-long-content | Использовать пустые поля, длинные имена, подписи и тексты на всех ширинах | Текст читаем; сокращение соответствует контракту; кнопки доступны; размер шрифта не уменьшен ради сокрытия ошибки |
| internal-overlaps | Раскрыть меню, модалки и блоки; дождаться перехода, CSS и шрифтов | Нет непредусмотренных наложений внутри блока; одного замера общего overflow недостаточно |
| visual-review | Осмотреть каждую страницу и применимые состояния на всех ширинах | Выполнен именно визуальный осмотр; снимок и автоматическая геометрия сами по себе не означают приёмку |
| public-api-reuse | Сопоставить карту переиспользования с исходниками и публичным API | Покрытые задачи используют Kit; согласованные wrappers находятся вне слоя; одинаковые application-блоки не продублированы |

Принудительный отказ записи можно воспроизвести через `page.addInitScript`,
подменив `Storage.prototype.setItem` исключением до открытия страницы.
Повреждённые данные внесите в отдельном подготовительном контексте на том же origin,
затем отключите подмену записи и откройте нужный маршрут. Не предполагайте, что
приложение использует только localStorage: для IndexedDB или серверного хранения
нужен соответствующий тестовый отказ. `page.route` позволяет вернуть тестовый
HTTP 500; обрыв соединения отдельно проверяет неизвестный исход операции.

Правильно: ошибка видна, «сохранено» отсутствует, введённый текст остаётся доступен
в пределах принятого контракта, исходный повреждённый черновик не затёрт.
Неправильно: проверить только появление ошибки, не проверив ложный успех,
или восстановление в тренировке выдать за проверку отдельного задания.

## Проверка переиспользования

Из папки `courses` выполните
`node tools/audit-application-reuse.mjs D:/work/guide-test/prototype/app`.
Команда только читает Vue-шаблоны, показывает найденные публичные компоненты и
места с нативными полями/кнопками, для которых есть кандидаты в Kit.
Нужны зависимости самого гайда (`npm ci` из папки `courses`);
устанавливать Nuxt Kit или зависимости проверяемого продукта для аудита не нужно.

Это список для ревью, а не автоматический запрет HTML. Для каждого замечания
проверьте назначение, props/slots/models/emits кандидата и согласованную карту
переиспользования. Обоснованное исключение или wrapper запишите с ограничениями;
не исправляйте прототип или read-only слой автоматически. Алиасы импортов,
динамические компоненты, JSX и внутренности wrappers требуют ручного просмотра.
Отсутствие замечаний не подтверждает полное соблюдение архитектуры.

## Отчёт и проверка покрытия

Шаблон для своих маршрутов выводит команда
`node tools/validate-application-qa.mjs --template / /bank /account` из папки
`courses`. Замените маршруты настоящими; шаблон содержит только невыполненные
проверки и пустые ревизию/тип результата, поэтому не проходит приёмку.

В JSON-отчёте укажите `schemaVersion: 1`, `revision`, `deliverable`, `routes`,
`widths` и `entries`. Каждая запись содержит `route`, `check` из таблицы, `width`,
`status`, `method`, `steps`, `expected`, `actual` и `evidence` — ссылки на тест,
лог или снимок. Для продуктового поведения добавьте `productContract` — ссылку
на согласованное решение. Для пропуска или неприменимости вместо результата
обязательно запишите `reason`.

Статусы: `verified`, `issue-found`, `not-verified-with-reason`,
`not-applicable-with-reason`. Методы: `browser-test` (ручной или автоматический
браузерный сценарий), `manual-visual`, `source-review`.
Адаптивные и визуальные проверки имеют отдельную строку для каждой ширины;
функциональные — минимум одну для каждого маршрута, дополнительные при отличиях.
Список маршрутов сверяется с реальным приложением, а не только с самим отчётом.

Из папки `courses` выполните
`node tools/validate-application-qa.mjs путь/к/отчёту.json`.
Пропущенная строка, потерянная ширина, отсутствие контракта или свидетельства
дают ошибку; найденная проблема и невыполненная проверка блокируют приёмку.
Неприменимость допустима с проверяемой причиной, но не как способ скрыть дефект.
Валидатор проверяет структуру и покрытие, не истинность свидетельств и не факт
исполнения теста. Правильные и запрещённые примеры проверяет
`node tools/test-application-qa.mjs`; это тест инструмента, не приёмка приложения.
