# Работа за границей знаний Хабр Курсов

Если подходящего компонента или паттерна нет, используй ближайший подтверждённый
пример как отправную точку и явно назови допущение. Отсутствие разметки означает
«не знаем», а не «компонента не существует».

Не добавляй сведения в канонический слой, пока у них нет evidence или явно
помеченного нормативного решения.

## Актуальная граница

Гайд v1.1 включает двенадцать гостевых страниц в адаптивном атласе и их живые
Vue/Nuxt-композиции. Все двенадцать приняты владельцем 05.10.2026; текущий
provider — Courses Nuxt Kit 1.4.0; статус публикации находится в
`machine/consumer-workflow.json`. Точные границы и решения:
[машинный индекс](../../machine/index.json), [правила страниц](../guide/production-pages.md)
и [приёмка](page-analysis-approval.md). Версии и покрытие проверять по этим
источникам, а не считать количество исторических recipes.

Личный кабинет, авторизация как целый сценарий, тренажёр, редактор, избранное,
сравнение, тёмная тема и не снятые состояния не подтверждены как страницы
production Курсов. Наличие в Kit поля, Loader или EmptyState не подтверждает
всю композицию загрузки, сетевой ошибки или авторизации. Записи с
`knowledge.scope: "design-source-only"` не являются production evidence.

По явной задаче пользователя новые сценарии можно проектировать вне layer.
Отсутствие готового рецепта не запрещает разработку, но не даёт права объявлять
новую композицию канонической. Существенные дизайнерские решения остаются
предложениями до согласования; не расширять задачу самостоятельно.

## Оболочка нового сервиса · решение владельца 05.10.2026

Это нормативное решение для новых сборок внутри Курсов, не новый production-срез.

- Общая шапка сайта Курсов сохраняется. Для обычной страницы использовать
  существующий вариант простых страниц; не заменять её самодельной шапкой сервиса.
  Уточнение владельца 06.10.2026: сохранять не только форму и логотип, но и
  существующий состав навигации, действия и поведение. Новую навигацию вписывать
  в то, что уже есть. Использование SiteHeader не подтверждает сохранение шапки,
  если содержимое slot убрало штатные пункты. Перед сборкой перечислить состав
  выбранного подтверждённого варианта и отдельно показать предлагаемые изменения
  на desktop/mobile. Удаление, замена или перенос пунктов требуют явного решения
  пользователя, а не трактуются как часть разрешения добавить аватарку.
- Дополнительную навигацию агент не выбирает автоматически по количеству
  сценариев. Если размещение не задано, предложить пользователю варианты с
  объяснением доступности разделов и desktop/mobile-поведения, затем дождаться
  выбора до реализации навигации. Возможные варианты — меню аватарки в общей
  шапке, видимая навигация в ней или отдельный уровень; это альтернативы для
  обсуждения, не разрешённый по умолчанию второй ряд.
- Для прототипа «Репетитор» владелец предпочёл аватарку пользователя в общей
  шапке с dropdown разделов. Это предпочтение конкретного проекта, не обязательный
  рецепт для всех новых сервисов. Состав меню и поведение гостя/mobile ещё не
  согласованы; возможность реализации через публичный API проверяется отдельно.
- На обычной внутренней странице H1 и содержимое размещаются на общем белом
  фоне. Не создавать автоматически отдельную светло-синюю или «компактную
  светлую шапку» вокруг заголовка. Hero тоже возможен по задаче и ситуации;
  если вариант не задан подтверждённым аналогом или требованиями, предложить
  обычный заголовок и hero пользователю и согласовать выбор.
- Главная может иметь синий градиентный hero. Когда он примыкает к общей шапке,
  градиент должен быть цельным, а не начинаться заново в каждом блоке.
- Футер остаётся общим. Если нужны ссылки или варианты, которых нет в публичном
  API, зафиксировать запрос на доработку канонического Kit отдельно; не создавать
  собственную замену и не менять копию layer.
  Уточнение владельца 06.10.2026: самостоятельная замена футера запрещена.
  Даже если она описана в задаче, отдельно показать предлагаемые изменения,
  варианты решения и последствия и получить подтверждение пользователя до
  реализации. Сам текст задачи не заменяет это согласование. Адреса существующих
  пунктов настраивать через публичный API SiteFooter, сохраняя состав и вид;
  изменение адресов само по себе не является заменой футера.

Эти правила не утверждают новый вид меню, аватарки или hero. Сначала согласуется
композиция, затем проверяется её реализуемость готовыми props/slots. Недостающий
API — отдельная задача владельцу Kit, а не повод менять выбранный дизайн молча.

## Навигация, вкладки и фильтры · уточнение владельца 05.10.2026

Перед выбором компонента определить смысл действия: переход между разделами,
переключение содержимого или фильтрация одного списка. Внешне похожий ряд кнопок
не делает эти случаи одинаковыми; нельзя сначала назвать всё вкладками, а затем
лишь пытаться уместить их на mobile.

Решение владельца: для фильтрации используются чипсы, а не табы. Это выбор
по назначению действия, не адаптивная замена при нехватке места. Не использовать
ButtonGroup как ряд табов для фильтрации списка только потому, что он помещается
на desktop. Выбор параметра в форме и переключение содержимого — другие случаи;
это правило не запрещает их подтверждённые переключатели.

На `/editor` прототипа «Репетитор» пункты «Все задания», «Черновики»,
«На проверке», «Опубликованы» фильтруют список по статусу. Принято на всех
ширинах: чипс открывает dropdown выбора статуса; отдельный desktop-ряд не нужен.
Это application-композиция фильтра, а не новый универсальный тип вкладок.
Сначала проверить публичные API FilterChip и доступного dropdown/select;
не считать сам Chip готовым интерактивным фильтром и не форкать слой.

Подпись чипса и поведение выбора/сброса сверять с публичным контрактом фильтра;
неподдержанные варианты требуют отдельного уточнения, не локального форка.
Dropdown с чипсом не переносить автоматически на переключатели содержимого
всех страниц. Для нового неописанного случая объяснить назначение,
предложить подходящие варианты и
получить решение пользователя, а не уменьшать подписи или прятать пункты молча.

## Карта переиспользования перед сборкой

Для повторяющихся элементов и областей записать короткую карту в документации
продуктового проекта. Читать выбранные API, а не весь корпус компонентов.

| Выбор | Когда применять | Что записать |
|---|---|---|
| Готовый компонент | Публичный API покрывает задачу | guide-id, export, props/slots и apiFile |
| Application-wrapper | Нужны данные, поведение или расположение вокруг компонента | Базовый компонент и добавленная ответственность |
| Новая композиция | Новый предметный объект или сценарий из нескольких элементов | Аналогия, отличия, использованные компоненты и статус согласования |
| Недостающий API | Нужный вариант готового элемента недоступен | Ограничение и запрос владельцу Kit; не локальный форк |

Например, Link, Toast, Button и поля сначала искать в provider mapping.
Новый текст действия или место уведомления сами по себе не требуют их
перевёрстки: расположение можно задать application-wrapper. Если нужного
визуального варианта нет в API, назвать gap вместо скрытой замены компонента.
Предметную карточку задания, напротив, допустимо собрать из готовых элементов.

Не переопределять внутренние `.crs-*` селекторы. Глобальные reset-правила для
`a`, `button`, заголовков и focus должны проверяться на влияние на Kit:
не отменять его disabled, hover, focus и типографику. Локальные правила
application-композиции ограничивать её собственными классами.

Использование токена не подтверждает выбранную геометрию: произвольный множитель
в `calc()` может ввести новый размер. Существующие роли и размеры брать из
контрактов; новые фиксированные размеры и роли явно отмечать как допущения,
не добавлять в канонические токены без решения владельца.

## Читаемость новой композиции · уточнение владельца 06.10.2026

Владелец отметил слишком мелкую типографику повторной сборки. Размер выбирать
по роли текста и подтверждённому контракту, не уменьшать ради плотности или
отсутствия overflow. Историческая частота small/micro не подтверждает их
назначение новому содержимому. Неописанную маленькую роль сначала согласовать;
типографику публичных компонентов не переопределять. Проверять читаемость
на desktop/mobile. Новый универсальный минимальный кегль не утверждён.
Подробности — [типографика](../guide/typography.md).

## Минимальный контракт новой композиции

Решение владельца 05.10.2026: для аналогов собранных страниц использовать
существующую композицию и её контракт. Для нового сценария сначала предложить
структуру — необходимые блоки, их порядок и расположение. Существенно разные
варианты показать пользователю с рекомендацией и дождаться выбора до реализации
новой композиции. После выбора собирать из Kit, не изобретая замены уже покрытым
элементам. Гайд не назначает жёсткий универсальный шаблон всем новым страницам.

Предложение должно описывать desktop и mobile. На узкой ширине содержательные
блоки и доступные действия сохраняются: допустимо менять расположение, переносы
и оформление, но не молча удалять блок ради компактности. Если предполагается
скрытие содержимого, отдельно показать его пользователю и получить согласование;
подтверждённые адресные исключения существующих страниц сохраняют силу.
Пример выявленной ошибки: блок «15 минут для себя» на `/training` прототипа
исчезает на mobile. Для этого нового сценария его нужно сохранять в адаптивной
композиции, а не считать исчезновение нормой. Это решение не требует исправлять
проверочный прототип: он остаётся источником выявленных проблем.

До реализации зафиксировать:

1. Цель, маршруты и основной пользовательский сценарий.
2. Ближайший подтверждённый пример и отличия от него; для новой страницы
   аналогия не означает подтверждение всей её структуры.
3. Оболочку, порядок областей, карту компонентов и повторно используемые
   application-композиции. Одинаковую механику на нескольких экранах не
   реализовывать независимо без явной причины.
4. Источник данных: реальные, демонстрационные или имитация действия.
   Фикстуры и обещания интерфейса не выдавать за работающий backend.
5. Состояния, поведение на узких ширинах и критерии проверки ниже.
6. Открытые решения и статус: подтверждено существующим контрактом,
   принято владельцем или предложено для согласования.

Для набора страниц добавить доступный список маршрутов и способов открыть
состояния. Существенные допущения сообщать пользователю и хранить в документации
проекта; в viewer использовать previewNotes. Не добавлять технические пояснения
в конечный UI, если этого не требует сама задача демонстрационного прототипа.

## Перезагрузка и возвращение · решение владельца 06.10.2026

Сохранение состояния зависит от задачи, а не является универсальным правилом.
Если поведение не задано требованиями или подтверждённым контрактом, агент
предлагает человеку понятные варианты с последствиями и рекомендацией, затем
ждёт выбора до реализации. Например: сохранить заполнение, сбросить его или
сбросить поля, но сохранить уже отправленный результат. Вопрос задавать про
поведение пользователя, а не про технический выбор localStorage или backend.

Отдельно определить, что происходит с введёнными, но не отправленными данными,
с отправленным результатом, незавершённой работой и фактами вроде просмотра
подсказки. Не молча выводить решение для этих частей из одного слова «сохранить».
Рекомендация агента не заменяет выбор человека и не становится общим правилом
для всех форм или сервисов.

Примеры владельца: в тренажёре нужно помнить, что ответ уже отправлен; форму
заявки на странице после перезагрузки нужно сбросить для нового заполнения.
Сброс формы не означает отмену уже отправленной заявки или разрешение повторно
отправить её автоматически. Эти примеры не утверждают сохранение просмотра
подсказки или конкретный способ хранения: непокрытые детали согласуются отдельно.

Записать выбранное поведение в контракте продуктового проекта и проверить
перезагрузку до и после отправки, а также возвращение в сценарий. Гайд задаёт
порядок согласования, не универсальную политику хранения данных.

### Отображение сохранённого ответа · уточнение владельца 06.10.2026

Если сохранение отправленного ответа уже принято, обычный вариант — показать
его настоящим значением исходного поля с readonly. Не подставлять сохранённый
ответ в placeholder пустого поля: подсказка не является введённым значением.
После восстановления проверять само значение и состояние поля, а не только
сохранившееся сообщение об успехе.

Допустим альтернативный вариант: отдельный текст «Ваш ответ: …» и результат
проверки вместо поля. Агент может предложить его, объяснив преимущество для
конкретного сценария и показав варианты; выбор согласовать с человеком, если
он не задан контрактом. Предпочтение readonly-поля не является запретом текстового
отображения и не утверждает сохранение данных во всех сценариях.

## Ошибка отправки · предпочтение владельца 06.10.2026

Самый частый сценарий: сообщить об ошибке отправки, постараться сохранить
введённые данные в браузере, подсказать пользователю, как разобраться с проблемой,
и предложить повторить попытку без повторного заполнения. Например, при известной
проблеме соединения предложить проверить интернет; при подтверждённой серверной
ошибке — повторить позже. Использовать готовые компоненты ошибок и действий Kit.

Не придумывать причину: если она неизвестна, сообщить, что отправку не удалось
подтвердить. Потеря ответа сервера сама по себе не подтверждает, что данные
не получены; для рабочего сервиса предусмотреть проверку исхода или защиту от
дублирования при повторной отправке. Не показывать успех, если результат не
подтверждён, и не повторять отправку молча.

Локальное сохранение и отправка на сервер — разные результаты. Не обещать
сохранение черновика после reload, если запись в браузер не удалась; объяснить
фактическое ограничение. Для локального прототипа без сетевой отправки не
приписывать отказ хранилища интернету или серверу. Состав и срок хранения
сверять с контрактом и чувствительностью данных, не вводить универсальное
сохранение любой формы навсегда.

Это предпочтение частого сценария, а не единственное допустимое решение.
Если задача требует другого поведения, агент предлагает варианты с последствиями
и рекомендацией и согласует выбор человека. Отдельно проверить ошибку отправки,
сохранность введённого, отказ локального сохранения и повторную попытку по
выбранному контракту. Политику восстановления устаревших данных это решение
не определяет.

## Устаревший черновик · предпочтение владельца 06.10.2026

Если форма изменилась и старый черновик нельзя восстановить целиком, обычный
вариант — восстановить совместимые поля, когда соответствие надёжно известно,
и явно сообщить, что остальные данные нужно заполнить заново. Не угадывать
значение полей по похожим названиям и не объявлять частичное восстановление полным.
Восстановленные значения снова проверяются по текущим правилам формы.

Если безопасное восстановление невозможно или сценарий требует другого подхода,
агент объясняет ограничение, предлагает реализуемые варианты с последствиями
и рекомендацией и ждёт выбора человека. Например: начать заново, сохранив старый
черновик для просмотра, или сбросить черновик после подтверждения пользователя.
Не удалять и не перезаписывать исходный черновик молча; не обещать просмотр старых
данных, если система его не поддерживает.

Это предпочтение, не универсальная схема миграции. Состав восстанавливаемых
полей и обработку непригодных данных определить в контракте проекта. Проверить
полное и частичное восстановление, невозможность восстановления, понятность
сообщения о недостающем и сохранность исходных данных до согласованного сброса.

## Замена незавершённой работы · решение владельца 06.10.2026


Если начало нового действия может уничтожить или заменить незавершённую работу,
агент заранее согласует поведение, если оно не задано задачей или подтверждённым
контрактом. Предложить подходящие варианты с последствиями и рекомендацией:
продолжить текущую работу, подтвердить её замену либо сохранить обе работы.
Не выбирать молчаливую перезапись как удобный способ реализации.

Выбор варианта остаётся за человеком; это не обязательная модалка для любого
нового действия. Способ взаимодействия, доступные варианты и момент подтверждения
зависят от сценария и реализуемости. Не обещать сохранение обеих работ, если
система его не поддерживает. После выбора записать контракт в продуктовом проекте
и проверить сохранность текущей работы, отмену нового действия и согласованный
путь замены/продолжения. Само принятие правила не выбирает поведение прототипа.

## Согласованность статусов · решение владельца 06.10.2026

Перед сборкой описать возможные статусы, их смысл, переходы и учёт в итогах.
Если трактовка или способ учёта не заданы задачей либо подтверждённым контрактом,
обязательно предложить человеку варианты решения с объяснением последствий
и рекомендацией, затем дождаться выбора. Не заменять варианты единственным
предложением с вопросом «подтверждаете?». Принятый контракт не открывать заново
без необходимости; для нового случая не назначать трактовку самостоятельно.

Например, для ответа с помощью можно предложить отдельную категорию в итогах
или включение в общее число верных с явным разделением самостоятельных ответов.
Это альтернативы для конкретной задачи, не утверждённая схема статистики.
Набор вариантов должен соответствовать сценарию и возможностям системы.

После выбора единый смысл статуса применять в карточке, уведомлении, прогрессе
и итоговом экране. Пропуск не превращается в ошибку при переходе между экранами;
незавершённая работа не называется завершённой. Если нужен особый способ учёта,
его явно согласовать и объяснить пользователю, не менять значение статуса молча.
Зафиксировать в продуктовом контракте условия доступности итогов, подписи
и правила расчёта; проверить каждый статус и переход на всех связанных экранах.
Новые цвета и компоненты статусов этим решением не утверждены: использовать
подходящие публичные состояния Kit, а непокрытый вариант согласовать отдельно.

## Переходы и область действия · решение владельца 06.10.2026

Требования зависят от результата задачи: дизайн-прототип или рабочий сервис.
Не оценивать каждое упрощение прототипа как ошибку готового продукта и не
переносить разрешённые упрощения в рабочий сервис.

- В дизайн-прототипе допустимы упрощённые переходы, неполный перенос выбранных
  параметров и демонстрационный объём действия, если механики страниц схожи
  и упрощение не мешает оценить целевой дизайн. Например, переход на аналогичный
  экран с демонстрационной выборкой не обязательно должен переносить все фильтры.
  Зафиксировать ограничения в документации и отчёте, не заявлять готовность
  рабочей механики. Если задача проверяет именно переходы или фильтрацию,
  упрощение этой механики уже мешает её цели и требует согласования.
- В рабочем сервисе требуемый выбранный контекст передаётся корректно, а действие
  соответствует подписи и обещанному объёму. Молчаливая замена ОГЭ на ЕГЭ или
  выполнение «всех ошибок» только для одного предмета недопустимы. Не считать
  намеренный переход в другой контекст ошибкой, если он предусмотрен контрактом
  и понятен пользователю. Это не требование сохранять все фильтры навсегда.

Если тип результата неясен, уточнить его до выбора требований к поведению.
Для рабочего сервиса определить контракт переходов и области действия; если
неочевидно, какие настройки переносить, предложить варианты с последствиями
и рекомендацией и дождаться выбора человека. Проверять выбранный контракт,
а не произвольную универсальную политику. Разрешение упрощать дизайн-прототип
не отменяет требований к общей шапке, типографике и сохранению mobile-контента.

## Доступность статусов композиции · предпочтение владельца 06.10.2026

Важный статус нельзя передавать только цветом. Предпочтительный вариант —
понятные иконки и подписи: пользователь может понять состояние без различения
цветов, а экранный диктор получает текстовое объяснение каждого важного статуса.
Не считать одну общую подпись полосы прогресса объяснением всех её шагов.

Выбор зависит от ситуации. Если нужны компактность или другое представление,
агент объясняет задачу, предлагает альтернативы с последствиями и рекомендацией
и согласует выбор, если он не задан контрактом. Возможные варианты — компактные
шаги с доступным пояснением при фокусе/нажатии или текстовый список статусов.
Это не новые утверждённые компоненты и не разрешение заменять готовый Kit.

Для выбранного варианта проверить всю композицию: смысл каждого статуса без
цвета, подписи для экранного диктора, клавиатуру и mobile. Пояснение, доступное
только по hover мыши, не является достаточной заменой для клавиатуры или touch.
Для статической иконки не создавать лишнюю кнопку ради подписи; интерактивные
объяснения должны иметь понятный способ открытия и закрытия. Недостающий API
или непокрытый визуальный вариант согласовать отдельно с владельцем Kit.

## Проверка итоговых чисел · решение владельца 06.10.2026

Для дизайн-прототипа вручную сверять демонстрационные цифры и статусы:
показанные итоги должны соответствовать выбранной схеме и данным примера.
Не требовать рабочего backend или расчётов там, где задача показывает статичный
дизайн. Для рабочего сервиса дополнительно проверять вычисления автотестами
на разных сочетаниях ответов и состояний.

Ожидаемые результаты брать из согласованного продуктового контракта, а не
выводить из той же реализации, которую проверяет тест. Например, проверить
наборы с самостоятельными верными и неверными ответами, пропусками и помощью,
если эти статусы есть в задаче. Числа, доли и проценты, правила округления и
условия показа итогов должны следовать выбранной схеме. Не требовать, чтобы
сумма любых показателей равнялась общему числу, если по контракту категории
пересекаются или показаны только отдельные категории.

Подсчёт строк результатов не заменяет проверку самих чисел. Если схема
не определена или неоднозначна, сначала предложить человеку варианты с
последствиями и рекомендацией и согласовать её по правилам статусов выше.
В отчёте отдельно указать ручную сверку примера и автоматическую проверку
расчётов, не выдавать одно за другое.

## Матрица состояний

Решение владельца 05.10.2026: загрузку, пустой результат, ошибку и успех
собирать из готовых компонентов и состояний Kit, не создавая собственный
визуальный стиль. Для подтверждённого случая применять существующий контракт.
Если размещение или поведение для нового сценария не описано, предложить
вариант пользователю и согласовать его до реализации. Проверять публичный API
выбранного компонента; недостающая возможность требует запроса владельцу Kit,
не копирования его разметки. Это правило процесса, а не утверждение нового
внешнего вида или всех backend-состояний как production evidence.

Выбирать применимые строки, а неприменимые помечать с причиной. Это checklist
поведения и проверки, не новый визуальный рецепт и не факт о production.

| Область | Что проверить |
|---|---|
| Данные | Заполнено, пусто, нет результатов фильтра; длинные тексты и числа |
| Асинхронное действие | Загрузка, успех, ошибка, повтор; защита от повторной отправки |
| Поле и форма | Начальное, заполненное, невалидное, disabled; отправка клавиатурой, понятная ошибка |
| Авторизация, если есть | Гость и вошедший пользователь; видимость входа/выхода и доступных действий |
| Навигация | Корректный active/aria-current, возврат, прямой URL, неизвестный маршрут или id |
| Перезагрузка и возвращение | Холодное начало; согласованный сброс/восстановление до и после отправки, отправленный результат и незавершённый сценарий |
| Раскрытие и overlay | Закрыто/открыто, длинное содержимое, клавиатура, закрытие и возврат фокуса |
| Адаптивность | Длинные вкладки, видимость важных данных и действий, локальный скролл и переносы |

Дополнительно сопоставить список содержательных блоков desktop и mobile:
ни один блок не должен исчезнуть без подтверждённого контракта или отдельного
согласования. Проверка общего scrollWidth не обнаруживает `display:none` потери.

Не выбирать минимальный размер подписи, новый вид вкладок или новую оболочку
на основании этого checklist: такие дизайнерские вопросы требуют отдельного
решения. Нельзя скрыть существенную информацию на mobile только ради отсутствия
горизонтального переполнения.

## Проверка и отчёт

Решение владельца 06.10.2026: для дизайн-прототипа и рабочего сервиса требуется
одинаково подробная визуальная проверка. Упрощённая функциональность прототипа
не разрешает сокращать проверку внешнего вида, читаемости и адаптивности.

Вести таблицу покрытия: маршрут/страница, применимое состояние, ширина экрана,
способ проверки и фактический результат. Проверять все собранные страницы,
desktop/mobile и применимые состояния, включая ошибки, раскрытые меню, модалки
и блоки; ширины и адаптивные границы — по процедуре ниже. Статусы проверки:
«проверено», «найдена проблема», «не проверено» и «неприменимо»; для последних
двух указать причину. Не выдавать пропуск за успешную проверку.

Прикладывать показательные скриншоты desktop/mobile и важных состояний,
подписанные маршрутом, состоянием и шириной, и связывать их со строками отчёта.
Одного мобильного снимка главной страницы недостаточно для отчёта о всём
сервисе. Полная таблица покрытия нужна в обоих режимах, но не требуется отдельный
скриншот каждого повторяющегося сочетания. Если состояние не реализовано в
согласованном объёме прототипа, отметить это явно, а не заявлять, что оно проверено.
Это не требование реализовать backend прототипа или изменить согласованный
порядок автоматической проверки расчётов.

Уточнение владельца 06.10.2026: проверить выполнение уже существующих правил,
а не только использование названных компонентов. Текущий раздел должен быть
виден в навигации: открыть меню, проверить визуальную отметку и семантическое
обозначение текущего пункта (aria-current для ссылок, где применимо), в том числе
на вложенных маршрутах и mobile. Переходы без ошибок не доказывают наличие active.

Одинаковые application-блоки на разных экранах переиспользовать. Сопоставить
карту переиспользования с реализацией и проверить согласованность поведения,
а не только общий Button внутри нескольких независимых копий блока. Если
нужны отличия, объяснить их и предложить варианты с рекомендацией, дождаться
выбора человека, если решение ещё не задано контрактом. Не назначать общий
блок там, где задачи действительно различны, и не менять публичный Kit ради
локального варианта: нехватку API оформить отдельным запросом владельцу.

Сборка, отсутствие JavaScript-ошибок и горизонтального переполнения — необходимые,
но недостаточные проверки. Для страниц в покрытии соблюдать адресную процедуру
из [production-pages.md](../guide/production-pages.md); для новой композиции
проверять применимые состояния на 320 / 480 / 768 / 1024 / 1440 и границы
собственных адаптивных правил. Полный проход основных сценариев дополнять
визуальной проверкой desktop и mobile.

Снимать dropdown, modal и раскрываемый блок именно в открытом устойчивом
состоянии после завершения перехода. Проверять не только наличие элемента,
но видимость содержимого, действий и фокуса. Для форм проверить Enter,
для навигации — правильное выделение, для сохраняемых данных — перезагрузку.
Записать версии, маршруты, ширины, состояния и результаты; явно перечислить
пропуски. Сохранённый снимок, чужой отчёт или чтение кода не выдавать за свежую
браузерную проверку. Автотесты не заменяют согласование новых композиций.

Проблемы приложения фиксировать отдельно от нехватки гайда. Новый нормативный
паттерн в гайд вносится после решения владельца, а не потому, что агент однажды
так собрал экран. Очередь таких решений — [roadmap](../../ROADMAP.md).
