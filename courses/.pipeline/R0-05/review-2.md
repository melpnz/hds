## Отдельно: `tools/known-missing-classes.json` — вынесено приёмке

**Согласен с решением не заводить файл.** Не «на усмотрение» — по трём
проверяемым основаниям.

1. Обоснование верно фактически. В образце базовая линия читается только для
   витрины: `career/tools/validate-classes.mjs:37` — `const known = own ? {} :
   JSON.parse(…)`. Для своей разметки (`validate-classes.mjs файл.html`) она
   не читается ни в образце, ни у Курсов, и в Курсах это не правка шага —
   строка унаследована от R0-01, `git diff` её не трогает. Значит файл, будь он
   заведён, `copy-check.html` бы не помог: ровно тот сценарий, в котором
   инвариант METHOD §6.1 и проверяется.
2. Единственный потребитель базовой линии — прогон по витрине, а витрины нет
   до R0-06. Сегодня файл был бы пустым объектом с преамбулой: заведённая
   форма без содержания, которую следующий шаг всё равно наполняет заново.
   Отсутствие файла при этом не ослабляет прогон, а ужесточает его: при
   отсутствующем файле `known = {}`, и каждый неопределённый класс — ошибка,
   а не предупреждение.
3. Названный настоящий ответ — правильный. Продукт собран утилитами; заменить
   их потомками `crs-` значит переписать продукт и развести «Анатомию»
   с «Разметкой». Тогда §6.1 может держаться только со стороны CSS, то есть
   `ui/utilities.css`. Точка изменения одна (`conventions.markupUtilities`),
   объём ограничен разметкой спецификаций, а рабочий список выдаёт сам
   `validate-classes.mjs`.

Это решение инварианта, а не отложенная проблема — с одной оговоркой, которую
стоит записать при приёмке: до R0-06 проверка копируемости остаётся ручной
(шаблон велит прогнать `validate-classes.mjs` по `copy-check.html`, но ни один
гейт этого не делает), и §6.1 начнёт проверяться автоматически только тогда,
когда витрина соберёт разметку спецификаций под безаргументный прогон.
Порядок «`ui/utilities.css` на R0-04 → спецификации с R2» обязан соблюдаться,
иначе первые спецификации выйдут с красной проверкой копируемости, и остановить
их будет нечем.
