## 1. Воспроизведение фикса самостоятельно (не на слово автора)

Собран HTML с двумя `<style>`-блоками своей формулировкой (не текстом автора:
`.doc-panel-one`/`.panel-two-no-prefix`, а не `doc-first-block`/
`second-block-leak-no-prefix`), протечка во втором блоке. Использованы также
две другие независимые фикстуры — точная копия структуры пробы `R-k` для
негативного теста и фикстура с тремя блоками (первый ломает разбор, третий
пустой) для проверки устойчивости индексации при ошибке.

**Позитив, текущий (исправленный) код:**

```
$ node tools/validate-classes.mjs   # pkgA: .doc-panel-one (чист), .panel-two-no-prefix (протечка) во втором <style>
Оболочка витрины и продуктовый слой смешались (1) — METHOD §6.2:
  showcase/components.html <style>#2: селектор без класса витрины doc- — .panel-two-no-prefix
EXIT=1
```

**Негатив — намеренно вернул старый нестабильный ключ** (`` `${file} <style>` ``
без `styleIndex`) в обоих местах вызова (`collectSelectorClasses` и
`selectorLeaks`) на изолированной копии файла (не в рабочем дереве), прогнал
на фикстуре, дословно повторяющей структуру пробы `R-k`:

```
$ node <изолированная копия со старым ключом>   # pkgB: .doc-first-block (чист), .second-block-leak-no-prefix (протечка)
Checked 2 classes in 1 file(s) against 2 stylesheets. All defined.
EXIT=0   # ← регрессия ловится: протечка второго блока пропала молча

$ node tools/validate-classes.mjs   # та же фикстура pkgB, текущий код
showcase/components.html <style>#2: селектор без класса витрины doc- — .second-block-leak-no-prefix
EXIT=1
```

Совпадает дословно с тем, что заявляет `fix-4.md` (тот же код возврата, та же
формулировка `Checked 2 classes… All defined.` на сломанном ключе). Тест
чувствителен именно к этому классу дефекта, не проходит «случайно»: на старом
ключе — ложный `EXIT=0`, на новом — верный `EXIT=1` с точным указанием
протёкшего класса.

Побочное наблюдение (не находка): когда протёкший класс второго блока **также
упомянут в разметке** (не только в CSS), старый нестабильный ключ давал
`EXIT=1`, но по **другой** причине — «Классы без определения в CSS» вместо
«Оболочка витрины и продуктовый слой смешались» (класс так и не попадал
в `defined`, поэтому считался неопределённым, а не протёкшим). И это, и
проверка с классом только в CSS (как в самой пробе `R-k`) — оба пути
подтверждают один и тот же факт: без фикса второй блок не разбирался вовсе.

## 3. Собственный красный набор — 4 сценария на кеш/идентификацию источника

Именно тот класс дефекта, что уже проявлялся дважды в этом шаге (разбор
селекторов → идентификация CSS-блока в кеше). Все прогнаны реальным CLI
в изолированных временных каталогах.

| Сценарий | Ожидание | Результат |
|---|---|---|
| Одинаковый по тексту `<style>`-блок в `showcase/components.html` и `showcase/pages.html` (оба существуют, оба протекают одним и тем же именем класса) — не схлопнется ли кеш между файлами? | обе протечки найдены раздельно | `showcase/components.html <style>#1: …identical-leak-text` **и** `showcase/pages.html <style>#1: …identical-leak-text` — обе строки в выводе, `EXIT=1`. Ключ кеша включает `file`, поэтому по конструкции не может схлопнуться между файлами независимо от содержимого |
| Один и тот же HTML-файл передан дважды в `own`-режиме (симуляция «найден и прямым путём, и по glob») | без падения, без задвоенной или потерянной проверки | `node tools/validate-classes.mjs custom/feature.html custom/feature.html` → `Checked 1 classes in 2 file(s)… All defined.`, `EXIT=0`, без ошибок. (Проверка §6.2 для `own`-файлов вообще не выполняется по конструкции — она жёстко привязана к списку `showcaseFiles`, а не к `htmlFiles`, так что дублирование аргумента не может провоцировать пропуск протечки; сейчас `showcaseFiles` — статический список из двух имён, не glob, так что сценарий «один файл найден дважды» для витрины структурно недостижим до появления `showcase/pages.html` с настоящим glob-поиском) |
| Пустой `<style></style>` и `<style>` только с комментарием | не должно падать, не должно давать ложных находок | Оба варианта в одной фикстуре → `Checked 1 classes… All defined.`, `EXIT=0`, без исключений |
| Три `<style>`-блока: первый не разбирается (`Unclosed string`), второй протекает, третий пустой | ошибка первого блока не должна маскировать проверку второго; индексация блоков должна остаться верной, несмотря на ошибку в предыдущем | `showcase/components.html <style>#1: CSS не разобран настоящим парсером — … Unclosed string` **и** `showcase/components.html <style>#2: …after-broken-leak`, оба в одном выводе, `EXIT=1` |

Ни один из четырёх сценариев не вскрыл нового обхода. Кеш-ключ, включающий
имя файла и порядковый номер блока, по конструкции устойчив к межфайловому
схлопыванию и к ошибкам разбора отдельных блоков.

## 4. Проверка заявления «методичный поиск не нашёл других мест»

Самостоятельно, не по тексту `fix-4.md`:

```
$ grep -n "new Map\|new Set" tools/validate-classes.mjs
145: parseCache            ← единственный кеш/мемоизация в файле
208, 221, 265: Set         ← плоские множества имён, не кешируются по составному ключу
271: used                  ← Map «класс → файл первого вхождения», не кеш разбора

$ grep -n "cache|Cache|memo|Memo" tools/*.mjs
только tools/validate-classes.mjs (parseCache) и tools/serve.mjs (HTTP-заголовок
"Cache-Control", не структура данных)
```

`validate-components.mjs` использует много `Map`/`Set` (`roadmapSteps`,
`seenSteps`, `seenSelectors`, `aliases`, `pageUrls`, `dependencies`,
`cycleState`, `keyOwners`, `stepOf` и другие) — проверено через `.set(` по
всему файлу: все ключи естественно уникальны на свою сущность (id шага, id
страницы, alias, селектор, id компонента), ни один не строится составным
ярлыком вида `` `${file} <тип>` ``, который предполагал бы «один блок на
файл» для источника, которых по факту может быть несколько. `measure-
selectors.mjs`, `capture.mjs`, `serve.mjs` используют `Set` только для
дедупликации (список уникальных страниц, ширин, типов файлов) — не как
кеш результата по ключу; `validate-counts.mjs` не использует ни `Map`, ни
`Set` вовсе. Заявление подтверждается: `parseCache` — единственная структура
такого рода во всём `tools/`.

## Что проверено и претензий нет

- Фикс кеша (`` `${file} <style>#${styleIndex}` `` вместо `` `${file} <style>` ``)
  воспроизведён самостоятельно, своей формулировкой, и позитивно (текущий код
  ловит протечку второго блока), и негативно (старый ключ на изолированной
  копии даёт ложный `EXIT=0` — тест реально чувствителен к этому классу
  дефекта, не проходит случайно).
- Индексация блока идентична в обоих местах вызова (`collectSelectorClasses`
  — `tools/validate-classes.mjs:277-284`, `selectorLeaks` — `:315-324`):
  оба цикла проходят одну и ту же строку `matchAll` над одним и тем же `html`
  в одном и том же порядке.
- Проба `R-k` в `validate-classes.selftest.mjs:123-139` — через `run()` /
  `spawnSync`, настоящий CLI, тот же путь, что и у остальных 26 проб; не
  вызывает внутренние функции напрямую.
- Полный набор — 27 из 27, прогнан лично, вывод совпадает дословно с
  `fix-4.md`.
- Собственный красный набор из 4 сценариев на кеш/идентификацию источника
  (межфайловое схлопывание при одинаковом содержимом, дублирование файла
  в `own`-режиме, пустой/комментарийный `<style>`, ошибка разбора одного
  блока не мешает проверке соседнего) — новых обходов не нашёл.
- Заявление «методичный поиск не нашёл других мест» — проверено

  components.mjs` (много `Map`/`Set`, все ключи естественно уникальны,
  ни один не строится составным ярлыком «один блок на файл»), `measure-
  selectors.mjs`, `capture.mjs`, `serve.mjs` (только дедупликация,
  не кеш по ключу), `validate-counts.mjs` (ни `Map`, ни `Set`).
- Регрессия X-80 (`ui/layout.css:193`, `Unknown word education-center`) —

## Ответ на вопрос об архитектуре инструмента

Пользователь просил сказать прямо, если новый обход снова окажется того же
класса (идентификация источника в кеше/состоянии), — сигнал был бы о том, что
дело не в парсере, а в архитектуре инструмента. В этой итерации такого
сигнала нет: собственный красный набор из четырёх сценариев, целившихся
именно в это (межфайловое смешение, дублирование файла, пустые блоки,
ошибка соседнего блока), не нашёл ни одного нового обхода. Один
проявившийся дефект (review-4, находка 1) был закрыт корректно, с верной
и позитивной, и негативной проверкой, и не тянет за собой видимого нового
экземпляра того же класса. Единственная оставшаяся структурная зависимость —
статический список `showcaseFiles` вместо glob (см. «Что проверить не
смог» выше) — сейчас не является дефектом, а станет проверяемым вопросом
только на R6, когда появится `showcase/pages.html` через glob-поиск; заводить
её находкой сейчас было бы расширением объёма шага без предмета для проверки.
