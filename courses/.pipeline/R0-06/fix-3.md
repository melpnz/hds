# Правки после review-3 — смена механизма `tools/validate-classes.mjs` (R0-06)

Четвёртый файл `fix-*.md` по счёту, но **по существу — первая итерация
нового технического подхода**, не четвёртая правка одной и той же находки.
Три предыдущие итерации (`review-1` → `fix-1` → `review-2` → `fix-2` →
`review-3`) чинили ручной регэксп-разбор CSS точечно; после review-3 шаг
ушёл в статус `blocked` (`.pipeline/R0-06/accept.md`, долг **X-79**,
`ROADMAP.md`) — METHOD §3 запрещает четвёртую итерацию правок над тем же
механизмом. Пользователь авторизовал не точечную правку, а **замену
механизма**: регэксп-разбор CSS заменён настоящим CSS-парсером
(`postcss` + `postcss-selector-parser`). Это меняет код `tools/
validate-classes.mjs` шире, чем одна находка, — согласовано явно в задаче,
не расширение объёма шага по своей инициативе.

Семантика METHOD §6.1/§6.2 не менялась ни на йоту: тот же критерий («каждый
класс в каждом отдельном селекторе оболочки витрины несёт `doc-`», «ни
одного класса/переменной `doc-`/`--doc-` в `ui/`»), тот же список
сохранённых сообщений и кодов возврата. Изменился только механизм разбора.

## Обнаруженная проблема вне границ шага — не находка review-3, а новая

При переходе на настоящий парсер `ui/layout.css` перестал разбираться:

```
CSS не разобран настоящим парсером — D:\work\guides\courses\ui\layout.css:193:23: Unknown word education-center
```

Причина — комментарий-пояснение к правилу «сетка секций» (строки ~166–206)
содержит подстроку `phone:gap-*/tablet:gap-*`; `*/` внутри неё — валидный,
но не задуманный автором конец CSS-комментария (в CSS комментарии не
бывают вложенными — первый `*/` всегда закрывает их). Всё, что дальше и до
настоящего закрывающего `*/` в конце блока (строка 206), — не текст
комментария, а невалидные CSS-токены верхнего уровня; `postcss` бросает
на них исключение вместо того, чтобы молча пропустить. Старый регэксп-разбор
этого не видел три итерации подряд, потому что не проверял синтаксис CSS
вообще — только извлекал `.classname`-подстроки из текста, и «сломанный»
хвост комментария для него ничем не отличался от настоящего.

Это **не находка о протечке `doc-*`/`--doc-*`** — сам файл продуктовый,
без единого класса оболочки. Это независимый, ранее невидимый дефект
уже принятого на R0-04 файла, который новый механизм не может обойти
молча: гейт **обязан** отказаться подтверждать «в `ui/layout.css` нет
протечки», если он не может этот файл разобрать. Файл в границах этого шага
не редактируется (явный запрет в задаче — `ui/layout.css` принят на R0-04).
Это записано долгом **X-80** в `ROADMAP.md` со ссылкой на этот отчёт, статус
`planned`. Воспроизведено регрессионной пробой `PARSE-ERROR` в
`tools/validate-classes.selftest.mjs` на точной копии проблемного фрагмента
(строки 166–206 реального `ui/layout.css`, встроены в пробу текстом).

Как следствие: `node tools/validate-classes.mjs` на рабочем дереве сейчас
даёт **код возврата 1** — не из-за какой-либо протечки METHOD §6.2, а
из-за отказа разобрать `ui/layout.css`. Это честный результат, а не
регрессия правки: до перехода на настоящий парсер эта проблема была
структурно невидима инструменту (он не проверял, разбирается ли файл как
CSS вообще), и её обнаружение — часть цели этой задачи, а не побочный
ущерб. Исправление одной строки в `ui/layout.css` тривиально по объёму, но
вне границ этого шага и не выполнялось.
