ни в `tools/validate-classes.selftest.mjs`, ни в `ROADMAP.md`, ни где-либо ещё.

Находки: **blocker 1 · major 0 · minor 0 · note 1**.

### 3. Selftest автора — не тавтологичен

Прочитан целиком (418 строк). `run()` (строка 84) вызывает `spawnSync('node', [scriptPath], { cwd: root })`
— настоящий CLI, не внутренние функции. Каждая `fixture()` строит независимый временный
каталог со своими `ui/`/`showcase/`. Разобраны построчно пробы ESC-1, ESC-2, NEW-1, NEW-4,
PARSE-ERROR:

- **ESC-1** (`.doc-badge.\6c eaked-hidden`) — `\6c` = hex `6c` = `l`, декодируется в
  `leaked-hidden`; ожидание `expectContains` требует ровно раскрытое имя
  `doc-badge, leaked-hidden` — арифметика hex верна, ожидание соответствует
  реальному поведению браузера, не тому, что код «случайно делает».
- **ESC-2** (`.\64 oc-injected-hack` в `ui/`) — `\64` = hex `64` = `d`; ожидание
  `класс оболочки витрины в продуктовом слое — .doc-injected-hack` — верно.
- **NEW-1** (скобка внутри значения атрибутного селектора) — проверяет ровно тот
  класс ошибки, который стал бы фатальным для ручного счётчика `{`/`}`; ожидание
  требует, чтобы оба правила (с `{` в атрибуте и следующее за ним) были
  распознаны раздельно — соответствует тому, что обязан делать настоящий парсер.
- **NEW-4** (комментарий `/* } не настоящая скобка { */` внутри правила) —
  `expectNotContains` явно проверяет, что `.doc-comment` НЕ попадает в находки
  (значит комментарий не спутал границы правила) — точная, не тавтологичная
  проверка отрицательного случая.
- **PARSE-ERROR** — использует точную копию сломанного фрагмента `ui/layout.css`,
  ожидает `CSS не разобран настоящим парсером` и имя файла — соответствует
  зафиксированному ниже (п. 5) реальному поведению.

Прогнан лично: `node tools/validate-classes.selftest.mjs` → 26/26, вывод совпадает
дословно с `fix-3.md`.

### 5. Находка X-80 (`ui/layout.css`) — подтверждена напрямую, не через гейт

```
$ node -e "postcss.parse(fs.readFileSync('ui/layout.css','utf8'), {from:'ui/layout.css'})"
ERROR: D:\work\guides\courses\ui\layout.css:193:23: Unknown word education-center
```

Локализовал причину независимо: `awk 'NR==166,NR==206' ui/layout.css | grep -n '\*/'`
даёт ровно два вхождения `*/` в этом блоке комментария — первое на относительной
строке 15 (абсолютная 180, подстрока `phone:gap-*/tablet:gap-*`), второе — настоящее
закрытие блока на строке 206. Комментарии CSS не вложены, значит первое `*/`
закрывает комментарий, открытый на строке 166, преждевременно; весь текст между
строкой 180 и «намеренным» `*/` на строке 206 становится невалидными CSS-токенами
верхнего уровня, отсюда `Unknown word education-center` на строке 193. Ошибка
реальная и не спровоцирована искусственно — воспроизведена вызовом `postcss.parse()`
напрямую на файле из рабочего дерева, без участия кода гейта.

`git log -1 -- ui/layout.css` → `56e01cc … courses: R0-04 ui/layout.css и
ui/utilities.css — принят`; `git diff --stat HEAD -- ui/layout.css` — пусто.
Файл этим шагом не редактировался, границы задачи соблюдены.

### 6. Докстринг vs METHOD §6.1/§6.2 и код — сверено построчно, включая эмпирическую проверку утверждений

`tools/validate-classes.mjs:1-63`. Семантика инварианта (каждый класс `showcase/*.css`
несёт `doc-`, исключение `:root`; ни одного `doc-*`/`--doc-*` в `ui/`) — не изменилась
против версии до `fix-3` (`git show HEAD:courses/tools/validate-classes.mjs`, diff
построчно): коды возврата (0/1/2), тексты всех пользовательских сообщений,
`known-missing-classes.json` (не существует в пакете — путь `{}` не читается,
поведение то же), разбор `class="…"` в HTML (двойные/одинарные кавычки/без кавычек)
— идентичны байт в байт, кроме нового блока `parseErrors` (новая категория отказа,
не подмена старой).

Отдельно проверено эмпирически (не на слово), что докстринг не обещает больше,
чем делает код (то, за что review-3 находка 2 упрекала прежний докстринг):

```
postcss.parse('@font-face{...} @page{...} @page :first{...} @property --foo{...}')
  .walkRules(...) → ничего не найдено (0 узлов Rule)
  .walkAtRules(...) → font-face/page/page:first/property — все decl-only узлы
```

```
postcss.parse('@page { margin:1in; @top-left { content:"x"; } }')
  → @top-left — узел atrule (не rule), вложен в @page
```

Оба утверждения докстринга («`@font-face`/`@page`/`@property` вообще не порождают
узлов Rule», «`@top-left` — не отдельная преамбула, попадающая в `AT_RULE_...`»)
подтверждены — ровно то, что было неточно в докстринге review-3, теперь верно
и проверено, а не просто переписано убедительнее.

### 7. Собственный красный набор — 5+1 проб, не текст автора

Файл `myredset.mjs` (скретчпад), реальный CLI через `spawnSync`, изолированные
временные каталоги:

- **Переменная со строковым значением, похожим на правило** (`--hint: ".leaked-lookalike { color: red }"` в значении `content`) — не порождает ни фиктивного правила, ни ложной протечки: `EXIT=0`, «All defined». Парсер корректно не путает содержимое строки с CSS-структурой.
- **Дублирующиеся `@layer base`** (два отдельных блока `@layer base { … }` с одинаковым именем) — оба тела разбираются, протечка во втором блоке ловится: `EXIT=1`, «…leaked-in-second-layer». `walkRules()` не завязан на уникальность имени at-rule, как и обещает докстринг.
- **`\0` (экранированный null) внутри имени класса** (`.doc-a\0 b`) — декодируется в `doc-a\uFFFD b`-класс, начинающийся с `doc-`; корректно не считается протечкой. Не падение, поведение согласовано со спецификацией CSS (замена на U+FFFD).
- **Составной селектор из 150 и из 2000 классов** — оба случая обработаны без задержки (`time`: 0.118 с на 2000-классовый селектор), находки корректны, падения/зависания нет.
- **Класс внутри `:not()` на в остальном `doc-*`-селекторе** (`.doc-item:not(.is-hidden)`) — засчитан протечкой (`is-hidden` без `doc-`). Соответствует докстрингу (классы считаются «в аргументе функционального псевдокласса вроде `:not()`»), это `note`, не находка — см. ниже.
- **Кеш парсинга при нескольких `<style>` в одном HTML-файле витрины** — см. находку 1, blocker.

Ни одна из первых пяти проб не вскрыла нового обхода — новый механизм по построению
закрывает эти углы. Шестая вскрыла реальный дефект.

## Находки

| # | Severity | Пункт | Находка | Где | Как проверить |
|---|---|---|---|---|---|
| 1 | **blocker** | B.8 | **Кеш разбора CSS у `parseCss` использует нестабильный ключ для инлайновых `<style>`: второй и последующие блоки `<style>` в одном HTML-файле витрины не проверяются вовсе, протечка в них даёт `EXIT=0`.** Оба места, что передают инлайн-стиль в `parseCss` (через `collectSelectorClasses`/`selectorLeaks`), используют один и тот же статический ярлык `` `${file} <style>` `` независимо от того, какой по счёту это блок `<style>` в файле (`tools/validate-classes.mjs:266` и `:301`). `parseCss` (`:136-147`) кеширует результат по этому ярлыку (`key = from ?? css`, `:137`) — при первом вызове с этим ключом парсит и кладёт в `parseCache`, при каждом следующем вызове с тем же ключом **возвращает закешированный результат первого блока, даже если реальное содержимое (`css`) другое**. Комментарий над кешем (`:129-133`) объясняет замысел («один и тот же CSS-блок разбирается несколькими проверками подряд, кеш разбирает каждый блок один раз») — но предпосылка «один блок — один ярлык» не выполняется для двух разных `<style>` в одном файле, и код это не проверяет. Результат: **METHOD §6.2 (оболочка витрины не протекла) перестаёт проверяться для всех `<style>`-блоков файла, кроме первого**, — тот же класс отказа, что был находкой review-1 (R-a, инлайн-`<style>` вообще не проверялся), только теперь применительно ко второму и следующим блокам, а не ко всем. Сейчас `showcase/components.html` не содержит ни одного `<style>` (`grep -c "<style" showcase/components.html` → 0), поэтому в текущем рабочем дереве дефект не проявляется, — но он реален, воспроизводим и не покрыт ни одной из 26 регрессионных проб автора (в `validate-classes.selftest.mjs` шаблон `html()` вставляет не больше одного `<style>` на фикстуру, `fixture({ inlineStyle })` не поддерживает второй блок) | `tools/validate-classes.mjs:136-147` (`parseCss`, кеш по `from`), `:266` (`collectSelectorClasses(style[1], `${file} <style>`)`), `:301` (`selectorLeaks(style[1], `${file} <style>`)`) | Изолированный пакет: `showcase/components.html` с двумя тегами `<style>` — первый `<style>.doc-first-block{color:red}</style>`, второй `<style>.second-block-leak-no-prefix{color:blue}</style>` (второй класс без `doc-`, обычный текст, не хак). `showcase/components.css`: `.doc-frame{display:block}`. `node tools/validate-classes.mjs` из каталога пакета → `Checked 1 classes… All defined.`, `EXIT=0` — вместо ожидаемого `EXIT=1` с находкой про `.second-block-leak-no-prefix` |

## Ответ на прямой вопрос — X-80 отдельно от X-79

Да, X-80 (дефект в чужом, ранее принятом `ui/layout.css`) обоснованно разводится
отдельной строкой долга и **не должен** держать сам факт «механизм заменён
и работает» в подвешенном состоянии: это независимый дефект другого файла,
