# Roadmap — Хабр Курсы v1.0

Сводная активная очередь находится в разделе [Courses общего

## Интеграция Courses Nuxt Kit · запланировано 23.09.2026

Рабочий Nuxt UI kit находится в `courses/courses-nuxt-kit/`. Первичный аудит
выполнен без изменений его файлов: это Nuxt 4 layer с 74 Vue-компонентами,
72 публичными записями реестра, общей таблицей токенов, ассетами, каталогом,
архитектурными проверками и 24 visual-regression эталонами для шести ключевых
компонентов на ширинах 320 / 480 / 768 / 1024.

### Точка продолжения · следующая сессия

Работу продолжать в таком порядке:

1. **Выполнено 25.09.2026.** Разобраны 34 несопоставленных provider token:
   размеры дополнены в `machine/dimension-tokens.json`, а цвета, эффекты,
   motion, opacity, font-family, z-index и ширина контента вынесены в отдельный
   нейтральный `machine/semantic-tokens.json`. Все 146 provider token теперь

   устаревших preview старых id заменены минимальными redirect на канонические
   примеры. Foundations, поведенческие схемы и evidence не удалялись. Результат:

3. **Выполнено 25.09.2026.** Шесть page-pattern получили явный

   являются второй канонической реализацией компонентов. Сводка:
   `machine/reports/page-pattern-composition.md`.
4. **Выполнено 25.09.2026 по решению владельца.** `RubricationBar` больше не
   считается компонентом: это область `rubrication-navigation` pattern

   machine/doc/example URL сохранены как migration note и redirect. В provider
   mapping осталось 72 direct и 0 guide-only записей.
5. Собрать неизменяемый `courses-nuxt-kit-v1.0.0.zip` и SHA-256, затем после
   подтверждения владельца опубликовать их в GitHub Releases и проверить
   скачивание/копирование в чистый Nuxt-проект.

   обоих `package.json` связаны одной автоматической проверкой. Имя ZIP и release
   tag выводятся из версии provider; проверка обновления не скачивает и не меняет
   файлы без явного запуска.
7. Расширить CI: component/API/token drift, compatibility, minimal consumer,
   render-smoke и приоритетные visual regression сценарии.
8. Провести финальный аудит инструкций для коллег и ИИ: скачивание, подключение,
   проверка версии, использование готового компонента, создание собственного
   wrapper снаружи read-only layer и запрос изменения владельцу kit.

Пункты 1–4 и 6 выполнены; 7–8 можно выполнять автономно. Участие владельца требуется
для неоднозначных токенов и публикации GitHub Release.

Целевая модель ответственности:

- **machine-гайд** — долговечный, не привязанный к конкретному фреймворку
  источник истины для назначения, поведения, состояний, доступности, допустимых
  сочетаний, page-pattern и известных ограничений;
- **активный implementation provider** — источник текущей разметки, публичного
  API компонентов, значений токенов, ассетов и итогового визуала;
- **Courses Nuxt Kit** — текущий временный provider, пока команда frontend не
  выпустила официальную библиотеку; его имя, Vue API и структура файлов не
  должны становиться обязательной частью ядра machine-схемы;
- **production и Figma** — доказательная база для изменения кита и гайда, но не
  параллельная реализация внутри витрины;
- витрина гайда не воспроизводит компоненты собственной HTML/CSS-копией, а
  показывает сборку из локальной копии активного provider соответствующей версии.

Это односторонний контракт, а не слепая двусторонняя синхронизация: изменение
визуала сначала попадает в кит, после чего его manifest и примеры обновляют
техническую часть гайда; изменение поведенческого правила сначала фиксируется в
гайде, после чего CI требует поддержать его в активном provider.

### P0 · Зафиксировать владельца и неизменяемую границу

**Выполнено 23.09.2026.** Владелец закреплён через `CODEOWNERS` и
`OWNERSHIP.md`; в каноническом kit и копируемом layer действуют отдельные
`AGENTS.md`. Коллегам и ИИ запрещено менять vendored layer, но явно разрешено
создавать собственные компоненты, wrappers и композиции снаружи. Локальные
изменения layer выявляются по контрольным суммам.

1. Канонический Courses Nuxt Kit изменяет и выпускает только его владелец.
   GitHub handle владельца фиксируется в `CODEOWNERS`; правила и контакт для
   change request — в отдельном ownership/contribution документе.
2. Скопированный `layers/courses` считается vendored/read-only кодом. Коллеги и
   ИИ могут использовать компоненты, props, slots и документированные точки
   расширения, но не редактируют файлы layer и не переопределяют внутреннюю
   разметку или стили.
3. Коллеги свободно создают собственные компоненты вне `layers/courses`, в том
   числе составные компоненты на базе примитивов кита. Такие компоненты принадлежат
   приложению, не выдаются за часть Courses Kit и не занимают имена его публичных
   exports.
4. Проектные особенности реализуются снаружи: композицией, wrapper-компонентом
   или отдельным приложенческим слоем. Если требуется изменить существующий
   kit-компонент или расширить его публичный API, оформляется запрос владельцу;
   изменение сначала вносится в канонический kit и выходит новой версией.
5. Manifest с checksums помечает локально изменённую копию как modified. Такая
   копия не считается поддерживаемой версией и не обновляется автоматически:
   сначала локальные правки выносятся наружу либо оформляются в каноническом kit.
6. Инструкции для ИИ явно запрещают менять vendored layer в продуктовых проектах,
   но разрешают создавать application-компоненты рядом с ним. Разрешение на
   изменение самого кита есть только при работе владельца непосредственно с
   каноническим `courses/courses-nuxt-kit/`.

### P0 · Отделить гайд от конкретной реализации

**Частично выполнено 23.09.2026.** `machine/index.json` объявляет активный
provider, а generated mapping отдельно связывает стабильные guide-id с версией,
Vue export, source, preview, состояниями и публичным API Nuxt Kit. `props`,
`slots`, `emits` и именованные `v-model` извлекаются непосредственно из `.vue`,
а не поддерживаются вторым ручным списком. В manifest кита автоматически
попадают 72 публичных и 2 внутренних компонента. Из рабочего `courses.css`
также генерируется provider token manifest: 146 переменных с типом, значением и
ссылками на другие токены. Инвентарный, API- и token drift блокируют валидацию.
Осталось нормализовать provider tokens в нейтральные семантические id и
подключить provider adapter к витрине.

1. Добавить в machine index понятие `activeImplementationProvider`, но хранить
   provider-specific сведения в отдельном mapping, например
   `machine/providers/courses-nuxt-kit.json`, а не в базовых component records.
2. Зафиксировать нейтральный provider contract: стабильный guide id, версия,
   public/internal/deprecated, component/export name, props/slots/events,
   поддержанные states, token mapping, preview и source reference.
3. Все инструкции формулировать через «локальный активный provider», а Courses
   Nuxt Kit указывать как текущее значение. Не встраивать Vue-имена и пути кита в
   правила поведения и page-pattern.
4. **Выполнен adapter 23.09.2026:** витрина читает provider mapping, загружает
   только адресный API открытого компонента и для всех 72 прямых соответствий
   позволяет переключиться с документирующего HTML-примера на реальный Vue-
   preview Nuxt Kit. Интегрированный локальный запуск поднимает обе витрины;
   статический пример остаётся fallback для GitHub. Аудит 25.09.2026 закрепил
   69 `provider-primary`, три `hybrid` и восемь redirects старых id. Позже тот же
   adapter сможет читать manifest официальной библиотеки или Storybook без смены
   id и структуры поведенческих записей.
5. Значения токенов пока импортируются из Nuxt Kit, но нормализуются в
   нейтральный semantic token contract. Следующая библиотека сможет предоставить
   новое сопоставление, не меняя потребителей гайда вручную.

### P0 · Сделать кит скачиваемым и версионируемым

**Частично выполнено 23.09.2026.** Ассеты перенесены внутрь `layers/courses`,
поэтому одна копируемая папка самодостаточна. Добавлены manifest версии `1.0.0`,
SHA-256 для 148 файлов, локальная команда проверки обновления, changelog и
тесты чистой/изменённой копии. Команда запускается только явно, ничего не
скачивает и не изменяет. Manifest привязан к точному commit SHA содержимого
версии. Команда `create:release` собирает ZIP только из tracked-файлов layer и
отдельный SHA-256, а minimal-consumer копирует layer в чистый временный Nuxt-
проект и успешно собирает его полностью офлайн. Осталось опубликовать архив
`v1.0.0` в GitHub Releases и автоматизировать выпуск по release tag.

1. Сохранить copy-based модель: коллега скачивает release-архив и копирует
   `layers/courses` в свой проект. После копирования приложение собирается и
   работает полностью локально, без runtime/build/dev-запросов к GitHub.
2. Не публиковать обязательный npm-пакет и не связывать проект с live Git
   dependency. Каноническая версия остаётся в этом репозитории, а неизменяемые
   архивы публикуются в GitHub Releases.
3. В каждую копию включать `courses-kit.manifest.json` с semver, датой выпуска,
   commit SHA, совместимой версией гайда, URL канонического репозитория и
   контрольными суммами файлов публичного layer.
4. Добавить локальную команду `check:update`, которая только по явному запуску
   читает latest release manifest с GitHub и сравнивает его с локальным. Никаких
   фоновых проверок, телеметрии или сетевых запросов при установке, разработке и
   сборке.
5. Результат проверки должен сообщать `актуально / доступно обновление / локальная
   версия новее / проверить не удалось`, показывать версии и ссылку на changelog.
   Проверка ничего не скачивает и не изменяет.
6. Перед обновлением сверять checksums. Если локальный layer не менялся, его можно
   заменить новым архивом; если есть локальные изменения — сначала сформировать
   diff, вынести проектные изменения за границу layer и не перезаписывать файлы
   автоматически.
7. Добавить проверяемый minimal-consumer: чистый Nuxt-проект с локальной копией
   layer запускается и отображает несколько компонентов без файлов demo и без
   доступа к сети.
8. В release-архив не включать `.nuxt`, `.output`, `node_modules`, test-results
   и другие генерируемые каталоги.

### P0 · Свести токены и визуальную реализацию

**В работе с 23.09.2026.** Nuxt Kit экспортирует
`courses-kit.tokens.json` непосредственно из `:root` рабочего CSS: на текущем
срезе это 146 токенов без неизвестных типов. Manifest и provider mapping
содержат адрес этого файла, а проверка кита ловит рассинхронизацию. Сгенерировано
сопоставление завершено 25.09.2026: все 146 токенов связаны с нейтральными
токенами гайда, конфликтов значений нет. Дополнительные размеры вошли в общую
шкалу, а цвета, тени/focus, motion, opacity, font-family, z-index и ширина
контента — в отдельный `machine/semantic-tokens.json`.

1. Устранить два независимых пространства токенов: кит сейчас использует
   `--crs-*`, гайд — `--courses-*`, `--color-*` и часть `--fig-*`.
2. Обязать provider экспортировать структурированный token manifest. Пока он
   генерируется из Nuxt Kit; гайд нормализует его в нейтральный semantic contract
   и на его основе строит machine-артефакты. На переходный период оставить
   aliases и отчёт об устаревших именах.
3. Сопоставить цвета, размеры, типографику, радиусы, тени, motion и breakpoints;
   расхождения не усреднять, а оформлять как решение со ссылкой на production или
   Figma.
4. **Выполнено 25.09.2026:** реальные component-preview доступны
   переключателем для 72 прямых mappings; 69 помечены `provider-primary`, три —
   `hybrid` из-за отсутствующих состояний. Самостоятельные HTML/CSS-примеры
   сохранены как GitHub fallback, а восемь устаревших дублей старых id заменены
   минимальными redirect. Foundations и доказательные кейсы не удалялись.

1. Когда появится библиотека команды frontend, не переносить в неё правила из

2. Сформировать coverage report: реализовано полностью, отличается API,

3. Проверить обязательные состояния, accessibility, токены и page compositions;

4. Добавить новый provider mapping параллельно старому, переключить витрину на
   тестовый provider и прогнать одинаковые machine- и visual-контракты.
5. Только после проверки сменить `activeImplementationProvider`. Nuxt Kit
   оставить архивным provider минимум на один переходный релиз с migration map;
   стабильные id и поведенческие записи гайда при этом не переименовывать.

### P1 · Автоматическая синхронизация и выпуск

1. Общий CI запускает проверки гайда и активного provider (сейчас Nuxt Kit),
   schema/manifest diff, token diff, проверку public API, typecheck/build,
   component smoke tests и visual tests.
2. Для всех публичных компонентов обеспечить хотя бы render-smoke на четырёх
   контрольных ширинах; visual regression расширять сначала на layout,
   overlays, формы и составные карточки, а не обновлять снимки автоматически.
3. Любое изменение публичного API, токена или эталонного визуала требует
   changelog и semver; breaking change — migration note. Изменение только
   поведения/документации может повышать версию гайда без выпуска кита.
4. Команда синхронизации генерирует machine mapping и token artifacts и падает
   на незакоммиченном diff. Ручными остаются purpose, behavior, accessibility,
   page patterns, evidence и решения по неизвестным состояниям.
5. После прохождения CI публиковать release-архив локального layer и статический
   каталог из одного tag; записывать версии и commit SHA в оба manifest.

### Критерии завершения интеграции

- коллега копирует зафиксированную версию кита в чистый Nuxt-проект по одной
  инструкции; проект работает без сетевой связи с GitHub;
- коллеги и ИИ не меняют vendored layer; изменения provider выпускает только
  зафиксированный владелец из канонического репозитория;
- проверка обновлений выполняется только по запросу, не меняет файлы и отличает
  чистую копию от локально модифицированной;
- ИИ по маршруту Courses сначала находит компонент локального активного
  provider, а затем применяет поведенческий и page-pattern контракт гайда;
- публичные компоненты, состояния и токены не расходятся молча: CI либо
  синхронизирует generated-часть, либо останавливает изменение;
- в гайде нет второй визуальной реализации существующего kit-компонента;
- версии provider и гайда связаны compatibility matrix и воспроизводимыми preview;
- смена Nuxt Kit на другой provider не требует переписывать базовые machine-id,
  поведенческие правила и page-pattern.
