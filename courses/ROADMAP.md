## Чеклист приёмки шага

Прогоняется приёмкой каждого шага. Выдача вставляется в `accept.md`
копированием из терминала вместе с кодом возврата — не пересказом (X-41).

```bash
node tools/validate-components.mjs --strict   # реестр: код 0
node tools/validate-counts.mjs                # заявленные числа: код 0
node tools/validate-classes.mjs               # классы витрины: код 0 (postcss-механизм, R0-06)
node --check tools/*.mjs                      # инструменты разбираются
npm test                                      # когда скрипт вернётся, X-01
```

**Обязательная пара для любого шага, трогавшего селекторы, `occurrences`
или `seenOn`** — сначала перемер **без флага**, затем сверка:

```bash
node tools/measure-selectors.mjs
node tools/validate-components.mjs --strict
```

Порядок здесь и есть проверка. `validate-components` в одиночку сверяет реестр
с переписью, а не с разметкой: согласованная правка числа в `manifest.json`
и в `selector-census.json` проходит у него зелёным. Первая команда перезаписывает
перепись настоящим измерением в браузере, вторая ловит расхождение кодом 1.
Проверено приёмкой R0-05 прогоном `.pipeline/R0-05/red-3-pair.mjs` на копии
пакета: подделка `badge.occurrences` 87 → 8700 с переписанной в ту же сторону
переписью даёт `validate-components --strict` в одиночку **код 0**, а пара —
**код 1** с адресом `badge: occurrences 8700 ≠ measured 87`. Флаг `--check`
для этого не годится: он ничего не пишет, и подделанная перепись остаётся
на месте, сходясь сама с собой.

## Решения пользователя, 2026-09-08

Пять открытых вопросов инвентаризации закрыты. Решения обязательны для всех
последующих шагов.

1. **Пакет описывает текущий прод**; Figma даёт состав, варианты и целевой
   контракт. При конфликте — METHOD §3, но см. п. 2.
2. **Канонические брейкпоинты — Figma: 320 / 744 / 1024.** Прод реализован
   на 480 / 768 / 1024; расхождение фиксируется как факт в `evidence/coverage.md`
   и в responsive-разделе каждой спецификации, а не замалчивается. Правила
   пакета формулируются в терминах канонической схемы.
3. **Доступность фиксируется как есть.** Нормативный слой не дописывается;
   отсутствие `role`, `form`, `label`, `select` в снятой разметке идёт
   в «Ограничения» спецификаций и в `coverage.md`. `ui/state-contract.css`
   остаётся только для визуальных состояний, не снятых с прода.
4. **`BaseFilterModalNew` — актуальная реализация.** `BaseFilterModal` уходит
   в `legacyAliases` со статусом `legacy-only`.
5. **Гидрируемые узлы снимаются интерактивно** — поиск в шапке, поля hero-формы,
   панель сервисов, открытый `Select`, открытая модалка фильтров. GAP остаётся
   только там, где узел не удалось открыть.

> **Результат шага принят 8 сентября 2026.** Ниже 1024 в сборке продукта
> **две** границы раскладки, а не одна, и они разной природы.
>

> с хватом (`.base-modal__wrapper { align-items: end; grid-template-rows: 1fr;
> margin: 0 }`, `.base-modal__footer`, `.base-modal__sausage { display: flex }`),
> а выпадающий список фильтра подменяется на модальное раскрытие: `base-modal`
> до 479, `v-popper--theme-dropdown` от 480, условным рендерингом,
> **6/10 снятых страниц** — все, где в разметке есть управление фильтром.
>
> **767/768 — конец мобильного диапазона.** `(max-width: 767px)` активен
> на 480, 744 и 767 и гаснет только на 768. Здесь подменяются оболочка
> и сетки, но одним числом это покрытие не описывается: `footer` 476 → 256

>

> четвёртый диапазон сборки, которого нет ни в [`BRIEF.md`](BRIEF.md),

> и `phablet-and-tablet`.
>
> Отсюда каноническая **744 сидит в мобильном диапазоне**: оболочка и сетки
> мобильные, а список фильтра — уже планшетный дропдаун. [`BRIEF.md`](BRIEF.md)
> §5.6 «480 / 768 / 1024» и §9 «на 744 прод отдаёт мобильную раскладку»

> брейкпоинтов и оговоркой, что 480 делит мобильный диапазон надвое, —
> строки X-24 и X-35.
>
> Вывод стоит на трёх независимых артефактах: активные запросы по 13 ширинам
> холодной загрузкой ([`media-queries-cold.json`](evidence/source/production/media-queries-cold.json)),
