# HDS — гайды Хабра

Гайды для создания интерфейсов сервисов и лендингов. Здесь собраны правила визуального языка, примеры, компоненты и границы применимости. Это частично готовые пакеты знаний, а не единая завершённая дизайн-система.

**Начни с этого файла.** Его можно дать коллеге или ИИ вместе с описанием задачи:

> Прочитай README в репозитории https://github.com/melpnz/hds, выбери подходящий маршрут и используй его при разработке. Моя задача: …

**Нужны логотипы сервисов? Бери готовые SVG из [assets/logos](assets/logos/README.md).** Для каждого сервиса есть русское и английское текстовое название, детальный знак и пиксельный знак для маленьких размеров. Используй нужный файл при создании фичи или лендинга — не перерисовывай логотип и не заменяй его обычным текстом.

## Что собираемся создать

Если ты ИИ, сначала установи **контекст размещения**, затем продукт или тип лендинга. Это два разных выбора. Если контекст ещё не указан, спроси: **«Это страница внутри интерфейса сервиса или страница/форма для лендинга?»** Дождись ответа и только после него предложи соответствующий выбор:

| Интерфейс сервиса | Лендинг |
|---|---|
| Хабр (гайд v1.0) | О компании (гайд v0.1, в разработке) |
| Карьера (гайд v1.2) | Продуктовый (гайд v0.1, в разработке) |
| Курсы (в разработке) | Брендинговый, акционный (гайд v0.1, в разработке) |
| Q&A (в планах) | Партнёрский спецпроект (отдельный пакет в разработке, релиз не объявлен) |

В вариантах выбора показывай версии доступных гайдов и пометки «в разработке» / «в планах». Версии берутся из [VERSIONING.md](VERSIONING.md) и обновляются в этом меню при релизе пакета. Это версии гайдов, а не сервисов; изменения в `Unreleased` не означают новую выпущенную версию.

**«В разработке»** — папка с материалами гайда уже опубликована на GitHub, но материалы ещё очень сырые. ИИ может сильно ошибаться и додумывать отсутствующие правила, поэтому результат требует особенно внимательной проверки. До работы прямо предупреди пользователя об этом. Затем используй только реально опубликованные материалы под задачу; пробелы обозначай явно, а не заполняй выдуманными правилами. Если нужных материалов нет, сообщи об этом и не выдавай реализацию за соответствующую гайду. Этот статус сам по себе не требует завершать инструкцию.

**«В планах»** — материалов самого гайда пока нет. Исследование не считается готовым гайдом, но **его разрешено использовать для приблизительной реализации**. Если исследование опубликовано, перед работой предупреди: «Готового гайда пока нет, использую исследование. Будьте внимательны: результат будет очень приблизительным, ИИ может ошибаться и додумывать детали. Его нужно сверить с продакшеном». Затем прочитай исследование и продолжай задачу; дополнительного подтверждения только из-за этого статуса не требуется. Если нет ни гайда, ни исследования, сообщи об отсутствии материалов и заверши инструкцию по направлению. Не переходи автоматически к стилю другого продукта.

Статус определяется опубликованными материалами, а не наличием локальной папки: `courses/` и пакет `landings/` уже есть, отдельного пакета Q&A нет. Для партнёрских спецпроектов начата отдельная инвентаризация в `partner-specials/`; готовой библиотеки там пока нет. Наличие пакета не означает одинаковое покрытие всех типов лендингов. Хабр и Карьера доступны в пределах описанного покрытия, а не как полностью завершённые пакеты.

Если пользователь уже явно назвал контекст и направление, не спрашивай повторно. Название продукта само по себе не определяет контекст: у Хабра, Карьеры, Курсов и Q&A могут быть промостраницы. «Страница Хабра» неоднозначна — уточни интерфейс или промо.

**Не выводи контекст из функции страницы.** «Авторизация», «регистрация», «форма», «оплата», «заявка», «простая HTML-страница» описывают функциональность или формат, а не выбор между интерфейсом и лендингом. Форма авторизации может находиться на лендинге. Пока контекст неизвестен, не задавай сужающий вопрос «Для какого сервиса?» и не выбирай интерфейсный гайд. Ответ с названием продукта на преждевременно заданный вопрос тоже не подтверждает контекст — сначала уточни его.

Пример: на запрос «Создай простую HTML-страницу с формой авторизации» первый вопрос — «Это страница авторизации внутри интерфейса сервиса или форма для лендинга?» После «для лендинга» уточни тип лендинга из правой колонки, продукт/бренд и цель, если они ещё не известны. После «внутри сервиса» уточни сервис из левой колонки. До определения маршрута не начинай реализацию и не выбирай стиль. Если пользователь не уверен, помоги определить контекст по месту размещения и назначению, не подставляя вариант по умолчанию.

Затем проверь готовность выбранного маршрута и открой его файлы ниже; одной ссылки на них пользователю недостаточно. Ограничение готовности интерфейсного гайда Q&A относится к интерфейсу Q&A, а не автоматически к любому лендингу с этим брендом.

## Маршруты для интерфейсов

**Проверка готовности до начала реализации.** Выбор направления не означает, что гайд готов. Для Q&A готового гайда пока нет. При выборе Q&A ответь:

> Гайд по Q&A пока в планах, поэтому использую исследование. Будьте внимательны: результат будет очень приблизительным, ИИ может ошибаться и додумывать детали. Перед использованием его нужно сверить с продакшеном.

После предупреждения открой исследование Q&A и продолжай реализацию. Прочитай ограничения и «Типы правил», затем разделы под задачу. Сохраняй наблюдаемые особенности продукта, а решения для непокрытых сценариев обозначай как допущения. Например, форма авторизации не подтверждена исследованием публичных страниц: её структура и поведение будут проектным решением. В итоговом ответе напиши «приблизительная реализация по исследованию Q&A», а не «применён готовый гайд Q&A». Предупреждение относится к сообщению пользователю и описанию результата; не добавляй его в сам интерфейс без запроса.

| Задача | С чего начать | Что читать дальше |
|---|---|---|
| **Хабр** | [Гайд и границы покрытия](habr/README.md) | [Правила композиции](habr/RULES.md): разделы под задачу → [реестр компонентов](habr/components/INDEX.md) → нужные спецификации. Для подключения CSS — [контракт рендера](habr/evidence/runtime-contract.md) |
| **Карьера** | ИИ: [контракт для модели](career/AGENTS.md). Человек: [быстрый старт](career/docs/development/quick-start.md) | ИИ следует контракту: [машинный индекс](career/machine/index.json) → нужные данные. Человеку: [карта пакета](career/README.md), [компоненты](career/components/INDEX.md), [подключение](career/docs/development/installation.md) |
| **Курсы** | [Состояние пакета](courses/README.md) → актуальные принятые шаги в [роадмапе](courses/ROADMAP.md) | Доступные основы: [токены](courses/docs/guide/tokens.md), [типографика](courses/docs/guide/typography.md). Для недостающего контекста — соответствующие разделы [исследования](04-habr-courses.md), с учётом статусов правил |
| **Q&A** | **Гайд в планах — предупредить о приблизительности** | [Исследование](02-habr-qna.md): ограничения, «Типы правил», затем разделы под задачу. Приблизительная реализация разрешена |

Не переноси стиль одного сервиса на другой. Курсы и Карьера — разные визуальные системы, несмотря на общий домен. Для Q&A не заменяй исследованный язык более современным стилем другого продукта.

Исследования ниже можно использовать для приблизительной реализации непокрытых частей с тем же предупреждением и обозначением допущений; они не становятся от этого подтверждёнными правилами или готовыми компонентами:

Эти документы описывают исследованные страницы, а не универсальные шаблоны. Акционный проект без близкого примера требует собственного решения; не объявляй его готовым паттерном. В партнёрском проекте учитывай бренд партнёра, в продуктовом — какой продукт продвигается. B2B-страницы рекламных продуктов company.habr.com относятся к первому маршруту; при такой неоднозначности уточни контекст.

**Новый пакет [landings/](landings/README.md) активно разрабатывается.** Для применения новых блоков или нового брендового стиля проверь [роадмап](landings/ROADMAP.md) и прочитай только относящиеся к задаче принятые материалы. Наличие CSS-файла или папки не означает готовность. Не считай весь пакет готовым и не считай его автоматически заменившим все четыре документа выше. В покрытой области учитывай новые принятые решения и явно отличай их от старых наблюдений; при неразрешённом конфликте обозначь его, а не смешивай правила молча.

## Как применять гайд и не читать лишнее

**Логотипы:** для всех направлений используй [общий набор SVG](assets/logos/README.md). Там русские и английские текстовые версии, детальные и пиксельные знаки семи сервисов. Бери готовый файл нужного сервиса; не перерисовывай логотип и не заменяй его текстом. Читай только выбранный вариант, а не всю библиотеку. Наличие логотипа не меняет статус готовности гайда.

1. Выбери один маршрут и проверь его готовность. Если маршрут требует остановиться, сообщи об этом и не переходи к реализации. Для доступного гайда кратко назови его и существенные пробелы для задачи.
2. Прочитай входную инструкцию, границы и только нужные разделы. В длинном файле сначала просмотри заголовки, затем извлеки выбранные разделы. Не загружай все продукты, исследования и изображения сразу.
3. Применяй правила с учётом их статуса. Наблюдение о существующей странице не превращается в обязательное требование. Не выдавай своё решение за подтверждённый паттерн.
4. Для внешнего вида используй доступные токены, CSS и спецификации выбранного пакета. Учитывай стек проекта; пример HTML/CSS сам по себе не является готовой библиотекой React/Vue-компонентов. Для Карьеры соблюдай отдельный контракт разметки.
5. Открывай витрину или отдельный скриншот, когда нужно понять композицию, неоднозначную деталь или проверить сходство. Скриншоты не обязательны для первоначального выбора маршрута и не загружаются пакетом.
6. Перед завершением проверь результат по относящимся к задаче правилам и доступным проверкам пакета. Назови допущения там, где гайд не покрывает сценарий.

Если файлы недоступны, попроси доступ или локальную копию; не утверждай, что прочитал их. Ссылка сама по себе не гарантирует, что ИИ может открыть приватный репозиторий. При чтении через GitHub переходи к содержимому файлов; при наличии клона используй локальные пути. Не обходи ограничения вложенных инструкций.

## Примеры и устройство репозитория

Состав публикации: [что отправляем в GitHub и что оставляем локально](PUBLICATION.md).

- Карьера: [компоненты](career/showcase/components.html), [страницы](career/showcase/pages.html).
- Хабр: [компоненты](habr/showcase/components.html), [страницы](habr/showcase/pages.html).

Это HTML-файлы: в интерфейсе репозитория GitHub они показываются как код. Для живого просмотра используй локальный сервер по инструкции пакета; опубликованного сайта эта навигация не предполагает.

Папки продуктов содержат рабочие гайды. Корневые документы 00–08 — исследовательский корпус; для направлений с отдельным пакетом начинай с пакета. Для проверки конкретных правил доступны evidence внутри продуктов.

Авторские папки `.audits/`, `.claude/`, `_sources/`, `design/` и журналы шагов `.pipeline/R*/` не публикуются. Упоминания и ссылки на них в исследовательских материалах и роадмапах относятся к внутренним материалам автора. Реестры `.pipeline/inventory.json` сохранены для работы проверок. Для создания фичи не нужно искать внутренние папки или запускать конвейер сборки гайдов: создавай макет в проекте своей задачи. Если необходимое правило не изложено в опубликованных материалах, обозначь пробел, а не предполагай содержимое внутреннего источника.
