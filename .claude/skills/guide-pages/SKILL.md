# Ключевые страницы и блоки

Вход текущего запуска: `$ARGUMENTS`.

Прочитай [`core-contract.md`](../../guide/core-contract.md),
[`evidence.md`](../../guide/evidence.md),
[`guide-structure.md`](../../guide/guide-structure.md) и
[`writing-style.md`](../../guide/writing-style.md).

Компоненты по отдельности не отвечают на главный вопрос потребителя гайда —
**как из них собирается экран**. Этот шаг закрывает его примерами.

## Что считается ключевым

**Интерфейс продукта** — по одной странице на семейство, а не самые красивые
страницы. Минимальный набор:

| Семейство | Что показывает |
|---|---|
| Листинг | сетка, фильтры, ритм списка, пагинация |
| Страница сущности | шапка сущности, место основного действия, секции |
| Профиль | идентичность, действие при личности, состав |
| Дашборд / сводка | плотные данные, крупные числа, разрезы |
| Форма / поток | поля, валидация, шаги, сохранение |
| Пустое состояние | что видно, когда данных нет |
| Ошибка | 404 и отказ операции |

Нет семейства в продукте — так и пишется в `coverage.md`; выдумывать его нельзя.

**Лендинг** — по одному примеру на тип блока: hero, секция преимуществ, stats,
карточки, форма заявки, CTA, футер, врезка соцдоказательства. Плюс **рецепты**:
из каких блоков и в каком порядке собираются целые страницы.

## Порядок

### 1. Отбор

Из `.pipeline/inventory.json` возьми страницы. Проверь, что все модули, из
которых страница состоит, уже приняты: страница собирается **только из закрытых
компонентов**. Не хватает модуля — строка в `ROADMAP.md`, страница ждёт.

### 2. Возьми уже снятые страницы

Опора — снимки экрана с инвентаризации,
`evidence/source/production/pages/<id>/`. По ним раскладываешь каркас и
сверяешь собранный пример. **Не ходи на прод заново.** Нет файлов — дыра
инвентаризации, досними в ту же папку `--full-page --name <PageId>`, не
как «съёмку шага 6».

Состояния, которые меняют композицию (фильтры, пустой список, ошибка формы),
снимай только если их ещё нет рядом с основным снимком.

Блок лендинга, которого нет в корпусе страниц, — кроп узла без `--full-page`.

### 3. Разбор

Разложи **уже лежащий** снимок экрана на области и модули: что где стоит,
в каком порядке, какой ширины, с каким шагом. Числа — из `computed.json`
страницы, не с глазомера. Отметь, чем это семейство отличается от соседнего.

### 4. Воспроизведение

Собери страницу в `showcase/pages.html` **из компонентов пакета**, с якорем
`p-<id>`. Ничего нового не верстается: если для сборки чего-то не хватает, это
дыра в компонентах, и она уходит в roadmap, а не закрывается разовым CSS.

Рядом с живым примером — правила семейства, которые уже выведены частотой
(`showcase-rule`, `data-rule`). Нет ещё правил — так и есть; не выдумывай
ради карточки на витрине.

Для лендинга, которому по замыслу нужна новая тематическая иллюстрация Slerm,
вызови `image-slerm` с темой и размерами конкретного блока. Сохрани результат в
`ui/assets/illustrations/`, подключи локально и проверь mobile/desktop. Не
генерируй картинку, если source design требует другую фотографию, логотип или
иллюстрационный язык.

### 5. Статья паттерна

`pages/<id>.md` (или `blocks/<id>.md` для лендинга) по структуре из
`guide-structure.md`: что за семейство · каркас числами · состав по областям ·
как перестраивается · правила семейства · живой пример · ограничения.

Для лендинга рецепты собираются в `PATTERNS.md`: последовательность блоков,
обязательные и необязательные, чем заканчивается страница.

Правила выбора и размещения изображений опиши человеку в `docs/guide/assets.md`:
роль, подходящие темы, aspect ratio, фон, focal point, responsive crop, alt и
границы генерации. Не вставляй prompt вместо правила применения.

### 6. Машинная проекция

Добавь паттерн в `machine/patterns.json` (схема — `machine-layer.md`): сетка
числами, области с последовательностью модулей, брейкпоинты, ссылки на правила,
пример со снимком. Это то, по чему модель потом соберёт аналогичный экран.

Использованные изображения добавь в `machine/assets.json` с тем же id, что в
`docs/guide/assets.md`: локальный файл, роль, размеры, поведение, alt policy и
`source.skill: image-slerm`, если генерация действительно разрешена.

### 7. Проверь

- страница держится на 320 / 768 / 1024 / 1400 без горизонтального overflow;
- порядок схлопывания совпадает со снятым с продакшена;
- в разметке нет классов, которых нет в `ui/`;
- `node <product>/tools/validate-components.mjs --strict` проходит.

## Отчёт

`.pipeline/pages-<id>/capture.md`: что снято, из каких модулей собрано, чего не
хватило, какие различия семейств зафиксированы.

## Чего не делать

- Не собирать страницу из разового CSS ради красивого скриншота.
- Не брать «самую впечатляющую» страницу вместо типичной для семейства.
- Не пересказывать содержимое страницы: паттерн описывает устройство, а не текст.
- Не выдумывать семейство, которого в продукте нет.
- Не переснимать прод: пример собирается из принятых компонентов, сверка —
  по снимкам страниц с инвентаризации.
- Не подменять снимок экрана кропом элемента и наоборот.
