# Шаг 2 — снять и сверстать

Вход текущего запуска: `$ARGUMENTS`.

Прочитай [`core-contract.md`](../../guide/core-contract.md),
[`evidence.md`](../../guide/evidence.md),
[`naming-states.md`](../../guide/naming-states.md),
[`package-invariants.md`](../../guide/package-invariants.md) и
[`spec-template.md`](../../guide/spec-template.md). Чужой готовый пакет не открывай.

По умолчанию работаешь над **batch из 2–4 связанных элементов** одного семейства
с общими источниками и закрытыми зависимостями. Один элемент бери для пилота,
blocker или явного запроса. Соседние проблемы не чини: добавляй отдельными
строками `planned` в `ROADMAP.md`.

## 1. Собери контекст элемента

Из `.pipeline/inventory.json` возьми записи batch: источники, селекторы, node keys
и зависимости. Все элементы должны относиться к одному семейству, не зависеть
друг от друга незакрытым шагом и переиспользовать общий контекст. Если `dependsOn`
не `done`, исключи элемент из batch и сообщи причину.

## 2. Сними факты с продакшена

Сначала посмотри, нет ли уже снимков в
`evidence/source/production/<id>/` (именованные PNG канонических ширин +
`computed.json`). Если есть — **не ходи на прод заново**, бери файлы с диска.
`evidence.md`.

Не хватает — снимай **кропом узла**, имя из inventory (`canonicalName`, иначе
story Storybook, иначе имя компонента в Figma):

```bash
node <product>/tools/capture.mjs --url <url> --selector "<selector>" \
  --name "<CanonicalName>" --out <product>/evidence/source/production/<id> \
  --widths 320,768,1024,1400
node <product>/tools/capture.mjs --url <url> --selector "<selector>" \
  --name "<CanonicalName>" --state hover \
  --out <product>/evidence/source/production/<id> --widths 320,768,1024,1400
```

Получится `CourseCard.1400.png`, `CourseCard.hover.320.png` — кроп элемента.
Снимки экрана (`pages/<id>/`) не подменяй и не снимай заново: они уже есть
с инвентаризации и понадобятся на шагах 6–7. `--full-page` на элементе не ставь.

Сними каждое состояние, которое достижимо: hover, focus-visible (клавиатурой),
disabled, open, loading — отдельным запуском или интерактивно через браузер.
Что снять не удалось — это будущий GAP, а не повод дорисовать.

Из `computed.json` возьми геометрию и типографику **срезом по селектору
элемента**, не читая файл целиком. Если элемент виден на нескольких страницах
(`seenOn` в inventory) — сними или перечитай кропы **всех** вхождений и сведи
таблицу «где → значение». Побеждает частое: его верстаешь и пишешь в правило.
Редкое — в «Ограничения», не в CSS «на всякий случай». Из `tokens.json` —
переменные `:root`. Найди в сборке продукта CSS-правила компонента (сетевые
ответы `.css`, поиск по корневому классу) — правила нужны текстом, не пересказом.

## 3. Сверься с Figma

Если в `evidence/source/figma/` уже лежат снимок узла и выписка metadata —
не зови MCP за новыми скриншотами. Иначе: `get_metadata` по **конкретному
node**, не по корню файла; `get_variable_defs` — имена переменных;
`get_screenshot` — эталон; `get_code_connect_map` — если у продукта есть
привязка к коду. Ничего не редактируй.

Figma даёт внешний вид, состав, варианты и responsive-намерение. Семантику, API и
имя берёшь из прода и HTML (`evidence.md`). Расхождение прода и Figma не сглаживай —
это запись в «Ограничения» со ссылкой на обе стороны.

## 4. Свёрстывай

- Токены — в `ui/tokens.css`: только те, что реально используются, со значениями
  из `:root` прода. Новых переменных не изобретай.
- CSS компонента — секцией в `ui/components/<id>.css`, подключённой из
  `ui/<product>.css`. Значения через `var(--…)`; литерал допустим, только если
  в проде литерал, и тогда это отмечается в спецификации.
- Иконки и шрифты — локальные копии в `ui/assets/`; в разметке спецификации пути
  локальные. Продовые URL остаются только в «Анатомии» как протокол снятого DOM.
- Разметка обязана работать на пустой странице с одним `ui/<product>.css`.
  Проверь это буквально: временный html в `.pipeline/<batch-or-id>/copy-check.html`, открыть
  через `node tools/serve.mjs`, посмотреть, удалить.
- Состояния, которых в проде нет, но без которых компонент не собрать, пиши
  в `ui/state-contract.css` и помечай как новую реализацию.

## 5. Спецификация

По шаблону, разделы в фиксированном порядке. Каждый факт — с источником; раздел,
которому нечем подтвердиться, не пишется. Пиши на языке продукта.

Файл: `<product>/components/<category>/<id>.md`.

## 6. Живой пример и правило на витрине

Секция в `showcase/components.html` с якорем `c-<id>`: сам элемент настоящей
вёрсткой, все состояния и варианты, каждое подписано.

Если по фактам уже есть победитель (покрытие ≥2) — в **той же секции** блок
`showcase-rule` с `data-rule`, формулировкой, счётом голосов и исключением.
Читатель видит образец и правило сразу. Тот же `id` — в спецификации и, если
`machine/` есть, в `rules.json`. Оболочка витрины — только её префикс, в `ui/`
не протекает.

## 7. Реестр

Добавь запись в `components/manifest.json` со всеми обязательными полями
(`id`, `canonicalName`, `storybookNames`, `legacyAliases`, `category`, `kind`,
`specPath`, `cssRoots`, `showcaseAnchor`, `figmaEvidence`, `status`, `requiredStates`)
и строку в `components/INDEX.md`. Статус ставь честно: `complete` — только если
покрыты все обязательные состояния; иначе `partial` с перечислением непокрытого.

## 8. Проверь себя перед сдачей

```bash
node <product>/tools/validate-components.mjs --strict \
  > <product>/.pipeline/<batch-or-id>/build.validate.log 2>&1
```

Плюс глазами: открой витрину на 320 и 1400, сравни с уже лежащими скриншотами
прода и Figma. Очевидные расхождения чини сам — ревью не место для того,
что видно сразу.

## 9. Отчёт

`.pipeline/<batch-or-id>/capture.md`: состав batch; по каждому id — источники,
состояния, node keys, созданная человекочитаемая статья, machine id, новые
evidence, конфликты и неподтверждённые места.

Полный вывод валидатора сохрани в `build.validate.log`. В capture и финальном
сообщении укажи exit code, число ошибок и путь, не копируй весь лог.

## Чего не делать

- Не выдумывать ARIA, состояния и props, которых нет в источниках.
- Не переносить в пакет фреймворк-атрибуты (`data-v-*`, скоупы, хеши).
- Не расширять согласованный batch на соседние компоненты.
- Не ставить `complete`, когда состояния не покрыты.
- Не открывать `career/` и `_sources/` как образец и не править их.
- Не переснимать прод и Figma, если evidence уже на диске.
- Не снимать ширины вне канона 320 · 768 · 1024 · 1400.
- Не верстать редкое значение, если частое уже измерено.
