# Шаг 1 — ТЗ и роадмап

Вход текущего запуска: `$ARGUMENTS`.

Прочитай [`core-contract.md`](../../guide/core-contract.md),
[`package-layout.md`](../../guide/package-layout.md),
[`evidence.md`](../../guide/evidence.md) и
[`naming-states.md`](../../guide/naming-states.md). Готовый чужой пакет не открывай.

Твоя работа: превратить набор ссылок в **список того, что предстоит сделать**, где
у каждой строки есть источник. Ничего не верстается и не описывается — на этом шаге
только инвентаризация и порядок.

## Вход

Ссылки любого вида: страницы продакшена, файлы и узлы Figma, Storybook, гайды,
локальные папки. Если не сказано, как называется пакет, выведи имя из продукта
и скажи, какое взял.

Перед инвентаризацией определи две вещи (`core-contract.md`):

- **Режим.** Пакет уже есть — сначала аудит: вызови скилл `guide-audit`, и план
  доработки станет входом для роадмапа. Пакета нет — идёшь дальше по этому скиллу.
- **Вид продукта.** Интерфейс или лендинг. От этого зависит единица работы
  (компонент → страница против примитив → блок → рецепт) и состав пакета.
  Признаки перечислены в `core-contract.md`; смешанный продукт разводится на два
  раздела, а не сваливается в один.

## Порядок

### 1. Разбери источники

Составь таблицу: тип (production / figma / storybook / guide / local), ссылка, что
на ней ожидается. Проверь достижимость каждой: страница открывается гостем?
узел Figma читается? Недостижимое не выкидывай — помечай `недоступно` с причиной,
это граница покрытия, а не мусор.

### 2. Сними страницы

Это **корпус страниц**: он нужен сразу, чтобы увидеть повторяющиеся узлы, и
потом ещё раз — чтобы собрать примеры экранов и вывести принципы. Снимается
один раз. По каждой production-ссылке сначала проверь
`evidence/source/production/pages/<page-id>/`: если именованные PNG канонических
ширин и `computed.json` уже есть — не ходи на прод. Иначе снимок **страницы
целиком** (`--full-page`), имя — id страницы:

```bash
node <product>/tools/capture.mjs --url <url> --selector body --full-page \
  --name "<PageId>" --out <product>/evidence/source/production/pages/<page-id> \
  --widths 320,768,1024,1400
```

Скрипт-шаблон — [`.claude/guide/capture.mjs`](../../guide/capture.mjs); при первом
запуске скопируй его в `<product>/tools/`. `serve.mjs` и `validate-*.mjs`
скопируй из `career/tools/` один раз при каркасе — не читая спецификации Career.

Открой снимки. Из `dom.html` и скриншотов выпиши **повторяющиеся узлы**: то, что
встречается на двух и более страницах или в двух и более экземплярах на одной, —
кандидат в компоненты. Уникальное, но крупное — кандидат в модуль или страницу.

### 3. Сними инвентарь Figma

Если в `evidence/source/figma/` уже есть выписка корня и обзорные снимки —
не зови MCP заново. Иначе: `mcp__figma__get_metadata` по корневому узлу —
состав страниц и component sets; `get_variable_defs` — переменные;
`get_screenshot` — общий вид, не галерея всех фреймов. Ничего не редактируй.
Схлопывай component sets по смыслу: `Button/Primary` и `Button/Secondary` —
один компонент с вариантами, а не два.

Если Figma MCP недоступен (не запущен desktop, нет прав), не выдумывай состав по
названиям ссылок — пометь источник `недоступно` и работай от прода.

### 4. Сведи реестр

Один элемент = одна запись, сведённая **по смыслу интерфейса**, а не по структуре
источников. Имена — канонические (`naming-states.md`), не из слоёв Figma.

`<product>/.pipeline/inventory.json`:

```json
{
  "product": "courses",
  "collectedAt": "2026-09-07",
  "elements": [
    {
      "id": "course-card",
      "canonicalName": "CourseCard",
      "category": "entities",
      "kind": "module",
      "seenOn": ["https://.../courses", "https://.../company/x"],
      "sources": [
        { "type": "production", "url": "https://.../courses", "selector": ".course-card" },
        { "type": "figma", "node": "12:345", "url": "https://figma.com/design/...?node-id=12-345" }
      ],
      "dependsOn": ["button", "chip", "avatar"],
      "occurrences": 14,
      "wave": "R3",
      "status": "planned",
      "notes": ""
    }
  ],
  "pages": [
    {
      "id": "courses-listing",
      "family": "listing",
      "url": "https://.../courses",
      "keyExample": true,
      "composedOf": ["page-header", "filter-panel", "course-card", "pagination"],
      "states": ["default", "empty", "filtered"],
      "wave": "R6"
    }
  ],
  "blocks": [
    { "id": "hero", "type": "hero", "url": "https://.../info/promo", "selector": ".hero", "usedOn": 3, "wave": "R3" }
  ],
  "unreachable": [{ "url": "https://.../profile", "reason": "требует логина" }]
}
```

`dependsOn` заполняй честно — по нему строится порядок волн.

### 5. Отбери ключевые примеры

Не все страницы равны. Для интерфейса ключевая страница — **по одной на
семейство** (листинг, страница сущности, профиль, дашборд, форма, пустое
состояние, ошибка), а не самая красивая. Для лендинга — по одному примеру
на тип блока плюс целые страницы как рецепты. Разбор — в скилле `guide-pages`;
твоя задача здесь отметить их `keyExample: true` и назначить волну.

Семейства, которого в продукте нет, не выдумывай — запиши в границу покрытия.

### 6. Разложи по волнам

Порядок неизменный: сначала предсказуемое ядро, потом композиции, потом
обобщение. **Интерфейс продукта:**

```
R0 Каркас пакета: структура, tokens.css, foundations, manifest, tools, витрина-пустышка
R1 Словарь состояний STATES.md и матрица обязательных состояний
R2 Примитивы: типографика, иконки, аватар, чип, бейдж
R3 Базовые компоненты: кнопки, поля, селекты, чекбоксы, вкладки, пагинация
   → Core Gate: все базовые complete, валидатор и браузерные проверки зелёные
R4 Каркасные модули: шапка, подвал, секции, сайдбар, фильтры
R5 Entity-модули: карточки сущностей продукта
R6 Ключевые страницы: по одной на семейство, композицией из закрытых модулей
R7 Принципы: правила композиции и Decision Guides из снятых страниц
R8 Машинный слой: machine/*.json, AGENTS.md, валидатор проекций
```

**Лендинг:**

```
R0 Каркас пакета
R1 Токены и типографика: шкала, цвета, сетка, отступы
R2 Примитивы: кнопки, ссылки, поля, иллюстрации
R3 Блоки: hero, секции, stats, карточки, форма, CTA, футер
R4 Рецепты страниц: из каких блоков и в каком порядке собирается каждый тип
R5 Принципы: ритм секций, распределение внимания, роль акцента
R6 Машинный слой
```

Элемент не попадает в волну раньше своих зависимостей. Модули не начинаются до
Core Gate — исключение только для исследовательского прототипа вне пакета.

Внутри волны назначь `batchId` группам из 2–4 элементов одного семейства, если
они используют общие страницы/evidence и не имеют незакрытых зависимостей друг
на друга. Пилот, blocker и уникальный тяжёлый модуль оставляй отдельным batch.
`batchId` запиши и в inventory, и в roadmap. Это единица build/review/accept и
атомарного коммита; строки элементов при этом остаются раздельными.

Черновой слой правил каркаса и сетки допускается сразу после инвентаризации:
без него не собрать модули. Он помечается черновиком и пересматривается в R7.

### 7. Напиши документы

**`<product>/BRIEF.md`** — ТЗ: что за продукт; таблица источников со ссылками и
достижимостью; что считаем в объёме и что сознательно нет; граница покрытия
(гость / логин); критерии готовности пакета; риски и открытые вопросы.

**`<product>/ROADMAP.md`** — по волне на раздел, в разделе таблица шагов:

```markdown
### R3 — базовые компоненты

| Шаг | Batch | Элемент | Источники | Зависит от | Статус | Результат |
|---|---|---|---|---|---|---|
| R3-01 | controls-a | [Button](https://prod/...) · [Figma 12:340](https://figma.com/...) | `.btn` на 4 страницах | — | planned | |
```

Плюс на каждую волну — **exit criteria** списком проверяемых условий, а не
пожеланий. Сверху раздела — таблица «Текущий прогресс»: волна, сколько
шагов `done` / всего, что блокирует.

Статусы шагов: `planned` → `in-progress` → `review` → `done` (ставит только приёмка,
шаг 5) → `blocked` (с причиной).

## Выход

`BRIEF.md`, `ROADMAP.md`, `.pipeline/inventory.json` и, если пакет новый, каркас
папок из `package-layout.md`. В финальном сообщении: сколько элементов найдено, как они
разложены по волнам, что недостижимо и какие решения приняты за пользователя.

## Чего не делать

- Не описывать компоненты — это шаг 2.
- Не раздувать реестр вариантами одного компонента.
- Не переносить в реестр имена слоёв Figma.
- Не ставить статус `done` — его ставит только приёмка.
- Не переснимать страницы и Figma, если evidence уже на диске.
- Не открывать `career/`, чтобы подсмотреть структуру: она в `package-layout.md`.
