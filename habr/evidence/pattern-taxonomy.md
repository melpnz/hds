# Pattern Library — taxonomy checkpoint

Снято перед сборкой `showcase/pages.html`, как и договаривались. Categories
ниже — не готовый список, а результат прогона реальных источников через
исследовательский чек-лист (feed/list, article/content, profile/entity,
hub/company, search, editor/content creation, settings/forms,
authenticated/admin, management lists, entity edit, modal/overlay). Career
taxonomy не переносилась — категории выведены заново.

Источники: 14 production-страниц (гость, `evidence/source-map.md`),
Figma `🧶habr` (карта сайта — низкое разрешение, не читается, взято как
направляющий сигнал, не как факт), Figma `m.habr-admin-company` (навигация,
таблицы, форма, состояния — просмотрено визуально через 5 скриншотов),
Storybook (только для behaviour оверлеев, уже учтён в `components/`).

## 1 · SHELL (сквозной, не семейство страниц)

| | |
|---|---|
| **Источники** | production, все 14 страниц |
| **Наблюдений** | 14/14 |
| **Production/Figma** | Production |
| **Confidence** | HIGH |
| **Статус** | **CONFIRMED** |

**Layout regions.** Шапка (sticky, 56/48px) → `.tm-page-width` контейнер
(1096/24 · 768/16 · edge-to-edge) → `.tm-page__wrapper` (flex) →
`.tm-page__main_has-sidebar` (гибкая) + `.tm-page__sidebar` (300px,
`position: relative`, НЕ липкий) → подвал (`tm-footer-menu` + `tm-footer`).

**Hierarchy.** Шапка → тело страницы → подвал. Внутри тела: главная
колонка первична, сайдбар вторичен.

**Reusable modules.** Header (не специфицирован отдельно — GAP, см. §7),
Footer (не специфицирован — GAP), `ui/layout.css`.

**Primary actions.** Нет — это оболочка, не экран.

**Responsive.** Единственный найденный шаблон: ≥1024 — контейнер 1096/24,
768–1023 — 768/16, ≤767 — во всю ширину. Двух брейкпоинтов оболочки
(767/768 и 1023/1024) достаточно объясняют все наблюдения — третьего
не найдено.

**States.** Нет.

**Ключевой факт: сайдбар — зарезервированная колонка, не гарантированный
контент.** На 6 из 14 страниц (`feed`, `articles-all`, `news`, `hub`,
`article`, `article-comments`) сайдбар физически пуст для гостя (23 символа
— пустой Vue-фрагмент). Заполнен реальным содержимым только там, где есть
facts-блок сущности (`user`, `company`, `user-posts`) или фильтр/статистика
(`companies-list`, `authors`, `sandbox`). **Правило переноса:** не считать,
что сайдбар листинга обязан быть пустым или обязан быть заполненным —
это зависит от типа страницы, и оба случая подтверждены.

## 6 · PROFILE / ENTITY (user · hub · company)

| | |
|---|---|
| **Источники** | production: `user`, `hub`, `company` |
| **Наблюдений** | 3 страницы |
| **Production/Figma** | Production |
| **Confidence** | HIGH |
| **Статус** | **CONFIRMED** |

**Ключевое отличие от интуиции, унаследованной из Career:** идентификационная
карточка сущности (аватар, имя, рейтинг/подписчики, действие «подписаться»)
стоит **в верхней части главной колонки**, а не в левом сайдбаре. Подтверждено
трижды позиционным сравнением в DOM (`tm-hub-card`/`user-card`/
`tm-company-profile-card` встречаются в разметке РАНЬШЕ `tm-page__sidebar`
на всех трёх страницах). Сайдбар при этом не пуст — несёт **вторичные факты**:
`tm-user-basic-info`/`tm-company-basic-info` (`DescriptionList`) +
`tm-user-specialization` (квалификация/зарплата/навыки).

Это же построение подтверждено ещё раз в authenticated-контексте: скриншот
admin-дашборда компании (Figma) показывает идентичность компании (лого,
рейтинг ★4.17, подписчики) **тем же способом** — в верхней части главной
колонки, а не в сайдбаре. Композиционное правило работает по обе стороны
входа.

**Layout regions.** Shell → главная колонка: identity-карточка → `tabs`
(навигация по разделам сущности — для `user`: «Публикации/О себе»-подобное;
для `company`/`hub`: «Статьи/О компании») → список (для `company`/`hub`
это тот же `article-snippet`-фид, для `user` — `tm-block` секции: badges,
description-list) → `tm-pagination`, если список есть. Сайдбар: facts-блок.

**Reusable modules.** `user-card`/`tm-hub-card`/`tm-company-profile-card` —
три РАЗНЫХ модуля с одинаковой ролью, не один общий компонент — **не
объединять в один «EntityCard» без проверки**, они наблюдались с разными
наборами полей. `DescriptionList`, `Badges` (не специфицирован —
критично для этого паттерна, см. чекпойнт §6), `Block`.

**Primary actions.** «Подписаться»/«Написать» — на identity-карточке
(`tm-button-follow`), рядом с идентичностью — не в конце страницы. Это
единственное найденное сходство с Career-правилом «действие рядом
с сущностью».

**Responsive.** Не проверено детально — GAP.

**States.** Не наблюдалось пустых состояний (у всех трёх сущностей был
контент).

## 9 · AUTHENTICATED / ADMIN — три подпаттерна

Единственное семейство, где production не источник вообще (`/auth/`
уводит на другую систему, см. `RULES.md`-эквивалент Habr). Источник — целиком
Figma `m.habr-admin-company`, подтверждено визуально (5 скриншотов), поэтому
всё ниже — **FIGMA-CONFIRMED**, не production-confirmed. Разница
принципиальна и сохраняется в маркировке паттернов.

### 9.1 · Admin section screen (dashboard-lite)

| | |
|---|---|
| **Наблюдений** | 1 полный экран (Биллинг), структура навигации — Figma-компонент с 6 секциями |
| **Confidence** | MEDIUM-HIGH (один полный скриншот, но композиция самосогласованна и перекрёстно подтверждена именами) |
| **Статус** | **CONFIRMED** (Figma) |

**Layout regions.** Стандартная шапка Habr (та же, что в public — логотип,
поиск, колокольчик, аватар) → identity-карточка компании (см. §6, тот же
приём) → **горизонтальные Tabs шести секций** (Статистика/Публикации/
Компания/Биллинг/Настройки/FAQ — тот же компонент `Tabs`, что в public) →
главная колонка: контентные карточки раздела (заголовок + описание +
условное состояние/форма) → правый сайдбар: **вторичный список** (карточка
с построчной навигацией внутри раздела, активный пункт — левая полоса
акцентным цветом + счётчик) + виджет «Новости Хабра» (та же карточка,
что и в public — заголовок + список ссылок с описанием).

**Reusable modules.** `Tabs` (переиспользован без изменений), `Block`
(вероятно, контентные карточки — не проверено на уровне кода), `Notice`
(информационное сообщение о заявке — похоже на `tm-notice_info`, не
подтверждено кодом, Figma-only), Button (зелёный «Запросить бронь» —
подтверждает Success-роль как основную CTA в admin).

**Primary actions.** Зелёная кнопка-действие рядом с описанием услуги —
тот же принцип «действие рядом с тем, к чему относится», что в §6.

**Responsive.** Не подтверждено — GAP (Figma не давала mobile-версию
именно этого экрана).

**States.** Явно показано состояние «запрос отправлен, ждём менеджера»
(информер вместо формы) вместо «услуга доступна» (форма + кнопка) —
两 разных состояния одного и того же блока услуги, качественное
свидетельство state-driven content.

### 9.3 · Admin management list (dense table)

| | |
|---|---|
| **Наблюдений** | 1 таблица (строки статей), с явным `mobile=no`/`mobile=yes` |
| **Confidence** | HIGH (структура полностью раскрыта, включая responsive-трансформацию) |
| **Статус** | **CONFIRMED** (Figma) |

**Layout regions.** Строка (desktop): заголовок (обрезка в 2 строки) +
иконка-редактирование + меню «⋯» → статус-чипы («В черновиках»/«На сайте»,
«Отложена: вкл/выкл») с иконками → переключатель «Трекинг: вкл/выкл» →
4 числовые метрики с цветным фоном ячейки (зелёный/голубой/оранжевый —
предположительно вид метрики) → FB/VK счётчики шеринга.

**Responsive transformation — не сжатие, а перекомпоновка:** на мобильном
метрики переезжают ПОД заголовок/статусы, группируясь парами
иконка+число (↑/💬/🔖/👁), а не остаются в строку — тот же принцип
«перекомпоновка, не просто уменьшение», что видели у Dialog (модалка→шторка).

**States.** Как минимум 4 состояния строки видны прямо в срезе:
черновик / опубликовано / запланировано (вкл/выкл) / не участвует
в рейтинге — комбинируются одновременно, не взаимоисключающие.

**Reusable modules.** Ни один существующий компонент пакета не покрывает
эту таблицу целиком — статус-чипы близки к `StatusChip`-подобному
паттерну, но отдельного компонента для «управленческой строки» в пакете
нет. Не специфицируется как компонент на этом этапе (это PAGE-PRESENTER
уровня паттерна, не переиспользуемый примитив) — фиксируется как паттерн.

## 10 · MODAL / OVERLAY FLOWS

| | |
|---|---|
| **Источники** | Storybook (Dialog, Dropdown, Hint — уже специфицированы в `components/overlays/`) |
| **Confidence** | см. соответствующие спецификации |
| **Статус** | **CONFIRMED** как компоненты, **PARTIAL** как паттерн композиции страницы |

Как компоненты — полностью покрыты (§ предыдущий этап). Как **паттерн
использования на странице** (что именно открывает модалку, в каком месте
экрана, с каким содержимым) — не подтверждено ни на одной production-
странице (все модалки требуют авторизации/действия, гостю недоступны).
Здесь модаль документируется только на уровне компонента, не на уровне
page pattern — считать эту категорию закрытой компонентами, не page
family.

## 11 · SETTINGS / FORMS (вне admin)

**Не найдено отдельно от §9.2.** Единственная форма, доступная гостю —

«формой настроек» в полном смысле. Полноценная форма настроек вне admin
не подтверждена. **MISSING** как отдельное семейство — покрыто только
через admin-контекст.
