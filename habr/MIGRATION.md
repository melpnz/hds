# Перенос гайда на machine-first showcase

Этот документ фиксирует практику, полученную при переносе Career. Он предназначен одновременно для человека и ИИ-агента. Цель миграции — не просто воспроизвести старую витрину, а разложить знания на небольшие адресные спецификации, из которых viewer собирает удобное представление.

## Результат миграции

После переноса должны существовать два согласованных слоя:

1. `machine/` — канонические небольшие JSON-файлы для ИИ.
2. `viewer/` — производное человеческое представление тех же данных и изолированных примеров.

Viewer не является вторым источником истины. Значимые правила нельзя хранить только в HTML-превью или JavaScript оболочки.

## Базовые принципы

- Сначала инвентаризация, потом преобразование. Нельзя считать миграцию полной по числу созданных страниц.
- Одна сущность — один адресный JSON-файл. Не объединять весь гайд в один большой документ.
- Один пример показывает один компонент, модуль или сценарий. Не использовать снимок всей старой витрины как пример каждого элемента.
- Неизвестное обозначается явно. Запрещено восстанавливать неподтверждённый DOM по внешнему виду.
- Старый источник сохраняется до завершения сверки и не участвует в обычном порядке чтения ИИ.
- Оболочка универсальна; продуктовые цвета, отступы, ограничения ширины и адаптив находятся внутри примеров и спецификаций продукта.

## Этап 1. Зафиксировать исходное состояние

До изменений:

- сохранить старый пакет в `archive/<product>/v1/` или другом согласованном архивном пути;
- записать количество документов, компонентов, паттернов, примеров, изображений и иконок;
- собрать перечень ссылок между документами;
- отдельно перечислить отсутствующую разметку, недоступные страницы и неподтверждённые состояния;
- не удалять старые данные до прохождения проверки покрытия.

Архив нужен для сверки, но не должен быть входной точкой нового гайда и не должен автоматически загружаться ИИ.

## Этап 2. Построить карту соответствий

Для каждой исходной сущности зафиксировать:

| Поле | Что записать |
|---|---|
| Источник | старый файл, якорь или идентификатор |
| Новый `id` | стабильный kebab-case идентификатор |
| `kind` | `component`, `module` или `pattern` |
| Категория | назначение сущности, а не имя старой папки |
| Новый файл | путь внутри `machine/` |
| Примеры | отдельные HTML-сценарии или причина отсутствия |
| Статус | перенесено, объединено с дублем, отложено |

Перед созданием новой сущности проверить каталог на смысловой дубль. Если старый фрагмент содержит несколько независимых компонентов, разделить его на несколько записей. Не создавать вкладку «Старая витрина» или «Визуальная ссылка» как постоянный способ хранения таких фрагментов.

## Этап 3. Спроектировать машинный слой

Минимальный маршрут чтения ИИ:

1. `machine/index.json` — граница знаний, статус, порядок чтения и ключевые файлы.
2. `machine/catalog.json` — компактный маршрутизатор по `id`, `kind`, группам и `tags`.
3. Один выбранный файл сущности.
4. Только связанные `rules`, `implementation`, `examples` и evidence.

Требования к данным:

- названия и теги должны позволять найти сущность без чтения всех файлов;
- `maturity.spec`, `maturity.markup` и `knowledge.confidence` не заменяют друг друга;
- `markup: null` требует `missingReason` и безопасный `fallback`;
- состояния интерфейса, функции и домена хранятся раздельно;
- длинные исследования и исторические материалы не копируются в каждую спецификацию;
- цифры, CSS и evidence должны иметь один канонический источник.

## Этап 4. Нарезать примеры

Используются два режима.

### `intrinsic`

Для кнопок, иконок, полей, уведомлений и других небольших элементов:

```json
"preview": { "mode": "intrinsic" }
```

Правила:

- панель разрешений не показывается;
- iframe растёт по высоте содержимого и не имеет собственного скролла;
- несколько вариантов идут друг под другом с подзаголовками, а не во вкладках;
- пример не содержит лишней рамки, серой подложки или оболочки только ради демонстрации.

### `viewport`

Для модулей, композиций и страниц:

```json
"preview": {
  "mode": "viewport",
  "widths": [320, 480, 768, 1024],
  "height": 640
}
```

Viewer всегда предлагает `320 / 480 / 768 / 1024 / Auto`:

- 320, 768 и 1024 — контрольные брейкпоинты страницы;
- 480 — проверка резинового поведения между брейкпоинтами;
- `Auto` — вся доступная ширина viewer;
- между брейкпоинтами композиция должна быть резиновой;
- максимальная ширина продуктового контейнера, например 1100 px, задаётся внутри продукта, а не оболочкой.

Точечный фон принадлежит viewer. Всё внутри iframe должно выглядеть как продукт: белый фон остаётся белым, а внешние технические отступы не маскируются под продуктовые.

## Этап 5. Вынести пояснения из превью

Исследовательские комментарии, допущения и ограничения нельзя помещать внутрь демонстрационной страницы. Они воспринимаются как часть продукта.

Использовать `previewNotes`:

```json
"previewNotes": [
  { "type": "guidance", "text": "Что именно показывает пример." },
  { "type": "assumption", "text": "Какое решение не подтверждено." },
  { "type": "coverage-warning", "text": "Что пример не покрывает." }
]
```

Допустимые типы: `guidance`, `assumption`, `coverage-warning`.

## Этап 6. Организовать навигацию

Меню строится из `machine/catalog.json`:

- `navSection` — крупный слой: основы, компоненты, паттерны, правила, документы;
- `navGroup` — функциональная группа: действия, поля и выбор, карточки, обратная связь, страницы;
- `title` — короткое различимое имя;
- `tags` — синонимы, состояния и пользовательские термины для поиска.

Не переносить порядок старой витрины механически. Сначала собрать близкие сущности, затем выбрать понятный стабильный порядок внутри группы.

## Этап 7. Проверить ассеты

- Сверить количество иконок и изображений с исходным инвентарём.
- Проверить существование и декодирование каждого файла, а не только путь в JSON.
- Убедиться, что относительные пути работают из iframe.
- Не считать заглушку сломанного изображения перенесённым ассетом.
- Не загружать все ассеты в контекст ИИ: каталог должен позволять выбрать нужный файл адресно.

## Этап 8. Приёмка

Минимальный набор автоматических проверок:

```powershell
npm run validate
npm run serve
npm run validate:viewer -- http://127.0.0.1:4173
```

Статическая проверка должна обнаруживать:

- потерянные файлы и ссылки;
- несовпадение каталога и спецификаций;
- невалидный preview-контракт;
- `markup: null` без причины и fallback;
- устаревшие счётчики покрытия.

Браузерная проверка должна обнаруживать:

- ошибки загрузки и выполнения JavaScript;
- отсутствующие пункты меню и неработающий поиск;
- viewport-шапку у intrinsic-примеров;
- вкладки вместо последовательных intrinsic-вариантов;
- внутренний скролл или неверную высоту intrinsic iframe;
- неверный набор `320 / 480 / 768 / 1024 / Auto`;
- горизонтальный overflow страницы на 320 и между брейкпоинтами;
- комментарии, ошибочно оставленные внутри продуктового iframe;
- декодирование не всех заявленных ассетов.

Ручная сверка дополняет скрипты: пройти весь каталог, сравнить каждый новый элемент со старым источником и отдельно проверить 320, 480, 768, 1024 и широкую ширину.

## Инкрементальное повторное ревью

После первого полного прохода не нужно заново читать весь архив при каждой правке.

1. Зафиксировать карту соответствий и исходные счётчики.
2. На повторном ревью проверять изменённые сущности и их зависимости.
3. Полный прогон скриптов выполнять всегда.
4. Полную визуальную сверку повторять при изменении оболочки, общих стилей, схемы, мигратора или breakpoint-контракта.

## Definition of Done

Миграция завершена, когда одновременно выполнено следующее:

- каждая исходная сущность перенесена, объединена с подтверждённым дублем или явно внесена в roadmap;
- все знания доступны через `machine/index.json` и `machine/catalog.json`;
- viewer не содержит уникальных правил, отсутствующих в машинном слое;
- простые элементы изолированы, страницы адаптивны, пояснения вынесены из iframe;
- поиск находит сущности по названию, типу, группе и ключевым состояниям;
- ассеты полностью сверены;
- статическая и браузерная проверки проходят;
- старый пакет можно удалить из рабочего дерева без потери знаний, оставив при необходимости только внешний или игнорируемый архив.

Если хотя бы один исходный элемент не получил статус, миграция считается незавершённой.
