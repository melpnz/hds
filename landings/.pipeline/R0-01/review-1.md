### 1 · major · Обоснование отказа от дефолтных ширин опровергается данными пакета

`tools/capture.mjs:27-31` и `tools/README.md:313-316` утверждают одно и то же:

> Ни одна из этих четырёх ширин **не совпадает ни с одной** из пяти ширин артборда.

Это неверно. Ширина **1440 стоит в обоих списках**: она вторая по частоте среди
артбордов (5 узлов из 18) и она же есть в наборе скилла `375,768,1024,1440`.

```
$ node -e "… inv.nodes … " (в landings/)
ширины артбордов: {"1240":1,"1280":1,"1400":3,"1440":5,"1600":8}
пересечение с набором скилла [375,768,1024,1440]: [ 1440 ]
```

Подтверждается и без скрипта: `ROADMAP.md:24` — «Ширины: 1600 — 8 · **1440 — 5**
· 1400 — 3 · 1280 — 1 · 1240 — 1».

Само решение — сделать `--widths` обязательным, пока Q-4 открыт, — защитимо и
я его не оспариваю: аргумент «дефолт стал бы решением инструмента за владельца»
самодостаточен. Плохо то, что рядом с ним записан ложный факт, и записан дважды,
в исполняемом файле и в документации. METHOD §4: у факта есть источник; здесь
источник пакета говорит противоположное. **Исправить формулировку в обоих
местах, решение оставить.**

### 2 · major · `kebab()` ломает `id` имени с цифрой

`tools/validate-blocks.mjs:194-197`:

```js
const kebab = (name) => name
  .replace(/([a-z0-9])([A-Z])/g, '$1-$2')
  .replace(/([A-Z]+)([A-Z][a-z])/g, '$1-$2')
  .toLowerCase();
```

Правило `([a-z0-9])([A-Z])` разрывает цифру и следующую заглавную. Прогон по
**всем 24 каноническим именам из `.pipeline/inventory.json`** — то есть по тем
именно записям, которые заведёт R0-05:

```
ok    footer-social            <- FooterSocial          kebab=footer-social
…
FAIL  footer-corporate-b2b     <- FooterCorporateB2B    kebab=footer-corporate-b2-b
…
несовпадений: 1 из 24
```

Это блок **R2-01** — первый блок волны R2. Реестр получит ошибку
«id не kebab-case от canonicalName „FooterCorporateB2B“ — ожидалось
footer-corporate-b2-b», причём предложенное значение само не годится в `id`.

Побочно: `kebab()` не заменяет пробелы (`"Site Header" → "site header"`).
Для METHOD §5 (канонические имена PascalCase) это не срабатывает, но и защиты
от такого имени тоже нет — сообщение предложит `id` с пробелом.

Воспроизведение: `node tools/validate-blocks.mjs --strict` на реестре с записью
`{"id":"footer-corporate-b2b","canonicalName":"FooterCorporateB2B", …}`.

### 4 · major · `validate-normative` не видит светлую тему дефолтом в `:root`

Ключевой инструмент пакета (Exit criteria R0 п. 2 требует, чтобы он
подтверждал «светлая тема целиком — спроектировано» кодом 0). Область узнаётся
регуляркой `tools/validate-normative.mjs:95`: `theme=light`,
`prefers-color-scheme: light`, либо сегмент `light` в имени переменной.

Красный прогон **B** — светлая как база, тёмная как оверрайд:

```css
/* @snapshot 02_Landings 20097:8612 — палитра */
:root { --core-bg-page: #ffffff; --core-text-primary: #0f0f0f; }
:root[data-theme="dark"] { --core-bg-page: #0f0f0f; }
```

```
Проверено: объявлений 3 в 4 файле(ах) CSS, статей 0.
EXIT=0
```

Светлая тема подписана снимком с узла — сторож молчит. Так же проходят
`.theme-light` (прогон C, EXIT=0) и `.light-theme` (прогон D, EXIT=0).

Это не гипотетическая форма записи: прецедент, на который ссылается сам пакет
(`ui/tokens.css`, шапка; Хабр `light-v2.css` / `dark-v2.css`), устроен именно
так — светлая база, тёмная оверрайдом. То есть самый вероятный способ, которым
R0-02 напишет токены, проходит мимо И-2.

Что предложить R0-02 и правке: либо зафиксировать в контракте `ui/tokens.css`,
что светлая тема обязана быть отдельным селектором с `light` в имени (и это
проверять), либо узнавать область не по имени, а по маркеру: под `@snapshot`
может стоять только то, что снято, — а тема, объявленная не в тёмной ветке,
требует `@normative` независимо от селектора.

### 11 · minor · Пустой реестр без `schemaVersion` не проходит `--strict`

Exit criteria R0 п. 6 требует, чтобы `--strict` проходил на пустом реестре;
`capture.md` утверждает это без оговорки.

```
$ echo '{"entries":[]}' > blocks/manifest.json
$ node tools/validate-blocks.mjs --strict
  manifest: нет поля schemaVersion — по нему потребитель узнаёт, что схема сменилась
  Запуск с --strict: предупреждения считаются ошибками.
EXIT=1

$ echo '{"schemaVersion":1,"entries":[]}' > blocks/manifest.json
$ node tools/validate-blocks.mjs --strict
EXIT=0
```

`schemaVersion` не назван ни в контракте записи (`tools/README.md:60-95`), ни
где-либо ещё. Верхнеуровневые ключи манифеста вообще не задокументированы:
`schemaVersion`, `allowedStatuses`, `allowedStates`, `allowedKinds`,
`allowedCategories`. Причём `compareDictionary` (строка 96) молча пропускает
незаявленный словарь — то есть сверка «в обе стороны», обещанная в
`tools/README.md:65-68`, включается только если R0-05 сам решит объявить
словари. R0-05 нужен явный контракт верхнего уровня.

| Расхождение | Оценка |
