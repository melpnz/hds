# Инструменты пакета Landings

Шесть скриптов. Запускаются из корня пакета (`landings/`), Node без сборки.
Зависимость одна и только у съёмки — `@playwright/test`.

| Скрипт | Что проверяет или делает | Заведён на |
|---|---|---|
| `validate-blocks.mjs` | реестр `blocks/manifest.json` сходится со статьями, CSS и витриной | R0-01 |
| `validate-counts.mjs` | числа, заявленные в README, BRIEF, ROADMAP, CHANGELOG | R0-01 |
| `validate-classes.mjs` | классы витрины против CSS; отделённость витрины METHOD §6.2 | R0-01 |
| `validate-normative.mjs` | норматив не выдан за факт: маркеры происхождения, И-1 и И-2 | R0-01 |
| `serve.mjs` | локальный сервер витрины, порт 4180 | R0-01 |
| `capture.mjs` | съёмка узла живой страницы: DOM, computed styles, токены, PNG | R0-01 |

Общее соглашение о кодах возврата — оно же ответ на вопрос «почему проверка
не зелёная, если ошибок нет»:

| Код | Значение |
|---|---|
| **0** | проверено и сошлось |
| **1** | расхождение; в `--strict` — ещё и предупреждение |
| **2** | **проверять нечего**: предмета проверки в пакете ещё нет |

Код 2 существует потому, что «всё сошлось» и «сверять было не с чем» —
разные новости, а выглядят они одинаково. Пакет собирается волнами, и до
своего шага половина проверок не имеет предмета: зелёный ноль на пустом
месте приучал бы читать зелёный цвет как «проверено».

Что вернёт каждая проверка на 8 сентября 2026, сразу после R0-01:

```
node tools/validate-blocks.mjs      2   реестра нет, его заводит R0-05
node tools/validate-counts.mjs      0   70 утверждений в 5 файлах
node tools/validate-classes.mjs     2   витрины нет, её заводит R0-06
node tools/validate-normative.mjs   2   объявлений в ui/ нет, их заводит R0-02
```

> **Расхождения с чеклистом приёмки — все три.** `ROADMAP.md` (строки 56-61)
> ждёт кода 0 от каждой команды; сегодня три из шести отвечают иначе, и это
> не падения, а отсутствие предмета:
>
> | Команда | Чеклист ждёт | Сегодня | До какого шага |
> |---|---|---|---|
> | `validate-blocks.mjs --strict` | 0 | **2** — реестра нет | до R0-05 |
> | `validate-normative.mjs` | 0 | **2** — объявлений в `ui/` нет | до R0-02 |
> | `npm test` | 0 | **1** — скрипта `test` нет | до R0-06 |
>
> `validate-classes.mjs` в самом чеклисте оговорён («до R0-06 код 2»),
> и расхождением не считается. Строка для роадмапа заведена в отчёте шага
> R0-01; до её разбора читайте код 2 у этих проверок как «предмета ещё нет».

## validate-blocks.mjs

```bash
node tools/validate-blocks.mjs
node tools/validate-blocks.mjs --strict     # предупреждения тоже валят
```

Инвариант METHOD §6.5: у каждой записи реестра есть существующая статья,
существующий CSS root и существующий якорь витрины. Реестр — единственное
место, где сходятся статьи, CSS и витрина; разошёлся он — и на вопрос «что
в пакете есть» три источника отвечают по-разному.

Верхний уровень файла:

| Ключ | Обязателен | Что означает |
|---|---|---|
| `schemaVersion` | **да** | число. По нему потребитель узнаёт, что схема записи сменилась. Без него `--strict` не проходит |
| `entries` | **да** | список записей. Не список — код 2: реестр сломан, а не «пуст» |
| `allowedStatuses` | нет | словарь статусов METHOD §5, сверяется в обе стороны |
| `allowedStates` | нет | словарь состояний METHOD §5 |
| `allowedKinds` | нет | словарь видов METHOD §5 |
| `allowedCategories` | нет | словарь категорий METHOD §5 |

Необъявленный словарь — не ошибка (Exit criteria R0 п. 6 требует, чтобы
`--strict` проходил на пустом реестре), но и не «сошлось»: сверка по нему
не выполняется, и об этом печатается строка «К проверке руками». Молча
выключенная проверка выглядит как пройденная — этого здесь нет нигде.

Минимальный реестр, проходящий `--strict`: `{"schemaVersion": 1, "entries": []}`.
Реестр, который не разбирается как JSON, даёт **код 2** с текстом ошибки
разбора: разбирать в нём нечего.

Что проверяется у каждой записи:

- **обязательные поля**: `id`, `canonicalName`, `legacyAliases`, `category`,
  `kind`, `specPath`, `cssRoots`, `showcaseAnchor`, `figmaEvidence`,
  `status`, `requiredStates`, `wave`, `step`, `dependsOn`. Поля блока —
  `coverage`, `coverageBase`, `nodes`, `keyExample`, `measuredBy`, `rule`:
  если есть хоть одно, обязаны быть все;
- **закрытые словари METHOD §5** — статусы, категории, виды, состояния,
  в обе стороны: и «реестр расширяет словарь», и «реестр не знает значения
  из словаря». Слова `active`, `focus`, `select`, `inactive` запрещены
  отдельной строкой сообщения, потому что их приносят чаще всего;
- **`canonicalName` — PascalCase, `id` — kebab-case от него** (METHOD §5).
  Границей слова считаются три перехода: строчная → заглавная
  (`FooterSocial` → `footer-social`), цифра → начало слова
  (`Grid2Col` → `grid2-col`) и хвост аббревиатуры перед словом
  (`HTMLParser` → `html-parser`). Цифра сама по себе границей не считается:
  `FooterCorporateB2B` → `footer-corporate-b2b`, а не `footer-corporate-b2-b`.
  Имя не PascalCase отвергается раньше, чем считается `id`: из «Site Header»
  вывелся бы `id` с пробелом, который сам не проходит проверку. Прогон
  по всем 24 каноническим именам инвентаризации — 24 из 24;
- **уникальность** `id`, `canonicalName`, `showcaseAnchor`, `specPath`;
- **инвариант И-4**: `id` не оканчивается на `-career`, `-habr`, `-courses`.
  Один набор блоков на три продукта, различие живёт в токенах;
- **`specPath`** существует на диске. Путь пишется от корня пакета: статьи
  блоков лежат в `blocks/`, примитивов — в `components/`, и путь от папки
  реестра читался бы как `../components/…` у каждого примитива;
- **`cssRoots`** — имена классов без точки, каждый определён в `ui/**/*.css`.
  Пока в `ui/` нет ни одного правила, проверка откладывается целиком:
  иначе R0-05 не смог бы завести реестр до вёрстки блоков;
- **`showcaseAnchor`** есть в `showcase/blocks.html` и содержит `id` записи.
  Разметка витрины разбирается без комментариев, `<pre>` и `<code>`: строка
  внутри примера для копирования не должна удовлетворять проверке якоря
  наравне с живой секцией;
- **`figmaEvidence`** — node id вида `20216:120`, `fileKey` из числа файлов
  инвентаризации. Строка «hero второго макета» источником не является;
- **`step`** — существующая строка таблицы `ROADMAP.md`, `wave` с ним сходится;
- **`dependsOn`** — существующие записи, без ссылки на себя и без циклов;
- **покрытие**: `coverage` — дробь, знаменатель равен `coverageBase`,
  числитель равен длине `nodes`. Числитель сверяется со списком, а не
  со строкой: иначе дробь остаётся верной на вид при вычеркнутом узле
  (инвариант И-7). `rule` истинно при покрытии ≥ 2 и ложно при 1 — METHOD §8:
  подтверждение на одной странице это наблюдение, а не правило.

Поля `storybookNames` в контракте нет: Storybook у лендингов не существует
ни в одном источнике, и обязательное пустое поле приучало бы заполнять
реестр формально. Его место занимают `coverage` и `nodes`.

**Известный вопрос к R0-05.** METHOD §5 держит закрытый словарь видов —
`primitive`, `component`, `module`, `adapter`, — и значения «блок» в нём нет,
хотя METHOD §1 называет блок единицей лендинга. Проверка сверяет `kind`
со словарём METHOD, поэтому R0-05 обязан либо отобразить блок в `module`,
либо изменить METHOD; молча расширить словарь в реестре не получится.

## validate-counts.mjs

```bash
node tools/validate-counts.mjs
node tools/validate-counts.mjs --explain    # что где написано и чем измерено
```

Счётчики записаны прозой в четырёх файлах и правятся руками. После любой
правки они расходятся молча: документ продолжает утверждать старое число,
и по нему судят о покрытии.

Устройство: слева измерение (значение и то, чем оно получено), справа
таблица «файл · регулярка · ключ». Источник истины — `.pipeline/inventory.json`
и сам `ROADMAP.md`; шаги считаются по строкам его таблиц, а не по числу
в его же сводке.

Покрытия блоков считаются **по длине списка узлов**, а не по строке
`coverage`, — иначе сторож сверял бы строку с самой собой. Так дробь ловит
и вычеркнутый узел (инвариант И-7).

Правило, чей файл ещё не заведён, пропускается с пометкой. Правило, чей файл
есть, а формулировка не нашлась, — ошибка: значит, текст переписали, а сторож
остался сторожить исчезнувшее. Правьте документ — или правило в скрипте,
если формулировка изменилась намеренно.

Правило читает **все** вхождения формулировки в файле, а не первое: число,
повторённое в одном файле дважды, сторожилось в одном месте из двух, и вторая
копия молча расходилась с первой. Разделитель разрядов в тексте («12 000»)
разбору не мешает.

Сегодня сторожатся: 18 узлов лендингов, 4 бренд-доски, 23 баннера,
9 измеренных CSS, 19 типов блоков, 5 примитивов, 24 записи реестра,
3 рецепта, 3 производственные линии, 40 находок, 4 вопроса, 12 границ
покрытия, 46 шагов, 9 шагов R0.

Плюс три числа, которые чеклист приёмки называет поимённо:

- **83 %** — просмотренная доля узла `14871:1319`. Процент считается,
  а не читается: числитель (12 000 px) берётся из строки `renderCovered`,
  знаменатель (14 462 px) — из отдельного поля `height` того же узла.
  Сторожатся все три числа и сама строка `renderCovered` против пересчёта;
- **0 пар тем** — пара это проект, у которого среди снятых узлов есть
  и тёмный, и светлый. Считается по `nodes[].project` и `nodes[].theme`
  (9 dark · 6 light · 3 mixed). На этом нуле стоит решение Р-2;
- **все 19 покрытий блоков дробью**, а не шесть избранных: `18/18` hero,
  `17/18` шапка, `15/18` футер соцсетей и `15/18` копирайт, `11/18` форма,
  `10/18` программа, `9/18` партнёры, `8/18` спикеры, `7/18` нумерованные
  преимущества и `7/18` футер сообщества, `5/18` статистика и `5/18`
  интерактив, `4/18` бегущая строка, `3/18` номинации, `2/18` FAQ, таймлайн,
  галерея и корпоративный B2B-футер, `1/18` отзывы. Числитель — длина списка
  узлов, а не строка `coverage`. Подмена `2/18` → `9/18` у FAQ переключает
  `rule: false` в `rule: true` (METHOD §8) и раньше проходила зелёной.

Плюс сверки инвентаризации с самой собой: её итоги (`registryTotals`,
`roadmapTotals`, `findings.total`) написаны там же, где данные, и правятся
так же руками; к ним добавлены строка `coverage` и `coverageBase` каждого
блока против длины его же списка узлов — вычеркнутый узел оставлял «18/18»
при 17 узлах, и ни одна строка об этом не говорила.

Инвентаризация, которая не разбирается как JSON, даёт код 1 с текстом
ошибки разбора, а не стек Node.

## validate-classes.mjs

```bash
node tools/validate-classes.mjs                   # витрина пакета
node tools/validate-classes.mjs путь/к/блоку.html  # своя разметка
```

Две проверки.

**1. Классы без правила.** Класс, у которого нет правила в CSS, не
применяется молча — без ошибки в консоли и без следа, отличимого от «правило
есть, но слабое».

Своя разметка (аргументом) проверяется **только против `ui/`**. Если класс
статьи нашёлся лишь в `showcase/*.css`, оболочка витрины протекла в блок,
и на пустой странице с одним `ui/landings.css` он не сработает — инвариант
копируемости METHOD §6.1. Так проверяется `copy-check.html` перед сдачей
любого блока.

**2. Отделённость витрины, METHOD §6.2** — в обе стороны:

```
showcase/*.css и <style> витрины   каждый селектор несёт класс doc-*
ui/**/*.css                        ни одного класса doc-*, ни одной --doc-*
```

Проверка нужна именно механическая. В образце `career/showcase/components.css`
префикс держат только переменные: класса `doc-` нет **ни у одного** селектора —
**189 из 189**, 103 уникальных имени класса, среди них `.layout`, `.main`,
`.nav`, `.callout`, `.hint`, `.legend`. Рядом `pages.css` — ещё 63 селектора
и 25 имён, в счёт вообще не входивших. Замерено этим же разбором. Внимание
автора этот инвариант не удержало ни разу — строка R0-06 роадмапа прямо
запрещает повторять именование образца.

**Вторая сторона работает независимо от первой.** Скан `ui/` на протечку
оболочки идёт до всякого разговора о витрине: витрину заводит R0-06, а `ui/`
наполняют R0-02 и R0-03, и ранний выход по «витрины ещё нет» усыплял §6.2
ровно на этом промежутке. Сегодня `.doc-callout` в `ui/blocks/index.css`
даёт код 1 и без витрины; код 2 «проверять нечего» отдаётся только тогда,
когда витрины нет **и** протечек в `ui/` нет, и говорит об этом строкой.

Разбираются селекторы по отдельности, а не набор имён по файлу: иначе мимо
проходят селектор вовсе без класса (`body`, `button, input, a`) и класс
оболочки, объявленный в инлайновом `<style>` витрины. `:root` освобождён:
он несёт только переменные `--doc-*`.

Базовой линии известных пробелов (`known-missing-classes.json` у Курсов)
здесь нет и заводить её незачем: у Курсов она хранит утилиты Tailwind
со снятого прода, а разметка этого пакета с прода не снимается.

## validate-normative.mjs

```bash
node tools/validate-normative.mjs
```

**Проверка, специфичная для этого пакета.** Причина — в источниках:
переменных Figma в них нет (`get_variable_defs` отдаёт по лендингам только
`logo/*`, по бренд-доскам `{}` на 4 узлах из 4), и слой токенов выводится
из сырых литералов. Как только литерал переехал в переменную, снятое
и спроектированное становятся неразличимы на вид: `#0f0f0f` одинаково
выглядит и когда его сняли с узла, и когда придумали. Различить может
только пометка, а сторожить пометку — только скрипт.

Три области пакета нормативны целиком, и это решения владельца, а не вывод
из материала:

| Область | Почему норматив |
|---|---|
| светлая тема | решение Р-2: пар «один макет в двух темах» среди 22 узлов ноль (BRIEF §5 п. 5) |
| ось игривости | решение Р-3: опоры есть — вес дисплея 13/13, кислотный акцент, леттеринг 7/18, — самой шкалы в источнике нет |
| перенос стиля на веб-формат | BRIEF §5 п. 6: 23 из 23 баннеров — пост 1080 × 1350, веб-форматов ноль |

### Механика: маркер происхождения

Маркер — **отдельный CSS-комментарий, начинающийся с собаки**. Он действует
до следующего маркера или до конца файла, и под ним обязано стоять каждое
объявление:

```css
/* @snapshot 02_Landings 20097:8612 — фон и текст hero */
:root {
  --core-bg-page: #0f0f0f;
  --core-text-primary: #ffffff;
}

/* @normative светлая тема: 0 пар «один макет в двух темах» (BRIEF §5 п. 5) */
:root[data-theme="light"] {
  --core-bg-page: #ffffff;
}
```

- `@snapshot <файл Figma> <node id>` — снято. Имя файла сверяется
  с источниками инвентаризации (`02_Landings`, `04_Brand`), node id —
  с формой `20216:120`. Ссылка на несуществующий файл такой же вымысел,
  как выдуманное значение;
- `@normative <причина>` — спроектировано. Причина обязательна и не короче
  двенадцати знаков: маркер без причины — пожатие плечами, а не пометка;
- объявление, над которым маркера нет вовсе, — ошибка. На файл сообщается
  не больше трёх таких, остальные считаются числом: длинный файл без
  маркеров иначе даёт сотни строк, где первые три и так называют причину.

Маркером считается только комментарий, **начинающийся** с `@`. Поэтому шапка
`ui/landings.css`, объясняющая механику прозой, маркером не притворяется —
а вот `/* @snapshot 02_Landings 20216 */` с усечённым node id ошибку даёт.

### Механика: нормативная область под @snapshot

Селектор или переменная нормативной области под маркером `@snapshot` — ошибка
инварианта И-2. Такой маркер утверждает, что светлую тему сняли с узла;
снять её было не с чего.

Для оси игривости и веб-формата область узнаётся по имени: `--*-play*`
и `.play*`, `--*-web-format*` и `.web-format*`.

### Механика: контракт тем

Со светлой темой имени мало. Она — самая вероятная форма будущего R0-02,
и прецедент, на который пакет ссылается (Хабр `light-v2.css` / `dark-v2.css`),
устроен так: **светлая база, тёмная оверрайдом**. В такой записи в селекторе
светлой темы слова `light` нет вовсе — там просто `:root`. Поэтому область
темы определяется тремя способами по очереди.

**1. Селектор или преамбула.** Область названа темой явно:

```
[data-theme="light"]   [data-theme~="light"]   .theme-light   .light-theme
@media (prefers-color-scheme: light)
```

и те же четыре формы для `dark`. `light` ловится сегментом имени, а не
подстрокой: `--highlight-color` и `.highlight` темой не считаются.

**2. `color-scheme` внутри блока.** Если в самом блоке стоит
`color-scheme: dark` или `color-scheme: light`, тема названа им. Это не
выдуманный маркер, а штатное свойство CSS, которое ровно это и означает, —
и одновременно самый дешёвый способ назвать тему базовой области.

**3. Вывод исключением — для безымянной базы.** Тем в пакете две и обе
названы: измеренная тёмная и нормативная светлая (`ROADMAP.md`, строка «Тем»;
решение Р-2). Значит, если цветовая переменная объявлена в безымянной
корневой области (`:root`, `html`, `body`) и **ту же переменную** перекрывает
названная тема, база — тема противоположная. Перекрыта тёмной — база светлая:

```css
/* @snapshot 02_Landings 20097:8612 — палитра */
:root { --core-bg-page: #ffffff; }              /* ← ошибка И-2: база светлая */
:root[data-theme="dark"] { --core-bg-page: #0f0f0f; }
```

Если переменную перекрывают **обе** темы, вывести нечего — это ошибка
«тема базы не названа», и лечится она строкой `color-scheme: dark|light`
в том же блоке.

Переменная, которую не перекрывает никакая тема, темой не считается вовсе:
`--brand-acid` одинаков в обеих, и требовать от него имени темы незачем.
Цветом считается явный цветовой синтаксис — `#rgb`, `rgb()`, `hsl()`,
`oklch()`, `color-mix()` и остальные функции; `transparent` и `currentColor`
одинаковы в любой теме и в счёт не идут.

Чего механика не ловит: `color-scheme: dark` над белыми значениями. Это
прямая ложь в разметке происхождения, и автоматически она не отличима
от правды — ровно как «ааааааааааааа» в качестве причины `@normative`.
Такое ловит ревью, а не скрипт.

### Механика: маркер в статьях

Раздел статьи, где упомянута нормативная область, обязан назвать её
нормативом словами — «норматив», «спроектировано», «спроектирована».
Разделом считается кусок от заголовка до следующего заголовка того же или
высшего уровня; `README.md` не разбирается. Так ловится статья, где светлая
тема описана рядом со снятыми числами, без разделения.

Разбираются `blocks/`, `components/` и `docs/`. `evidence/` — намеренно нет:
там лежат протоколы снятых узлов, а среди 18 макетов светлых шесть, и
протокол вправе сказать «макет в светлой теме» как факт об артборде.
Нормативна светлая тема **продукта**, а не тема снятого узла, и, чтобы
разобрать `evidence/coverage.md` (R0-07), триггер сначала обязан различать
эти два смысла. Строка `X-11` роадмапа.

### Чего проверка не умеет

Она не судит, верно ли снято значение, и не сверяет число с узлом Figma —
это работа ревью (`guide-review`). Она отвечает ровно на один вопрос:
у каждого ли значения названо происхождение и не подписано ли
спроектированное как снятое.

Без `.pipeline/inventory.json` имя файла Figma в `@snapshot` сверять не с чем.
Проверка от этого не отключается молча: она печатает строку «Проверки
выключены» и продолжает. Ошибки маркеров печатаются **раньше** ветки
«проверять нечего»: прежний порядок глушил сломанный маркер в файле без
объявлений, а до R0-02 пакет состоит ровно из таких файлов.

## serve.mjs

```bash
node tools/serve.mjs        # или npm run serve
```

Порт **4180**, а не 4178 и не 4179: на 4178 сидит сервер `career/`,
на 4179 — `courses/`. Два пакета на одном порту дают `EADDRINUSE`, а хуже
того — один URL витрины на два разных набора файлов: кто поднялся первым,
тот и отдаёт, и правки видны не там, где их ищут. При старте печатается
корень, чтобы это было видно сразу.

Корень ведёт на `showcase/blocks.html`. Пока витрины нет (её заводит R0-06),
`/` отвечает текстом: сервер работает, витрины ещё нет, заводит её такой-то
шаг. Редирект на несуществующий файл дал бы пустой 404, а пустой 404 при
работающем сервере читается как «сервер сломан».

Отдаётся только то, что внутри корня пакета; `Cache-Control: no-store`,
потому что витрину правят и тут же перезагружают, а кэш браузера в этой
петле показывает предыдущую редакцию CSS.

## capture.mjs

```bash
node tools/capture.mjs --url https://technotext.habr.com --selector "header" \
  --out evidence/source/production/site-header --widths 1440,1600
```

Снимает узел живой страницы и кладёт в `--out`: `dom.html` (разметка
с вычищенными фреймворк-атрибутами, включая `data-w-id` Webflow),
`computed.json` (computed styles по всему поддереву), `tokens.json`
(кастомные свойства `:root` и подключённые шрифты), `<width>.png` на каждой
ширине и `meta.json` с URL, селектором, состоянием, датой и снятыми ширинами.

Ключи: `--widths` (**обязателен**, см. ниже), `--state hover|focus-visible`,
`--channel`, `--wait`, `--shot-timeout`, `--full-page`.

### Ширины: набора по умолчанию нет и не будет до двух решений

Вызов без `--widths` — ошибка вызова с кодом 2 и объяснением. Список ширин
ждёт:

- **Q-4** — какая ширина канонична. В 18 макетах пять разных ширин артборда:
  1600 — 8 узлов, 1440 — 5, 1400 — 3, 1280 — 1, 1240 — 1. Брейкпоинты
  Webflow из корпуса в Figma не подтверждаются (находка P2-8);
- **R0-00** — есть ли мобильные артборды вообще. В заданных 18 узлах их
  ноль, все 18 — одиночные десктопные (BRIEF §5 п. 4).

Дефолт, поставленный сейчас, был бы решением, принятым инструментом
за владельца, и разъехался бы по evidence всех последующих шагов. Набор
Курсов (`320,375,479,480,744,768,1024,1440`) здесь тем более неверен: он
построен на границах их прода, а не на ширинах этих артбордов.

> **Расхождение со скиллом `guide-build`.** Его §2 предписывает запуск
> с `--widths 375,768,1024,1440`. Из четырёх ширин с артбордами совпадает
> одна — **1440**, вторая по частоте (5 узлов из 18). Три остальные — 375,
> 768, 1024 — не встречаются ни у одного артборда, а четыре ширины, на
> которых нарисованы остальные **13 макетов из 18** (1600 — 8, 1400 — 3,
> 1280 — 1, 1240 — 1), в наборе скилла отсутствуют. Дефолт снимал бы
> тринадцать макетов не на их ширине. Пока Q-4 открыт, ширины называет тот,
> кто снимает, и записывает выбор в `.pipeline/<id>/capture.md`.

`dom.html`, `computed.json` и `tokens.json` снимаются на самой широкой
из запрошенных ширин — это записано в `meta.json` полем `computedAtWidth`.

### Что инструмент сообщает о своей работе

`meta.json` перечисляет в поле `widths` только те ширины, для которых PNG
действительно оказался на диске; запрошенный список лежит рядом
в `requestedWidths`, несостоявшиеся съёмки — в `failedWidths` с причиной.
Если снята не каждая ширина, скрипт печатает это в `stderr` и выходит
с кодом 1. Молчаливая потеря ширины означала бы, что evidence врёт о своей
полноте, — а весь пакет стоит на том, что evidence не врёт.

Ненайденный селектор — рядовой исход съёмки, а не отказ инструмента:
на живом лендинге узел переезжает и переименовывается. Скрипт печатает,
какой селектор не нашёлся и за сколько, закрывает браузер и выходит
с кодом 1.

**Инструмент прогнан на шаге R0-01** — все ветки, включая сквозную съёмку:
протокол в `.pipeline/R0-01/capture.md`. Зависимости в пакете нет: `npm i`
ставит `@playwright/test`, без него любой запуск падает
`ERR_MODULE_NOT_FOUND` раньше разбора ключей — то есть код 2 с объяснением
про Q-4 приходит только на поставленном пакете.

**Production этого пакета не переснимался** (BRIEF §4.4): оба аудита
работали «Figma против текста корпуса». Шесть из 18 узлов сходятся
с проектами корпуса, но не теми же редакциями — у совпавших макетов даты
и копирайт новее снятых страниц. Инструмент заведён под будущую сверку,
а не под уже сделанную.
