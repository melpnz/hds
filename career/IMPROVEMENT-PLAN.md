# План улучшения документации и UI kit Career

Дата аудита: **3 сентября 2026**  
Область: публичная гостевая часть `career.habr.com` и локальный пакет `career/`.

## 1. Цель

Сделать пакет пригодным не только для исследования существующего интерфейса, но и
для предсказуемой работы AI-агентов над новыми фичами. Агент должен уметь:

1. определить семейство экрана и целевую реализацию;
2. выбрать подтверждённые компоненты и композиционный паттерн;
3. собрать экран без смешивания Career, Хабра, Курсов и legacy;
4. обработать обязательные состояния и адаптив;
5. проверить результат автоматически и визуально;
6. явно сообщить о решениях, для которых нет evidence.

## 2. Что сравнивалось

### Локальные материалы

- `README.md` — карта знаний, Visual DNA и границы пакета;
- `RULES.md` — 57 правил и 16 Decision Guides;
- `components/` — 75 спецификаций;
- `ui/` — токены, foundation, utilities и CSS компонентов;
- `showcase/components.html` и `showcase/pages.html`;
- `evidence/` — production-снимки, curated references и coverage;
- `research/system-audit.md` — происхождение решений и история конфликтов.

### Текущий публичный сайт

- [главная Career](https://career.habr.com/);
- [листинг вакансий](https://career.habr.com/vacancies);
- [листинг компаний](https://career.habr.com/companies);
- [листинг специалистов](https://career.habr.com/resumes);
- [эксперты](https://career.habr.com/experts);
- [рейтинг компаний](https://career.habr.com/companies/ratings);
- [зарплаты](https://career.habr.com/salaries);
- публичная detail-страница вакансии;
- обычный и брендированный профили компаний.

Сравнение текущего сайта ограничено гостевым режимом. Закрытые формы, личный
кабинет, переписка, раскрытые порталы, success/error flows и часть модальных
сценариев нельзя считать проверенными.

## 4. Главные выводы

### Что уже можно считать опорой

1. Visual DNA: белые поверхности, холодная нейтральная шкала, границы вместо
   теней, фиолетовый для действий, синий для ссылок, высокая плотность.
2. Контейнер `1100 / 12`, основная сетка `752 + 24 + 300`, шаг карточек 12 и
   padding карточки 24 подтверждаются текущими продуктовым страницами.
3. Таксономия LISTING / DETAIL / PROFILE / DASHBOARD / SERVICE правильно описывает
   основную публичную часть Career.
4. Компонентные спецификации достаточно точны для воспроизведения существующей
   разметки.
5. Формат `OBSERVED / DECISION GUIDE / GAP` хорошо защищает от превращения
   единичного наблюдения в универсальное правило.

### Что мешает новым фичам

1. Нет короткого обязательного workflow для AI-агента. Пакет объясняет систему,
   но не задаёт единый порядок действий и формат результата.
2. Не определён нормативный default между новой и legacy-реализацией.
3. Главная `/` отсутствует в page families, хотя это значимая публичная часть
   текущего Career: hero-поиск, категории вакансий и курсов, рейтинги, зарплаты,
   журнал, рассылка и финальный CTA.
4. Брендированный профиль помечен как исключение, но не описан как отдельная
   управляемая система с разрешёнными зонами кастомизации.
5. Нет полного контракта состояний на уровне фичи: loading, partial loading,
   empty-before-search, no-results, validation, network error, retry, success,
   destructive confirmation, unauthorized и forbidden.
6. Нет режима «точная реплика» против «новая доступная фича». Например,
   документация фиксирует отсутствие видимого focus ring у части полей, но не
   устанавливает, должен ли новый интерфейс повторить дефект или исправить его.
7. `utilities.css` содержит только используемое подмножество Tailwind. Валидная
   новая утилита может отсутствовать в локальном runtime.
8. Нет воспроизводимого CI: заявленные copy-test, asset-test и visual checks не
   представлены командами, которые сможет запустить следующий агент.
9. Есть рассинхронизация метаданных: 99/100 компонентов, 120/121 переменная,
   63/64 CSS-секции и противоречивое описание локальности шрифта.
10. Документация велика и дублируется. Агенту не сообщено, что читать всегда, а
    что подгружать только для конкретного компонента или спорного решения.

## 5. Целевая модель документации

### 5.1. Слой 1 — обязательный контракт агента

Создать `AGENT_GUIDE.md` объёмом не более 150–200 строк.

Он должен содержать:

- область действия и явные исключения;
- default: **для новой фичи используется новая реализация**;
- условие, при котором разрешён legacy;
- обязательный workflow;
- список запрещённых импровизаций;
- два режима: `REPLICA` и `NEW_FEATURE`;
- формат фиксации `ASSUMPTION` и `GAP`;
- финальный acceptance checklist.

Рекомендуемый workflow:

```text
SCOPE → PAGE FAMILY → NEAREST REFERENCE → RULE IDS → COMPONENTS
→ STATES → RESPONSIVE → ACCESSIBILITY → VISUAL CHECK → HANDOFF
```

### 5.2. Слой 2 — нормативное ядро

Оставить нормативными только:

- `RULES.md` — композиция, адаптив и выбор решений;
- `tokens.css` + короткая семантическая карта токенов;
- реестр компонентов;
- спецификации компонентов;
- матрицу состояний.

Все остальные документы должны ссылаться на ID, а не повторять значения.

### 5.3. Слой 3 — evidence

Evidence должен подтверждать правило, но не участвовать в обычном prompt-контексте.
Для каждого изображения сохранить:

- route и дату фиксации;
- viewport;
- auth state;
- реализацию `legacy/new/mixed`;
- page family;
- связанные rule IDs и component IDs;
- статус `current / needs recheck / archived`.

### 5.4. Слой 4 — research/archive

`research/system-audit.md`, старые Storybook-кадры и история конфликтов нужны для
проверки происхождения, но не должны быть частью стандартного пути агента.

## 6. План улучшения документации

### P0 — сделать знания исполнимыми

#### D-01. Создать AI entry point

Результат: `AGENT_GUIDE.md` с алгоритмом, режимами, default-реализацией и
обязательным handoff.

Критерий готовности: новый агент, прочитав только entry point, знает, какие
следующие файлы открыть для LISTING, DETAIL, PROFILE и DASHBOARD.

#### D-02. Создать scope/route matrix

Для каждого route family указать:

- входит ли он в Career Product UI;
- modern, legacy или mixed;
- канонический reference;
- степень покрытия;
- запрещённые соседние системы.

Обязательно добавить `/` как отдельное семейство `HOME/MARKETING-HYBRID`, а
брендированные компании — как `BRANDED_PROFILE`, не смешивая их с PROFILE.

#### D-03. Устранить противоречия метаданных

Исправить и автоматически проверять:

- 99 или 100 компонентов;
- 120 или 121 custom property;
- 63 исходных файла и 64 собранные секции;
- шрифты описаны, но физически не хранятся;
- какие примеры полностью локальны, а какие требуют внешнего контента.

#### D-04. Добавить acceptance checklist

Минимальные проверки каждого нового экрана:

- правильное семейство и сетка;
- только разрешённые токены;
- отсутствие теней на обычных поверхностях;
- правильная роль primary action;
- состояния loading/empty/error/success/disabled;
- keyboard focus и семантическая разметка;
- 375, 768, 1024 и 1440;
- отсутствие горизонтального overflow;
- список допущений и неподтверждённых решений.

### P1 — закрыть расхождения с текущим сайтом

#### D-05. Задокументировать главную `/`

Снять desktop/mobile evidence и описать:

- hero с поиском;
- числовые product metrics;
- нумерованные секции;
- табы категорий;
- горизонтальные подборки карточек;
- переходы между Career и Courses;
- блоки рейтинга, зарплат и журнала;
- newsletter и финальный CTA;
- отличие этой композиции от продуктовой сетки 752 + 300.

#### D-06. Формализовать брендированные профили

Описать три слоя:

1. неизменяемая оболочка Career;
2. компоненты Career, допускающие brand tokens;
3. свободная рекламная зона компании.

Зафиксировать допустимые brand tokens, ограничения контраста, максимальные
кегли, правила секций, fallback без брендовых значений и мобильную перестройку.

#### D-07. Создать feature-state matrix

Отдельная таблица по компонентам и page families:

| State | Есть правило | Есть HTML | Есть visual evidence | Требует auth |
|---|---:|---:|---:|---:|
| Default | | | | |
| Loading | | | | |
| Empty | | | | |
| Error | | | | |
| Success | | | | |
| Disabled | | | | |
| Unauthorized | | | | |

#### D-08. Добавить продуктовую микрокопию

Нужны правила:

- обращение и тон;
- заголовки и пояснения;
- названия действий;
- сообщения ошибок и retry;
- подтверждение необратимых действий;
- empty/no-results;
- терминология вакансий, специалистов, компаний, зарплат и откликов.

### P2 — уменьшить стоимость поддержки

#### D-09. Ввести машиночитаемый manifest

Например, `manifest.json` или YAML:

```yaml
components:
  BaseButton:
    status: current
    implementation: new
    spec: components/actions/button.md
    css: ui/components/buttons.css
    showcase: "components.html#..."
    states: [hover, focus-visible, disabled, loading]
    confidence: high
```

Из manifest должны строиться счётчики README и coverage.

#### D-10. Убрать нормативное дублирование

README оставить навигационной картой. Значения токенов хранить в tokens,
правила — в RULES, статусы компонентов — в manifest. Changelog должен описывать
изменения, но не быть источником текущего состояния.

#### D-11. Ввести freshness policy

- shell и основные routes — проверка каждый релиз Career;
- компоненты — при изменении сборки;
- curated screenshots — дата и срок пересмотра;
- автоматический diff route inventory;
- правила перевода evidence в archived.

## 7. План улучшения UI kit

### P0 — определить контракт UI kit

#### U-01. Зафиксировать целевой runtime

Нужно выбрать и явно назвать один вариант:

- CSS + copy-ready HTML;
- Vue 3 component library;
- Tailwind preset + Vue components;
- framework-agnostic CSS primitives.

Текущий пакет сочетает все четыре подхода, поэтому формально UI kit пока не
имеет одного публичного API.

#### U-02. Разделить legacy и current

Предлагаемая структура:

```text
ui/current/       новая реализация, default для новых фич
ui/legacy/        только поддержка существующих страниц
ui/shared/        подтверждённые общие токены и композиция
```

Запретить незаметное смешивание классов из current и legacy.

#### U-03. Создать стабильный token contract

Добавить семантический слой поверх сырых цветов:

- `action-primary-*`;
- `action-danger-*`;
- `text-primary/secondary/tertiary`;
- `surface-page/card/overlay`;
- `border-card/control/focus`;
- `status-info/success/warning/danger`.

Сырые `--color-ui-*` оставить как foundation. Семантические токены дадут
агенту правильный выбор по роли, а не по похожему hex.

### P1 — сделать компоненты пригодными для новых фич

#### U-04. Собрать минимальное стабильное ядро

Первая поддерживаемая версия должна включать:

- Button, IconButton, LinkButton;
- TextInput, Textarea, Select, MultiSelect;
- Checkbox, Radio, Switch;
- Chip и StatusChip;
- Section/Card;
- Avatar и Icon;
- Tabs и Pagination;
- Notification, Toast, Modal;
- EmptyState, Skeleton и Loader.

Для каждого обязательны public API, все состояния, accessibility contract,
responsive behavior и visual tests.

#### U-05. Формализовать композиционные компоненты

Создать не только примитивы, но и стабильные layout primitives:

- `CareerShell`;
- `PageContainer`;
- `ListingLayout`;
- `DetailLayout`;
- `ProfileLayout`;
- `DashboardLayout`;
- `PageHeaderCard`;
- `SidebarCard`;
- `EntityCard`.

Это снизит вероятность того, что агент правильно оформит кнопки, но соберёт
непохожую страницу.

#### U-06. Решить проблему utility subset

Предпочтительный вариант — опубликовать Tailwind preset Career и генерировать
utilities из исходников новой фичи. Если это невозможно, manifest должен
содержать allowlist доступных утилит, а CI — отклонять отсутствующие классы.

#### U-07. Довести accessibility до нормативного уровня

Для новых компонентов зафиксировать:

- видимый `focus-visible` у всех интерактивных элементов;
- label/error/help связи полей;
- dialog semantics и focus trap;
- menu/listbox/combobox keyboard model;
- live regions для toast и async status;
- reduced motion;
- minimum target size;
- контраст текста, границ и focus indicators.

Исторические дефекты сохранить только в режиме legacy/replica.

### P2 — закрыть продуктовые модули

#### U-08. Реализовать основные entity cards

- VacancyCard;
- ResumeCard;
- CompanyCard;
- ExpertCard;
- RatingCard;
- SalarySummary/SalaryBar.

Нужны варианты данных: короткие/длинные названия, отсутствие зарплаты, много
навыков, удалёнка, несколько городов, rating/no-rating, промо и disabled action.

#### U-09. Добавить stateful modules

- фильтры листинга;
- search + sort + count;
- auth wall;
- form section;
- related entities carousel;
- promotion/guide block;
- conversations layout;
- page-level empty/error/loading.

#### U-10. Определить API брендирования

Branding должен передаваться ограниченным набором переменных, а не произвольным
CSS. Обязательны fallback, контраст и visual tests на светлых/тёмных брендах.

## 8. Автоматические проверки

Минимальный pipeline:

1. **Docs lint:** ссылки, дубли ID, обязательные разделы спецификаций.
2. **Manifest consistency:** автоматически вычисляемые количества и статусы.
3. **CSS lint:** неопределённые переменные, запрещённые raw colors, неизвестные
   utility classes, смешивание current/legacy.
4. **Component tests:** DOM, keyboard interaction и состояния.
5. **Accessibility smoke:** axe или эквивалент для showcase.
6. **Visual regression:** компоненты и page patterns на 375/768/1024/1440.
7. **Overflow check:** документ и каждый основной layout.
8. **Asset check:** все локальные ссылки разрешаются; внешние зависимости
   перечислены явно.
9. **Live drift report:** сравнение route inventory и ключевой структуры с
   production без автоматического принятия изменений за новую норму.

## 9. Рекомендуемая последовательность

| Этап | Состав | Результат |
|---|---|---|
| 1 | D-01—D-04, U-01—U-03 | Агент получает однозначный контракт; устраняются текущие противоречия |
| 2 | D-05—D-08, U-04—U-07 | Документация покрывает текущий публичный сайт и обязательные состояния |
| 3 | D-09—D-11, U-08—U-10 | Появляется поддерживаемый UI kit и снижается ручная стоимость обновлений |
| 4 | CI и visual regression | Изменения проверяются воспроизводимо, а drift становится видимым |

Начинать следует не с переноса всех 99/100 компонентов в библиотеку, а с
контракта агента, current/legacy boundary, layout primitives и 15–20 наиболее
частых компонентов. Именно они определяют качество большинства новых фич.

## 10. Definition of done

Работу можно считать завершённой, когда:

- новый агент стартует из одного файла и не обязан читать весь архив;
- для каждого публичного route определены scope, family, implementation и
  reference;
- current и legacy нельзя смешать случайно;
- значения и количества генерируются из manifest без ручных расхождений;
- UI kit имеет один документированный public API;
- ключевые layouts и компоненты покрыты состояниями и accessibility contract;
- showcase проходит visual regression на четырёх ширинах;
- любое решение без evidence автоматически попадает в handoff как `ASSUMPTION`;
- обновление production не меняет документацию молча, а создаёт drift report.
